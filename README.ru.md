# PetBox

PetBox - это один сервер с двумя задачами.

1. Он помогает ИИ-агентам для разработки помнить прошлое и держать работу в порядке.
2. Он служит маленьким бэкендом для ваших проектов: настройки, логи и базы данных.

Когда чат заканчивается, агент всё забывает. Он не знает, что решил на прошлой неделе. PetBox
даёт ему записную книжку, доску задач и набор инструментов. Небольшому проекту тоже нужно место
для настроек, логов и данных. PetBox даёт и его, так что три отдельных сервиса не нужны.

Я сделал его для своих проектов и развиваю на нём же: план и задачи PetBox лежат на его
собственных досках.

Технически это модульный монолит: одна программа из чётко разделённых модулей. У каждого модуля
есть переключатель в настройках. Выключенный модуль ничего не стоит.

## Стек

- **Языки:** C# на .NET 10, TypeScript, Python (только клиент).
- **Веб:** ASP.NET Core с Razor Pages, которые рендерятся на сервере. В браузере: htmx и Alpine.js. Стили: Tailwind и daisyUI. Фронтенд собирает bun.
- **Базы данных:** везде SQLite, доступ через linq2db. Схему меняет FluentMigrator.
- **Поиск:** SQLite FTS5 для слов, DuckDB для поиска по сессиям, со стеммингом Snowball. Эмбеддинги для смысла. Языковая модель может переранжировать.
- **Логи и запросы:** Kusto.Language разбирает KQL, а PetBox выполняет его на SQLite. Принимаются форматы Seq и OpenTelemetry. OpenTelemetry также трассирует сам PetBox.
- **Агенты:** сервер Model Context Protocol (MCP) и маршрутизатор языковых моделей.
- **Поставка:** Docker, Cake с GitVersion, GitHub Actions, Playwright для браузерных тестов.

DuckDB работает в продакшене в одном месте: индекс поиска по сессиям (см. Sessions). У модуля логов есть ещё диалект DuckDB для KQL, но настройки, которая его включает, нет.

## Модули

### Config

**Проблема:** одна и та же настройка в разных местах имеет разные значения.
**Решение:** значение привязывают к набору тегов, например `project:shop`, затем `service:api`,
затем `env:prod`. Запрос приносит свои теги. PetBox выбирает значение, все теги которого есть в
запросе. Побеждает то, где совпавших тегов больше. Два равных победителя дают ошибку, а не
догадку, поэтому ответ всегда один и тот же.

- У значения по умолчанию тегов мало. У переопределения для продакшена их больше, значит оно побеждает.
- .NET-клиент подключается к `IConfiguration` и опрашивает сервер об изменениях.

### Log

**Проблема:** небольшим проектам нужны логи, трассы и метрики, но не тяжёлая платформа.
**Решение:** PetBox принимает логи от клиентов Seq (формат CLEF) и от OpenTelemetry (логи, трассы
и метрики). У каждого проекта своё хранилище. Запросы пишут на KQL - языке из Azure Data Explorer.

- PetBox разбирает KQL официальной библиотекой Kusto.Language, затем превращает его в SQL для SQLite.
- Поддерживаются: `where`, `take`, `sort`, `top`, `project`, `extend`, `summarize`, `count`, `distinct`, `join`, `lookup`, `mv-expand` и `parse`.
- Не поддерживаются: `union`, `search`, `render`, `make-series` и многие другие. Неподдерживаемый оператор даёт понятную ошибку.
- Один и тот же язык работает на трёх таблицах: события, спаны и точки метрик.
- Есть живой хвост логов, очистка по сроку хранения и ссылки для обмена результатами.
- Логи хранятся в SQLite. У транслятора KQL есть ещё диалект DuckDB, его проверяют тестами рядом с SQLite. Сервер его не использует, и настройки для выбора нет.

### Data

**Проблема:** маленькому проекту нужна база данных, но не сервер баз данных.
**Решение:** у каждого проекта свои файлы SQLite. Вы отправляете параметризованный SQL по REST, а
PetBox его выполняет. Схему можно менять через версионируемые миграции.

- SQL строит клиент, поэтому серверу не нужно знать классы вашей модели.
- Тот же запрос можно выполнить и на локальной базе. См. «Клиентские пакеты».

### Tasks

**Проблема:** без правил задачи теряются, а у разных команд правила разные.
**Решение:** каждая доска следует методологии, которую вы задаёте: статусы и разрешённые переходы.
У меня так: идея, затем спецификация, затем работа, а новые запросы идут на доску входящих.
Движок блокирует переходы, которые нарушают правила. См. [doc/methodology.md](doc/methodology.md).

**Наблюдения (observations).** Агент часто замечает баг, который не относится к его задаче. В
каждом проекте есть особая доска для таких находок. Если другой агент сообщит о том же баге,
PetBox не создаст копию, а посчитает повторы. Человек может превратить наблюдение в задачу.
Когда задача выполнена, наблюдение закрывается. Если баг вернётся, оно откроется снова.

### Memory

**Проблема:** поиск по словам не находит заметку, написанную другими словами. Поиск по смыслу не
находит точные имена и коды ошибок.
**Решение:** PetBox запускает оба поиска и сливает списки через Reciprocal Rank Fusion (RRF).
Выигрывает запись, которая высоко стоит в обоих списках. Затем языковая модель может
переупорядочить лучшие результаты. Код слияния: `src/PetBox.Core/Search/HybridMerge.cs`.

- **История.** PetBox не затирает заметку. Каждая правка - новая ревизия, одна из них текущая.
- **Дубли.** Перед сохранением PetBox сравнивает факт со старыми: сначала по тексту, потом по смыслу. Почти копия не сохраняется.

### Sessions

**Проблема:** агент работает часами, а потом переписка пропадает.
**Решение:** агент сохраняет запись каждой сессии. Фоновая задача пишет короткую выжимку -
дайджест. Позже агент ищет по старым сессиям и узнаёт, почему выбрал то или иное решение.

Поиск идёт в два шага. Сначала PetBox находит нужные сессии по их дайджестам. Затем ищет внутри них.

- Для каждой найденной сессии PetBox строит временный индекс DuckDB в памяти. В нём полнотекстовый поиск с русским стеммингом и ранжированием BM25. Эмбеддинги сообщений сравниваются по косинусу.
- Два списка результатов сливаются через RRF. Если один список недоступен, второй всё равно отвечает.
- Индекс строится по запросу и сбрасывается примерно через десять минут простоя. Настройки лежат в разделе `Search:Episodic`.
- Код: `src/PetBox.Sessions/Episodic/DuckDbSessionEpisodicIndex.cs`.

### LLM router

**Проблема:** провайдер языковых моделей может упасть или ограничить число запросов.
**Решение:** маршрутизатор отправляет запрос первому рабочему провайдеру, а при сбое берёт
следующего. «Предохранитель» (circuit breaker) на короткое время перестаёт слать запросы сбойному
провайдеру. Он учитывает тип сбоя. Недоступный сервер пропускается для всех видов запросов.
Ответ «слишком много запросов» пропускается только для своего вида. Правило появилось после того,
как лимит на чат молча перекинул запросы эмбеддингов на резервный сервер.

### MCP

**Проблема:** в PetBox больше 100 инструментов. Если показать все, агент запутается, а менять
данные можно не каждому агенту.
**Решение:** MCP - стандартный способ, которым агент вызывает инструменты. У каждого API-ключа
есть список разрешений - scope. Например, `tasks:write` разрешает менять задачи.

- **Список.** Агент видит только те инструменты, что разрешены ключу. Без `tasks:write` он не увидит `tasks_upsert`.
- **Честные ответы.** `whoami` показывает все модули, scope и имена инструментов. Агент отличает «моему ключу нельзя» от «такого инструмента нет». `tool_describe` объясняет любой инструмент.
- **Безопасность.** Скрытие - не защита. Вызов без нужного scope отклоняется. Каждый инструмент объявляет scope один раз, а тест роняет сборку, если объявления нет.
- **Тестовые ключи.** Ключ-песочница (sandbox key) работает только в тестовых проектах. В остальных PetBox его отвергает.

### Dashboard и Deploy

- **Dashboard.** Проверяет здоровье ваших сервисов и опрашивает CI, так что статус виден в одном месте.
- **Deploy.** Ведёт учёт деплоев: что и когда было выложено.

## Клиентские пакеты

| Пакет | Реестр | Что делает |
|---|---|---|
| `PetBox.Client` | NuGet | HTTP-клиент с аутентификацией. Отправляет сырой SQL в модуль Data. |
| `PetBox.Client.Config` | NuGet | Загружает вычисленные настройки в `IConfiguration`, опрашивает сервер с учётом ETag. |
| `PetBox.Client.Data.Linq2Db` | NuGet | Позволяет писать запросы на LINQ через linq2db. |
| `@stdray-npm/petbox-client` | npm | TypeScript-клиент для Config и Data. |
| `petbox-client` | PyPI | Python-клиент для Config и Data. |
| `petbox-wire` | npm | Одна команда `npx`, которая подключает проект к PetBox: хуки, настройки MCP и навыки для Claude Code, opencode и Factory Droid. |

Как работает пакет с LINQ:

- Вы строите обычный `IQueryable` linq2db. Хватает подключения к SQLite, и оно даже не открывается.
- Пакет достаёт параметризованный SQL и отправляет его через `PetBox.Client`.
- Строки возвращаются в вашем классе. Сервер ваших объектов запроса не видит.
- Тот же `IQueryable` выполняется и на локальном файле SQLite обычным linq2db. Один запрос работает и на удалённой базе, и на локальной копии.

## Сборка и запуск

Нужны .NET 10 SDK (см. `global.json`), bun и PowerShell или bash.

```sh
./build.ps1 -Target Test        # или: ./build.sh --target=Test
./build.ps1 -Target Dev         # watcher'ы фронтенда и `dotnet watch run`
./build.ps1 -Target Verify      # Test плюс проверки клиентских библиотек
```

Контейнер слушает порт 8080 и хранит данные в `/app/data`. Остальные цели смотрите в `build.cs`.

## Как я держу качество

- **Один гейт.** Цель `Test` собирает код, проверяет форматирование, проверяет фронтенд линтером и запускает больше 4000 тестов. CI запускает ту же цель.
- **Правила как тесты.** Тесты проверяют архитектуру. Модули не лезут друг в друга. Подключения к базе нельзя получить через DI, потому что они не потокобезопасны. Арендаторы не читают чужие данные. См. `tests/PetBox.Tests/Architecture`.
- **Безопасный деплой.** Тег `deploy` запускает тесты, собирает образ, выкладывает по SSH и проверяет здоровье. Проверка качества кода может остановить деплой.
- **Процесс.** Любое изменение начинается с карточки задачи и делается в отдельном git worktree. См. [AGENTS.md](AGENTS.md).
