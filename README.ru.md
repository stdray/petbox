# PetBox

PetBox - это сервер, который помогает ИИ-агентам для разработки помнить прошлое и держать работу в порядке.

Когда чат заканчивается, агент всё забывает. Он не знает, что решил на прошлой неделе. Он не
видит, какие задачи ещё открыты. PetBox это исправляет: даёт агенту записную книжку, доску задач
и набор инструментов в одном сервисе. Я сделал его для своих проектов и развиваю на нём же:
план и задачи PetBox лежат на его собственных досках.

Технически это модульный монолит: одна программа из чётко разделённых модулей. Каждый модуль
включается и выключается настройкой. Выключенный модуль ничего не стоит.

## Как агент помнит

### Сессии

**Проблема:** агент работает часами, а потом переписка пропадает.
**Решение:** агент сохраняет запись каждой рабочей сессии. Фоновая задача делает из неё короткую
выжимку - дайджест. Позже агент ищет по старым сессиям и узнаёт, почему принял то или иное решение.

### Память

**Проблема:** поиск по словам не находит заметку, если слова другие. Поиск по смыслу не находит
точные имена и коды ошибок.
**Решение:** PetBox запускает оба поиска и сливает два списка. Способ слияния называется
Reciprocal Rank Fusion (RRF): выигрывает запись, которая высоко стоит в обоих списках. Затем
языковая модель может переупорядочить лучшие результаты.

- Поиск по словам работает на SQLite FTS5. Поиск по смыслу - на эмбеддингах: они превращают текст в числа.
- Код слияния: `src/PetBox.Core/Search/HybridMerge.cs`.

### История и дубли

**Проблема:** агенты правят свои заметки, а иногда старая версия была верной.
**Решение:** PetBox никогда не затирает заметку. Каждая правка сохраняется как новая ревизия,
одна из них считается текущей. Старые версии всегда можно посмотреть.

**Проблема:** агенты сохраняют один и тот же факт много раз разными словами.
**Решение:** перед сохранением PetBox сравнивает новый факт со старыми. Сначала проверяет
точный текст, потом смысл. Если новый факт слишком похож на старый, он не сохраняется повторно.

### Наблюдения

**Проблема:** агент замечает поломку, но она не относится к текущей задаче. Такую находку легко потерять.
**Решение:** в каждом проекте есть особая доска - наблюдения. Агент записывает находку туда.
Если другой агент сообщит о той же проблеме, PetBox не создаст копию, а посчитает, как часто
проблема повторяется. Позже человек может превратить наблюдение в настоящую задачу. Когда
задача выполнена, наблюдение закрывается. Если проблема вернётся, оно откроется снова.

## Как агент продолжает работать

### Маршрутизатор языковых моделей

**Проблема:** агент обращается к моделям нескольких провайдеров. Провайдер может упасть или
ограничить число запросов.
**Решение:** маршрутизатор отправляет запрос первому рабочему провайдеру. Если тот не отвечает,
берёт следующего. «Предохранитель» (circuit breaker) на короткое время перестаёт слать запросы
сбойному провайдеру.

Предохранитель учитывает тип сбоя.

- Если сервер недоступен, маршрутизатор пропускает провайдера целиком.
- Если провайдер отвечает «слишком много запросов», пропускается только этот вид запросов.

Это правило появилось после реального случая. Лимит на чат-запросы молча перекинул запросы
эмбеддингов на резервный сервер.

### Инструменты для агентов (MCP)

**Проблема:** в PetBox больше 100 инструментов. Если показать все, агент запутается. Часть
инструментов меняет данные, и не каждому агенту их стоит давать.
**Решение:** MCP - стандартный способ, которым агент вызывает инструменты. Каждый API-ключ
получает список разрешений - scope. Например, scope `tasks:write` разрешает менять задачи.

- **Список.** Агент видит только те инструменты, которые разрешены его ключу. Без `tasks:write` он не увидит `tasks_upsert`.
- **Честные ответы.** Инструмент `whoami` показывает все модули, все scope и имена всех инструментов. Агент отличает «моему ключу нельзя» от «такого инструмента нет». Инструмент `tool_describe` объясняет любой инструмент по имени.
- **Безопасность.** Скрытие - не защита. Если ключ вызовет инструмент без нужного scope, PetBox откажет. Каждый инструмент объявляет свой scope один раз, а тест роняет сборку, если объявления нет.
- **Тестовые ключи.** Ключ-песочница (sandbox key) работает только в тестовых проектах. В остальных PetBox его отвергает, поэтому тестовый прогон не заденет настоящие данные.

### Доски задач

**Проблема:** задачам нужны правила, иначе они теряются. А у разных команд правила разные.
**Решение:** каждая доска следует методологии, которую вы задаёте сами. Методология - это набор
статусов и разрешённых переходов. У меня так: идея, затем спецификация, затем работа, а новые
запросы сначала попадают во входящие. Движок блокирует переходы, которые нарушают правила.
Подробности: [doc/methodology.md](doc/methodology.md).

## Что ещё внутри

В PetBox есть также сервис настроек, сборщик логов с языком запросов KQL, отдельная база SQLite
для каждого проекта, дашборд здоровья и CI, учёт деплоев.

| Модуль | Задача |
|---|---|
| `PetBox.Core` | вход, модели данных, миграции, поиск |
| `PetBox.Web` | веб-приложение и MCP-эндпоинт |
| `PetBox.Tasks`, `PetBox.Tasks.Engine` | доски задач и правила методологии |
| `PetBox.Memory` | заметки и поиск по памяти |
| `PetBox.Sessions` | записи сессий и дайджесты |
| `PetBox.LlmRouter` | маршрутизатор языковых моделей |
| `PetBox.Config`, `PetBox.Log.Core`, `PetBox.Data` | настройки, логи, базы проектов |
| `PetBox.Dashboard`, `PetBox.Deploy` | проверки здоровья, учёт деплоев |

Клиентские библиотеки для .NET, TypeScript и Python лежат в `src/clients-net`, `src/clients-ts`
и `src/clients-py`.

## Стек

- Бэкенд: .NET 10, SQLite с linq2db, FluentMigrator, OpenTelemetry.
- Фронтенд: Razor Pages с рендерингом на сервере, htmx, Alpine.js, Tailwind с daisyUI, TypeScript, собранный bun.
- Поставка: Docker, Cake с GitVersion, GitHub Actions, Playwright для браузерных тестов.

## Сборка и запуск

Нужны .NET 10 SDK (см. `global.json`), bun и PowerShell или bash.

```sh
./build.ps1 -Target Test        # или: ./build.sh --target=Test
./build.ps1 -Target Dev         # watcher'ы фронтенда и `dotnet watch run`
./build.ps1 -Target Verify      # Test плюс проверки клиентских библиотек
```

Контейнер слушает порт 8080 и хранит данные в `/app/data`. Остальные цели смотрите в `build.cs`.

## Как я держу качество

- **Один гейт.** Цель `Test` собирает код, проверяет форматирование, проверяет фронтенд линтером и запускает больше 4000 тестов. CI запускает ту же цель. Зелёный локальный прогон означает зелёный пайплайн.
- **Правила как тесты.** Тесты проверяют саму архитектуру. Модули не лезут друг в друга. Подключения к базе нельзя получить через DI, потому что они не потокобезопасны. Арендаторы не читают чужие данные. См. `tests/PetBox.Tests/Architecture`.
- **Безопасный деплой.** Тег `deploy` запускает тесты, собирает образ, выкладывает по SSH и проверяет здоровье. Проверка качества кода может остановить деплой.
- **Процесс.** Любое изменение начинается с карточки задачи и делается в отдельном git worktree. Правила - в [AGENTS.md](AGENTS.md).
