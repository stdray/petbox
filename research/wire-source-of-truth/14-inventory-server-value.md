# Инвентаризация: какую пользу серверное хранение agent-defs несёт сегодня

Дата: 2026-08-30. Автор: petbox-worker (Sonnet 5). Область: серверный API agent-defs
(REST + MCP + admin UI) — что он реально даёт сейчас и что из этого `petbox-wire` может
сделать сам.

## Ответ одной строкой

Минимальный остаток — ровно одна вещь: живая правка ролевой прозы БЕЗ релиза кита и БЕЗ
git у получателя (правка сегодня, версия 18, `updated 2026-08-29` — проверено живьём).
Всё прочее (мерж по ролям, seed на создание проекта, per-project scope) — операции НАД
этим хранилищем, переносимые на файлы+CLI. Витрина для импорта сегодня не нужна вовсе:
второго человека, который реально делится, ещё нет (project_list проверен живьём).

## Факты

1. Живое использование, не гипотеза: `$system/default` version=18, updated
   2026-08-29T08:24 — правка происходит регулярно (mcp__petbox__agent_def_list, live
   2026-08-30, эта сессия).
2. Канон явно называет сервер единственным местом ролевой прозы: `AGENTS.md:255-256`
   ("role rules ... live in exactly ONE place: the server agent definition
   (agent_def_get('default'), project $system)... it drifts the moment either side
   changes").
3. Реальные вызывающие места резолвера (не тесты): `wire.ts:980` (apply),
   `status.ts:433` (doctor), `pull-memory.ts:99` (Claude Code SessionStart),
   `droid-pull-memory.ts:94` (droid), `opencode-plugin.ts:51` (opencode) — все три
   харнесса и apply/doctor реально читают через `agent-def-fetch.ts:340`
   `resolveAgentDefinitionWithLkg`.
4. Порядок разрешения зашит в коде: сервер → LKG-кэш
   (`~/.petbox/cache/<project>.agent-def.json`) → `DEFAULT_AGENT_DEFINITION` (кит)
   — `agent-def-fetch.ts:362-431`. Сервер уже сегодня НЕ единственный источник, а
   первый по приоритету перед файловым кэшем и хардкодным дефолтом кита.
5. Каждый новый проект сидируется дефолтным agent-def при создании,
   `ProjectAgentDefSeeder.cs:41-52`, никогда не перезаписывая существующий (version=0
   CAS, probe-then-write).
6. Авторизация per-project, не глобальная: scopes `agents:read`/`agents:write`,
   `ApiKeyScopes.cs:74-75,112-113`. REST и MCP используют один и тот же
   `IAgentDefinitionService` — `AgentDefsApi.cs:14`, `AgentDefTools.cs:9-11`.
7. Три поверхности над одним хранилищем: REST GET/PUT/DELETE (`AgentDefsApi.cs:10-13`),
   MCP `agent_def_list/get/upsert/delete` (`AgentDefTools.cs:26` и далее), admin-страница
   raw-JSON редактор (`ProjectAgentDefs.cshtml.cs:12-15`) — одна и та же запись видна
   во всех трёх немедленно.
8. Кто реально пользуется MCP-глаголами: `AGENTS.md:255` предписывает
   оркестратору читать `agent_def_get('default')` перед спавном воркера — то есть
   основной потребитель MCP-пути это АГЕНТ-ОРКЕСТРАТОР при делегировании, не человек
   через чат. ПРЕДПОЛОЖЕНИЕ: подтверждено прозой канона, не логами вызовов (не проверял
   access-log).
9. Провенанс правки НЕ хранится: `AgentDefinitionView` несёт только
   Key/Definition/Version/Created/Updated — `AgentDefinitionViews.cs:42-46`. Кто именно
   правил — нигде в этой модели.
10. Мерж по ролям — upsert принимает частичный список ролей, патчит по `slug`, explicit
    `deleted:true` для удаления (`AgentDefTools.cs`, описание `agent_def_upsert`,
    ~строка 60-90) — оверлей-семантика уже в проде, не гипотеза резерва.
11. Кит несёт СВОЮ копию базиса в гите: `src/common/default-agents.json`,
    `src/clients-ts/petbox-wire/src/default-agents.json`, плюс хардкод
    `DefaultAgentDefinition.cs`. Комментарий `ProjectAgentDefSeeder.cs:8-9` ссылается на
    тест `DefaultAgentDefinitionSyncTests`, которого под этим именем в дереве нет —
    вероятный кандидат `default-agents-baseline.test.ts`, построчно не сверял.
12. Если убрать API целиком: `AgentDefsApi.cs`, `AgentDefTools.cs`,
    `ProjectAgentDefs.cshtml.cs` гаснут одновременно (все три висят на одном сервисе,
    факт 6). `resolveAgentDefinitionWithLkg` не падает — откатывается на LKG, а на новой
    машине без LKG сразу на `DEFAULT_AGENT_DEFINITION` кита (`agent-def-fetch.ts:408-434`).
13. Что реально ломается: правка прозы, сделанная ТОЛЬКО на сервере (версия 18, факт 1)
    и ни разу не закоммиченная в `default-agents.json`, становится недостижима для всех
    без своей копии в гите. Единственный оставшийся канал — закоммитить + релиз кита +
    все делают `wire update` — то есть именно то, что `AGENTS.md:255` сегодня явно
    называет плохим ("it drifts the moment either side changes").
14. Витрина: авторизация через существующие project-scoped API keys (`ApiKeyScopes.cs`)
    — то, чего бесплатно НЕ даёт голый git URL/gist/npm-пакет (публичный gist = видно
    всем; приватный = отдельный токен вне petbox). Это реальная разница именно сервера.
15. Второго человека, который делится, сегодня нет: `project_list` (live, 2026-08-30)
    показывает один workspace `stdray` с проектами одного владельца плюс служебные
    `$ws-*`/`$system`/`smoke` контейнеры — ни одного второго пользователя/шаринга.
    Ключ этой сессии видит только `$system` (agent_def_list на `petsonde`/`infra`/
    `agent-relay` вернул `UnauthorizedAccessException` — per-project scope, факт 6,
    подтверждён на практике, не только по коду).

## Что из этого следует для гипотезы «источник истины — файлы»

Единственная сегодняшняя польза, которая ГЕНУИННО теряется при переходе на файлы —
факты 1, 2, 13: live-правка прозы без релиза кита и без git у получателя. Всё
остальное (мерж по ролям, per-project override, seed-on-create, три поверхности над
одним хранилищем) — это операции НАД хранилищем, переносимые на файлы + CLI; `roles.json`
уже прецедент локального оверлея (`petbox-agent-factory` SKILL.md). Минимальный остаток —
не "сервер", а write-хранилище с авторизацией и версионированием для прозы, которая
правится ЧАЩЕ, чем релизится кит; для этого не обязателен именно petbox — годится любой
тонкий authenticated write endpoint. Витрина (п.14-15) сегодня не нужна — обслуживает
сценарий, которого ещё нет (второй человек), а не текущую потребность.

## Спорное

Тезис резерва «(б) витрина — ВНЕ контура разрешения» противоречит текущему коду: apply/
doctor/session-banner делают live-fetch сервера ПЕРВЫМ шагом (`agent-def-fetch.ts:362-406`,
факт 3-4), не разовый импорт-копию. Если реализовать «витрину вне контура», это отдельное
изменение поведения `apply` (убрать сервер из resolve-цепочки для витринной роли), а не
просто переименование существующей роли сервера — резерв описывает ЦЕЛЕВОЕ состояние,
а не наблюдаемое.

## Чего я не проверил

- Нет доступа к agent-defs других проектов под ключом этой сессии (agents:read только на
  `$system`) — не могу подтвердить/опровергнуть, есть ли СЕГОДНЯ хоть один проект с
  оверлеем, отличным от дефолта (факт 10 подтверждён по коду API, не по данным).
- Не сверил построчно `default-agents-baseline.test.ts`; не проверял access-log сервера на
  частоту вызовов `agent_def_get` (факт 8 — по прозе `AGENTS.md`, не по замеру); сценарий
  «друзья на инстансе владельца» не проверен эмпирически (второго человека пока нет).

## Дополнение: идея владельца — зеркалирование user/project-scoped слоёв в PetBox

Ответ на пункты «требует проверки» из `04-owner-idea-mirroring.md`. Факты, не мнение.
Вывод раздела ниже: минимальный остаток из первой части НЕ меняется.

**1. Сущность «профиль пользователя» с хранением — нет.** `UserAccount` (веб-логин/admin)
несёт Id/Username/CreatedAt/WorkspaceQuota/Memberships, без поля произвольного документа
(`UserAdminService.cs:16-21`). Решающий факт: то, чем пользуется `petbox-wire` — ApiKey-схема
— пользователя вообще НЕ ЗНАЕТ. `ApiKey`: Key/ProjectKey/Scopes/Name/CreatedAt/ExpiresAt/
DefaultProjectKey/SandboxOnly/LastUsedAt/CreatedBy/HostId (`ApiKey.cs:6-73`) — нет `UserId`.
Живой `whoami` подтверждает: `{project, scopes}`, без пользователя (live, эта сессия).
Единственный намёк на человека — `CreatedBy` (`ApiKey.cs:56-60`): строка-метка
`"user:<username>"` о том, КТО ВЫПУСТИЛ ключ — не FK-связь и не хранилище документа. Цена
идеи: нужна НОВАЯ таблица user-scoped документов И новая привязка ApiKey→User (её нет) —
два новых механизма, не «положить в существующее место».

**2. Воркспейс как носитель — нет, это другая ось.** `$ws-{workspace}` — контейнер ГРУППЫ
ПРОЕКТОВ, не человека: `WorkspaceMembership` многие-ко-многим (`WorkspaceMembershipService.cs
:8,16`) — один юзер состоит в N воркспейсах, один воркспейс видят N юзеров. У владельца
сегодня один воркспейс `stdray` на одного человека (live `project_list`), поэтому ось
путается с «профилем», но модель — группа проектов. Второй участник ТОГО ЖЕ воркспейса
получил бы тот же слой — не свой личный.

**3. Полярность — не разводится без переписывания.** Сегодняшнее хранилище — НЕ дельта:
`MergeRolesAsync` мержит правку в ПОЛНЫЙ документ НА ЗАПИСИ (`AgentDefinitionService.cs:132`,
`AgentDefinitionJson.MergeRoles`) и сохраняет результат целиком; клиент получает готовый
документ и использует как есть (`agent-def-fetch.ts:376-385`) — клиентского слияния с
базисом кита нет вообще. Предложенное «базис из кита, слой с сервера, мердж на чтении»
требует: сервер хранит/отдаёт именно ДЕЛЬТУ (не резолвленный документ) — переписать модель
хранения; и клиент мержит на чтении — переписать `resolveAgentDefinitionWithLkg`. На
существующем коде «как есть» это не работает ни с одного конца.

**4. Офлайн — унаследует известную поломку, если не переделать кэш.** Сегодня: сервер → LKG
(кэш ПОЛНОГО документа) → `DEFAULT_AGENT_DEFINITION`, молча, с баннер-пометкой
(`agent-def-fetch.ts:408-434,458-491`); битый/отсутствующий кэш неразличим без спец-логики
(`readAgentDefCache:274-280`, баг `wire-silent-failures-invisible`). При слоях кэш ПОЛНОГО
документа не годится — нужен кэш ИМЕННО СЛОЯ отдельно от базиса, иначе баннер не может
сказать «работаю на голом базисе, персонализация недоступна» — ровно то, что идея сама
называет плохим (`04-owner-idea-mirroring.md:36-38`). Это новая форма кэша, не переиспользование.

**5. Мультимашинность — не подтверждена как текущая проблема.** Второй физической машины в
артефактах не нашёл: workspace-канон прямо говорит «Single user (stdray)» (memory canon
`index`, scope workspace, live); `project_list` не показывает второго участника. Найдено
РОДСТВЕННОЕ, не то же самое: WSL-чекаут на ТОЙ ЖЕ коробке («box stdray», память
`wsl-fresh-checkout-git-gotchas`, live) — Windows и Linux `$HOME` разные каталоги на одном
хосте, `~/.petbox/roles.json` реально дублируется уже сегодня БЕЗ второй машины. Проект
`agent-relay` (live `project_list`: «remote access to terminal CLI agents on the home PC»)
— это управление агентами, УЖЕ выполняющимися на home PC, не второй исполняющий хост — не
довод за мультимашинность в смысле идеи. Заявленная польза решает largely гипотетическую
проблему; единственный наблюдаемый случай дублирования — Windows/WSL на одной коробке.

**Пересмотр вывода.** Минимальный остаток из первой части (живая правка прозы без релиза
кита) не меняется — идея предлагает ДРУГОЙ механизм (профиль пользователя) для ДРУГОЙ
пользы (мультимашинность), эмпирически не подтверждённой как текущая проблема. Добавляю к
цене идеи: новая сущность user-scoped storage, новая привязка ApiKey→User, переписанная
модель хранения (дельта вместо резолвленного документа) и переписанный клиентский резолвер
— не мелкая правка контура `agent-def-fetch.ts`, а три независимых переделки.
