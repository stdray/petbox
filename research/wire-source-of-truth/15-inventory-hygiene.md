# Гигиена petbox-wire: имена скилов и путь ~/.petbox

Дата: 2026-08-30. Автор: petbox-worker (Sonnet 5). Область: два пункта владельца — паттерн
имён скилов `petbox-*` и переезд `~/.petbox` → путь по конвенции — плюс их реальная цена.

## Ответ одной строкой

Пункт 1: все 5 скилов, которые СТАВИТ `petbox-wire`, уже названы `petbox-*` — переименовывать
нечего; непрефиксованные скилы в репозитории (`analysis-workspace`, `factory-run`) заведены
владельцем вручную, не китом, и переименование — не дело wire. Пункт 2: `~/.config/petbox`
взято слепо — Unix-путь на Windows-машине владельца; нужен нативный сплит по типу данных
(config/secrets/cache/state), а не один каталог под любым именем.

## Факты

1. `writeSkillFiles` ставит ровно 5 скилов, ВСЕ уже с префиксом `petbox-`: `petbox`,
   `petbox-agent-factory`, `petbox-methodology`, `petbox-write-economy`, `petbox-node-authoring`
   — `src/clients-ts/petbox-wire/src/skill-files.ts:52-58`. Пишутся в `.claude/skills/<dir>` и
   `.factory/skills/<dir>` — `skill-files.ts:33-36`.
2. В этом же репозитории `.claude/skills/` лежат ещё три скила БЕЗ префикса или с иным:
   `analysis-workspace`, `factory-run`, `petbox-methodology-system` — все закоммичены в гит
   (`git ls-files .claude/skills`), ни один не упомянут в `PROJECT_SKILLS` и ни один не
   рендерится из `src/clients-ts/petbox-wire/src/templates/` (там только 5 директорий,
   один-в-один с PROJECT_SKILLS). Значит это ручная работа владельца поверх кита, не артефакт
   wire.
3. На уровне пользователя (`~/.claude/skills`) стоят `droid-handoff`, `pi-handoff`,
   `playwright-cli` — тоже без префикса. `pi-handoff` — симлинк на `D:\my\prj\llama-tooling\pi-handoff`
   (другой репозиторий), `droid-handoff` зарегистрирован в `~/.claude.json:1867` — оба явно
   ручная установка, не petbox-wire (в исходниках wire нет ни одного упоминания этих трёх имён).
4. `default-agents.json` НЕ содержит ни одного упоминания слова "skill" — проверено
   `grep -in skill src/common/default-agents.json` (пусто). Ролевая проза сегодня не ссылается
   на скилы по имени, значит поле немедленного риска при переименовании ровно пяти
   wire-скилов — тесты, не проза ролей.
5. Тесты хардкодят имена директорий буквально, не через константу PROJECT_SKILLS:
   `doctor-skill-drift.test.ts:194` (`"petbox-agent-factory"`) и `:199`
   (`"petbox-methodology"`). Переименование любого из пяти потребует правки этих тестов вручную.
6. Прецедент именно для ЭТОГО класса переименования уже есть в коде, но НЕ подключён к скилам:
   `cleanupLegacyArtifact` (`apply-write.ts:73`, комментарий `:15-19`) — родился из бага
   `petbox-namespaced-agent-names`, когда файлы агентов переименовали в `petbox-<slug>` и старый
   непрефиксованный файл нужно было явно удалить (только если он несёт origin-marker кита).
   Подключён СЕГОДНЯ только для agent-файлов — `wire.ts:774-782` (`file.legacyRelativePath !==
   file.relativePath`). `writeSkillFiles` (`skill-files.ts:118-133`) такого вызова не делает —
   при гипотетическом будущем переименовании скила старый каталог станет орфаном НАВСЕГДА, apply
   его не тронет (`apply-write.ts:18`: "It is only ever removed when it carries our marker").
   Друзья владельца после `update` + `apply` получат ОБА комплекта — старое имя остаётся на
   диске, новое дописывается рядом.
7. Путь `~/.petbox` НЕ централизован: `join(homedir(), ".petbox", …)` повторён построчно в 8
   файлах — `agent-def-fetch.ts:125`, `canon.ts:59`, `posix-env.ts:22,26,30`, `registry.ts:48,57`,
   `roles.ts:76`, `wire-log.ts:29`, `wire.ts:202,1078,1113,1246,1540,1552` (список неполный,
   `grep -n "\.petbox\b"` даёт 17 файлов всего). Нет ни одной обёртки вида `petboxDir()`.
8. Ни один XDG- или Windows-env (`XDG_CONFIG_HOME`, `APPDATA`, `LOCALAPPDATA`) не встречается в
   `src/clients-ts/petbox-wire/src/*.ts` — проверено `grep`, ноль совпадений (кроме тестов).
   `homeDir` инжектируется только для тестов, реальный код всегда берёт `homedir()` из
   `node:os` — платформа никогда не учитывается.
9. Реальное содержимое `~/.petbox/` на машине владельца (Windows 11): `roles.json` (4.8К),
   `projects.json`, `keys.json` (496Б — секреты), `e2e.env` (простым текстом пароль админа
   стенда — та же секретная категория, что и keys.json, но НЕ упомянут в брифе как секрет),
   `wire.log` (15К, растущий лог), `cache/` (LKG-реплики канона и agent-def по проектам — это
   именно КЭШ, безопасно удаляемый), `wire/` (полное зеркало пакета kit — исходники + шаблоны,
   это НЕ конфиг/кэш/лог/секрет, это установленный бинарник/данные приложения — 5-я категория,
   которую бриф не называл).
10. `runUpdate` (`wire.ts:1504-1520`) явно ограничен: копирует только `~/.petbox/wire/` с
    orphan-cleanup (`wire.ts:1461-1468`) и НЕ трогает `keys.json`/`projects.json` — цитата из
    кода: "Intentionally does NOT: rotate/require API keys, touch ~/.petbox/keys.json or
    projects.json" (`wire.ts:1506`). Прецедента миграции КОРНЯ каталога (переноса
    config/secrets в новое место) в коде нет вообще — есть только прецедент миграции содержимого
    файла на месте (`pruneLegacyPromptRagHooks`, `wire.ts:1477-1500`, тихая, идемпотентная,
    залогированная — но это правка файла, не переезд каталога).
11. Внешние аналоги (WebSearch, 2026-08-30): gh CLI — приоритет `GH_CONFIG_DIR` >
    `$XDG_CONFIG_HOME/gh` (если явно задан) > `%AppData%\GitHub CLI` (нативно на Windows) >
    `$HOME/.config/gh` (PR cli/cli#3671, cli/cli#2080). opencode — на Windows ВСЕГДА
    `%APPDATA%\opencode`, XDG-логика (`~/.config` или `$XDG_CONFIG_HOME`) применяется только
    вне Windows (issue anomalyco/opencode#6669, NoeFabris/opencode-antigravity-auth#265). npm —
    `.npmrc` в домашнем каталоге на всех платформах, но кэш отдельно и нативно:
    `%AppData%\npm-cache` на Windows. Claude Code (этот же харнесс) — наблюдается прямо в сессии:
    `~/.claude/settings.json`, `~/.claude.json` (`/c/Users/stdray/.claude/...`) — плоский
    dot-каталог в HOME на всех платформах, БЕЗ XDG и БЕЗ AppData вообще, без деления по типу
    данных.

## Что из этого следует для гипотезы «источник истины — файлы»

К пункту 1 гипотеза не относится напрямую, но факт 6 важен для «дешевизны файлового слоя»:
инфраструктура для безопасного переименования (origin-marker + cleanupLegacyArtifact) уже
существует как паттерн в коде — цена ПОДКЛЮЧИТЬ её к скилам мала, если/когда переименование
реально понадобится (сейчас не нужно — факт 1). К пункту 2: путь конфига — часть контракта
«где лежит источник истины локально»; сегодня он ни разу не абстрагирован (факт 7), поэтому
любая правка тут — не смена одной константы, а правка 8+ файлов. Рекомендация: НЕ
`~/.config/petbox` буквально (Unix-конвенция на Windows-машине — как раз то, чего опencode
избегает, факт 11). Взять gh-паттерн: явный `XDG_CONFIG_HOME` — уважать, если задан (не
игнорировать волю юзера/WSL), иначе нативно по платформе, и РАЗДЕЛИТЬ по типу (факт 9):
config (`roles.json`, `projects.json`) → config-dir; secrets (`keys.json`, `e2e.env`) → тот
же config-dir ИЛИ более узкий (не cache — кэш чистят инструментами уборки, для секретов это
опасно); cache (`cache/`) → cache-dir; log/state (`wire.log`, `wire/`) → state/data-dir. Один
общий каталог под любым новым именем воспроизведёт сегодняшний баг просто на новом месте.

## Спорное

Задача просила «дай рекомендацию, а не список» для платформенной логики пункта 2 — даю: XDG
явно только если задан пользователем, иначе платформенно-нативный путь (gh-паттерн), с
разделением по типу данных. Здесь я расхожусь с буквальным пожеланием владельца
(«~/.config/petbox» дословно) — владелец на Windows 11, где `~/.config` не является ничьей
нативной конвенцией (ни одна из проверенных программ, включая сам харнесс этой сессии, туда не
пишет); формулирую это как находку, не как решение за него.

Стык с другими темами (не решаю, только отмечаю): если каскад/оверлей (тема слоёв, `01-legend.md`)
захочет класть ПОЛЬЗОВАТЕЛЬСКИЙ слой (user-scoped, `01-legend.md:38-40`) в тот же каталог, что и
секреты/кэш wire — это тот же вопрос "один каталог vs разделение по типу", решать не мне.

## Чего я не проверил

Не проверял, ссылается ли канон памяти (server-side `memory`) на конкретные имена скилов или
путь `~/.petbox` буквально — сессия работает в режиме "в PetBox ничего не пишем", read
через memory_search не делал, т.к. бриф не называл это обязательным и бюджет ограничен; если
канон хранит literal `~/.petbox/...` в проце — та же цена правки, что и в коде. Не проверял
исходники gh/opencode напрямую (только WebSearch-сводки third-party issue-трекеров, не сам код
go-gh/opencode) — цитаты пункта 11 помечены как из веба, не из этого репозитория.
