# Готовая конфиг-технология каскада: применима ли HOCON или её TS-аналог

Дата: 2026-08-30. Автор: petbox-worker (Sonnet 5). Область: перекрытие HOCON и TS-кандидатов
с четырьмя операциями слоя (ДОБАВИТЬ/ИЗМЕНИТЬ/УБРАТЬ/ЗАМЕСТИТЬ), с упором на УБРАТЬ и
ПРОИСХОЖДЕНИЕ.

## Ответ одной строкой

Не применима как готовый движок: для TypeScript нет зрелого аналога JVM-версии HOCON —
ближайший кандидат, обещающий полный паритет со спекой, статистически похож на hobby-проект.
Писать свои ~50–100 строк поверх JSON, взяв у HOCON и RFC 7396 только идиому «null = УБРАТЬ»,
и добавить трекинг происхождения самостоятельно — этого не даёт из коробки ни один живой
JS/TS-пакет.

## Факты

1. HOCON: слияние дубликатов ключей — объект-к-объекту рекурсивно мержится, объект-к-необъекту
   необъект побеждает без слияния. github.com/lightbend/config/blob/main/HOCON.md,
   раздел «Duplicate keys and object merging».
2. HOCON явно поддерживает УБРАТЬ через null-разрыв: `{foo:{a:42}, foo:null, foo:{b:43}}` ≡
   `{foo:{b:43}}` — null в более приоритетной позиции блокирует слияние с нижним значением; на
   уровне API `Config.hasPath()` для null-пути возвращает false, то есть потребитель видит
   ключ как отсутствующий. Тот же раздел спеки + `com.typesafe.config.ConfigException.Null`
   javadoc.
3. `+=` — синтаксический сахар: `a += b` ⇒ `a = ${?a} [b]` (самоссылающийся append). Спека,
   раздел «The `+=` field separator».
4. `include` подставляет корневые ключи включаемого файла и мержит их по тем же правилам
   дублирующихся ключей, что и внутри одного файла. Спека, раздел «Include semantics: merging».
5. `withFallback` — API для явного связывания слоёв (`config1.withFallback(config2)`);
   определён в Java/Scala-реализации и в .NET-порте (akka.net/HOCON), это и есть опыт
   владельца с C#. Тот же репозиторий + getakka.net/articles/configuration/hocon.html.
6. `origin()`/`ConfigOrigin` (файл+строка, откуда взято значение) — это и есть готовая
   ПРОИСХОЖДЕНИЕ из коробки, но существует только в JVM-библиотеке
   (`com.typesafe.config.ConfigValue#origin()`). Ни в одном проверенном JS/TS-пакете
   аналог не документирован.
7. `@o3co/ts.hocon` (npm v1.13.0, публикация 2026-08-18) заявляет «Full Lightbend HOCON
   spec-compliant… for TypeScript», включая `withFallback`. Но: 1 звезда на GitHub, 1224
   скачивания/мес на npm — статистически сольный/ранний проект; provenance-API в README не
   упомянут. npm view + WebFetch github.com/o3co/ts.hocon.
8. `@pushcorn/hocon-parser`: v1.3.1, последняя публикация 2024-06-20, 14.8k скачиваний/мес —
   только парсер, `withFallback`/слоистость не документированы. npm view.
9. `hocon-parser` (оригинал): v1.0.1, публикация 2022-06-18, «very basic», без обновлений 4
   года — не кандидат.
10. `c12` (unjs): v4.0.0-beta.5, публикация 2026-05-06, 92.8M скачиваний/мес. После
    `loadConfig()` доступен массив `layers` (config + configFile на слой) — происхождение
    ПО КЛЮЧУ не даётся готовым, но восстановимо вручную, перебором слоёв поверх уже
    смерженного результата. unjs.io/c12 (WebFetch).
11. `defu` (движок слияния c12 по умолчанию): nullish-значения при слиянии ПРОПУСКАЮТСЯ —
    то есть `null` в верхнем слое НЕ перекрывает и не убирает значение нижнего слоя.
    Встроенной операции УБРАТЬ нет. github.com/unjs/defu (issues/docs, WebSearch).
12. JSON Merge Patch (RFC 7396): null в патче УДАЛЯЕТ ключ из базы — это прямое и стандартное
    попадание в операцию УБРАТЬ. Ограничение спеки: «impossible to use merge patch to set a
    key's value to null» — удалить можно, а вот явно ХРАНИТЬ null как значение — нельзя.
13. `json-merge-patch` (npm): v1.0.2, публикация 2022-06-19 — не поддерживается, но сам RFC
    крошечный и стабильный, тривиально реализуем заново (~15-20 строк).
14. JSON Patch (RFC 6902) имеет явный `remove` и `test`, но это скрипт операций над ОДНИМ
    документом, а не модель «слой B — fallback слоя A»; для каскада слоёв естественно не
    подходит, годится скорее для diff/review-представления уже готового результата.
15. `tsconfig.extends`: compilerOptions мержится (дочерний побеждает при конфликте
    ключа), но `include`/`exclude`/`files` и массивы типа `lib` — ЗАМЕЩАЮТСЯ целиком, не
    мержатся; частичного УБРАТЬ-из-массива нет и запрошено как feature request (issues
    #20110, #57486, WebSearch).
16. ESLint flat config: массив объектов-конфигов, «кто позже — тот и главный» на уровне
    отдельных правил; `extends` разворачивается в этот же массив. Явной операции
    УБРАТЬ-правило нет (только `rule: 'off'`), происхождение пользователю не показывается
    по умолчанию. eslint.org/blog/2025/03/flat-config-extends… (WebSearch).
17. VS Code settings: фиксированная иерархия User→Workspace→(Folder), простое
    last-write-wins по ключу; «убрать» = вручную удалить ключ из JSON, кросс-слойного
    null-механизма не документировано. code.visualstudio.com/docs/configure/settings.
18. opencode: собственный самописный мерж (не сторонний движок), цепочка remote→global→
    env→project→project-dir→runtime, массивы конкатенируются между слоями, «later configs
    only override conflicting fields» — ни delete, ни provenance не описаны.
    opencode.ai/v2/docs/config (WebSearch).
19. `cosmiconfig`: v10.0.0, ~500M скачиваний/мес — это ФАЙЛОВЫЙ ЛОКАТОР (ищет `.foorc`,
    `foo.config.js`, `package.json#foo`), а не движок слияния нескольких найденных
    конфигов; сам не мержит и не даёт происхождение по полю, только «какой один файл
    выбран».
20. `convict`: v6.2.5, 4.7M скачиваний/мес — схема+валидация+приоритет env/argv;
    `loadFile()` мержит несколько JSON-файлов, но это плоское/глубокое перезаписывание без
    задокументированного УБРАТЬ или provenance-по-ключу. npm-compare.com,
    mozilla/node-convict (WebSearch).
21. `rc`: v1.2.8, публикация 2025-02-21, 178M скачиваний/мес — каскад env/argv/rc-файлов для
    CLI, простой deep-merge без УБРАТЬ и без provenance.

## Что из этого следует для гипотезы «источник истины — файлы»

Вопрос ортогонален источнику истины напрямую, но затрагивает соседний слой: если файлы в гите
— источник, а сервер — кэш, то показать «какой файл дал это поле» (ПРОИСХОЖДЕНИЕ) — это ровно
то представление, которое делает кэш проверяемым при расхождении с источником. Ни один
проверенный живой TS-пакет эту витрину не даёт бесплатно: `c12.layers` ближе всего, но требует
собственной пере-развёртки. Значит происхождение придётся считать своим кодом независимо от
выбора формата хранения — довод в пользу «писать свой мерж» усиливается, а не ослабляется
выбором формата.

## Спорное

Формулировка владельца: «движок hocon (по крайней мере для C#) закрыл все вопросы из коробки».
Для .NET/JVM это подтверждается (`withFallback` + `origin()` — оба есть, факты 5 и 6). Для
TypeScript я нахожу, что аналогичного зрелого движка НЕТ: единственный кандидат, заявляющий
полный паритет со спекой (`@o3co/ts.hocon`, факт 7), статистически выглядит как сольный/ранний
проект (1 звезда, 1224 dl/мес) — ставить на него ядро `petbox-wire` рискованно именно потому,
что весь смысл «взять готовое» — снять риск поддержки, а этот пакет такой риск не снимает.

## Чего я не проверил

- Пакеты не устанавливались и не запускались функционально — только `npm view`/README/спека
  через WebFetch и WebSearch; поведение принято на веру у авторов, не подтверждено кодом.
  ПРЕДПОЛОЖЕНИЕ: пакеты ведут себя так, как документируют.
- Не проверял C#/.NET-порт (akka.net HOCON) напрямую — вывод о его полноте (факт 5) сделан по
  вторичным источникам, не по факту использования владельцем.
- Не искал prior art внутри самого репозитория petbox (например, уже написанный где-то ручной
  deep-merge с УБРАТЬ) — вне области задачи, но релевантно для «сколько стоит написать своё».
- Не смотрел `nconf`, `deepmerge`/`lodash.merge` с customizer, `ajv`-based config-merge
  библиотеки — за пределами явно перечисленного в поручении списка.
