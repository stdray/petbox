# Настоящий рычаг против промахов по простою: CacheWarmer (и почему он здесь мёртв)

У pi есть механизм именно под эту боль: `pi-coding-agent/dist/core/cache-warmer.js` —
перед истечением TTL кеша он повторяет запрос с `maxTokens: 1`, чтобы запись осталась живой.
`/session` показывает его состояние строкой «Cache warming: …».

На `opencode-go/deepseek-v4.1-flash` он не работает, и это три независимых замка.

## Замок 1: у модели нет TTL кеша

`getPromptCacheTtlMs` читает `model.promptCache[retention]` (секунды). В каталоге:

| провайдер | моделей | с `promptCache` |
|---|---|---|
| opencode-go | 30 | **0** |
| opencode | 81 | 0 |
| deepseek | 2 | 0 |
| anthropic | 17 | 17 |

Без TTL прогрев останавливается первым же `return` с причиной «cache lifetime unavailable»
(`cache-warmer.js:121-131`). Это та же причина, по которой не работал прогрев у Bedrock
(upstream #11528, закрыт).

## Замок 2: включён только «стриминговый» режим

`settings-defaults.js:60` — `cacheWarming: "streaming"`. В этом режиме прогрев живёт только
внутри хода агента, а на `onAgentSettled` останавливается («agent run settled»). Простой
между ходами согревает только режим `"idle"`, и он не по умолчанию (описание настройки:
«Global only because each refresh costs money»).

## Замок 3: экономика запрещает греть

Даже если объявить TTL в `~/.pi/agent/models.json` (композер моделей мержит
`override.promptCache`, `provider-composer.js:73`), решение принимает `evaluate()` с двумя
константами: `CACHE_WARMING_MINIMUM_EXPECTED_SAVINGS = 0.05` и
`IDLE_CONTINUATION_PROBABILITY = 0.15` (вероятность, что реальный запрос придёт до истечения).

Арифметика для нашей сессии — префикс 355 000 токенов, `input 0.15/M`, `cacheRead 0.003/M`,
`cacheWrite 0`:

| величина | значение |
|---|---|
| `cacheHitCost` | 355 000 × 0.003 / 1e6 = **$0.00107** |
| `cacheMissCost` | 355 000 × 0.15 / 1e6 = **$0.0533** |
| `warmCost` (cacheRead + 1 токен вывода) | ≈ **$0.00107** |
| `missCost` | $0.0522 |
| `expectedSavings` | 0.15 × 0.0522 − 0.00107 = **$0.0068** |
| порог | $0.05 → **stop** |

Чтобы прогрев включился, `missCost` должен быть ≳ $0.34, то есть префикс ≳ 2.3 млн токенов —
больше контекстного окна модели (1 млн). **На этой модели idle-прогрев не включится никогда, и
это не баг, а посчитанное решение:** вход дешёвый, а простой ничего не гарантирует.

## Что из этого следует

- Промахи после простоя ≥6 мин на дешёвых по входу моделях **структурны**. Лечится не
  настройкой клиента, а (а) удержанием префикса на стороне шлюза/апстрима и (б) не оставлять
  сессию в простое, если в ней большой контекст.
- Проверить состояние на своей машине: `/session` → строка `Cache warming:`; для этих моделей
  там будет `Inactive (cache lifetime unavailable)`.
- `cacheWarming: "idle"` + `promptCache` в models.json включат механизм, но `evaluate()` всё
  равно скажет `stop` — увидите это в той же строке как «expected savings $0.007 < $0.050».
