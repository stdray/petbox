# Сколько живёт кеш и где он на самом деле теряется

## Чужие числа — не мои

В расчётах из `03-cache-warming.md` я брал цены **из каталога pi для
`opencode-go/deepseek-v4.1-flash`**: input `0.15/M`, output `0.60/M`, cacheRead `0.003/M`,
cacheWrite `0`. Это то, чем pi СЧИТАЕТ стоимость; это не счёт от провайдера (у `opencode-go`
подписка, а не оплата по токенам).

В том же каталоге у провайдера `deepseek` те же токены стоят вдвое дороже: input `0.30/M`,
cacheRead `0.006/M` (`models-store.json`, провайдер `deepseek`, модель `deepseek-flash`).

**Проверка на чувствительность.** Условие прогрева — `0.15 × missCost − warmCost ≥ $0.05`.

| цена входа | `missCost` при префиксе 355k | `expectedSavings` (idle) | решение |
|---|---|---|---|
| 0.15/M (каталог go) | $0.052 | $0.0068 | stop |
| 0.30/M (каталог deepseek) | $0.104 | $0.0122 | stop |

Порог срабатывания: префикс ≳2.3 млн токенов при 0.15/M и ≳1.15 млн при 0.30/M — в обоих
случаях больше окна модели (1 млн). Вывод «прогрев не включится» от выбора ценового набора
не зависит.

## Что говорит сам DeepSeek

Дословно с https://api-docs.deepseek.com/guides/kv_cache/ :

> Cache construction takes seconds. Once the cache is no longer in use, it will be
> automatically cleared, usually within a few hours to a few days.

> The cache system works on a "best-effort" basis and does not guarantee a 100% cache hit rate.

Плюс правила попадания: запрос попадает в кеш только если **полностью совпадает** с
сохранённым префикс-юнитом; юниты создаются на границе ввода/вывода, на общем префиксе
нескольких запросов и на фиксированных интервалах токенов.

Итого: **десять минут простоя кеш не убивают.** Убивают часы, а на минутной шкале — не время,
а несовпадение префикса и маршрутизация.

## Что показывают наши собственные данные

Доля запросов с попаданием в кеш по длительности паузы перед запросом:

| пауза | pi (303 ответа) | opencode (196 ответов) |
|---|---|---|
| <1 мин | 304/305 — **100 %** | 1207/1260 — 96 % |
| 1–5 мин | 14/16 — 88 % | 153/175 — 87 % |
| 5–10 мин | 3/5 — 60 % | 6/16 — **38 %** |
| 10–20 мин | 1/3 — 33 % | 5/10 — 50 % |
| 20–60 мин | 3/4 — 75 % | 1/3 — 33 % |
| >1 ч | 0/3 — **0 %** | 0/1 — 0 % |

Читать это надо так:

- пауза 10 минут — **не приговор**, попадание примерно как подброс монеты; в выборке есть и
  паузы 25 минут с попаданием;
- часы — приговор: все прогоны с паузой >1 ч промахнулись;
- промахи на короткой паузе (5–20 мин) объясняются не временем: либо запрос обслужил другой
  апстрим (в разобранной сессии видно по семейству `responseId`), либо префикс не совпал
  полностью (сменился системный промпт/набор инструментов).

## Поправка к прежней формулировке

Раньше здесь стояло «пять промахов — префикс вытеснен на апстриме». Это слишком сильное
утверждение: по логу нельзя отличить вытеснение от смены апстрима, а по документации
вытеснение измеряется часами-днями, не минутами. Точная формулировка: **при паузе в минуты
промах вероятен, но не автоматичен; при паузе в часы — практически неизбежен.**
