# Метод: три проверки и их границы

Все три проверки — клиентские. Серверная часть шлюза (`opencode.ai/inference/go`) не
проверялась: из клиента не видно, какие заголовки шлюз читает для sticky-роутинга.

## 1. Юнит: реальное определение провайдера

```powershell
$env:PI_PKG = "$env:APPDATA\npm\node_modules\@earendil-works\pi-ai"   # каталог pi-ai с dist/
node scripts/header-probe.mjs                                       # все четыре адаптера
node scripts/header-probe.mjs <sessionId>                            # + сравнение «с id / без id / id уже стоит»
```

Скрипт берёт `opencodeGoProvider()` из `pi-ai/dist/providers/opencode-go.js` — то же
определение, что использует сам pi, — и подменяет `fetch`, собирая исходящие заголовки.
Ответ шлюза не нужен: `fetch` бросает после записи заголовков.

## 2. e2e: pi против фейкового шлюза

```powershell
# терминал 1
node scripts/fake-gateway.mjs            # 127.0.0.1:8792, логирует заголовки, 1-й ответ = tool-call

# терминал 2
pwsh -File scripts/run-e2e.ps1
```

`run-e2e.ps1` создаёт временный `PI_CODING_AGENT_DIR` c `models.json`, где у провайдера
`opencode-go` подменён `baseUrl` на `http://127.0.0.1:8792/v1`, и запускает настоящий
`pi` в print-режиме. Подмена `baseUrl` у **встроенного** провайдера сохраняет его
обёртку заголовков — на этом проверка и держится.

Первый ответ шлюза — `tool_calls` (`ls`), поэтому pi делает второй запрос в той же сессии:
видно, что заголовок не одноразовый.

Флаг `compat.sendSessionAffinityHeaders` проверяется тем же стендом: добавьте его в
модель в `models.json` (см. `run-e2e.ps1`, параметр `-Affinity`).

## 3. Статистика промахов

```powershell
python scripts/pi-session-misses.py "$env:USERPROFILE\.pi\agent\sessions\<dir>\<session>.jsonl"
python scripts/opencode-session-misses.py "$env:LOCALAPPDATA\..\.local\share\opencode\opencode.db"
```

Промах = ответ ассистента с `cacheRead == 0` при `input > 20000`. Рядом печатается простой
между ходами и семейство `responseId` — именно оно отделяет «префикс вытеснен по времени»
от «запрос ушёл на другой апстрим». Скрипт для opencode читает `opencode.db` в режиме
`ro` (WAL не трогается).

## Границы

- **Выборка.** Одна длинная сессия pi (303 ответа) и 196 ответов opencode в 9 сессиях.
  Достаточно, чтобы снять гипотезу «pi не шлёт заголовок»; недостаточно для «pi всегда
  лучше/хуже».
- **`google-generative-ai` адаптер** в юните не поймал заголовков вовсе: перехват `fetch`
  у Google SDK устроен иначе. Это дефект метода, а не вывод об отсутствии заголовка.
- **Порог 20k input** отсекает мелкие ходы, где промах почти ничего не стоит; он выбран,
  чтобы в отчёт не попадали ответы на короткие реплики.
- **`gw-…` в `responseId`** — идентификатор шлюза, не документирован; вывод «другой
  апстрим» опирается на смену СЕМЕЙСТВА идентификатора, а не на разбор его полей.
