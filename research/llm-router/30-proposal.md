# 30 — Предложение: автомат, шлюз, автономный хост

Опирается на 20-consolidated.md. Ссылки на PetBox-факты те же F-id; новые решения помечены **(нов.)**.

## 1. Модель автомата

Три РАЗНЫХ уровня состояния — их нельзя схлопывать в один, это и есть корень нынешней
недосказанности (20-consolidated §Q1):

**A. Endpoint/ключ-провайдер** (уже есть, `EndpointBreaker`, F3): `Closed → Open(cooldown) →
HalfOpen(probe) → Closed|Open`. **(нов.)** Разделить длительность cooldown по ПРИЧИНЕ, не держать
единую 30с на всё: `transient` (429/5xx/timeout) → короткий cooldown как сейчас; `quota_exhausted`
(см. §4) → длинный/до explicit reset. Аналог — LiteLLM's `allowed_fails`/`cooldown_time` per-
deployment override (подтверждено чтением docs.litellm.ai/docs/routing — Condition→Duration
таблица: 429/high-failure-rate/non-retryable различаются УЖЕ у них).

**B. Маршрут (цепь)** — НЕ отдельное персистентное состояние, а ПРОЕКЦИЯ над состояниями своих
endpoint'ов + порядком приоритета: `Primary` (первый leg closed и отвечает) / `Degraded` (обслуживает
leg N>1) / `Exhausted` (все legs open/провалились в этой попытке). Считать на чтении, не писать
отдельно — это прямое применение решения владельца из прошлого рисерча (m-516ab8b4...: «грань
агрегации выбираешь на чтении, перепартиционирование = переписать вьюху»). Второй источник правды
здесь был бы регрессией к тому же классу бага, что уже дважды укусил (route-registry flip, F10-code).

**C. Попытка (per-attempt) — это то, чего в коде НЕТ и что реально нужно (нов.):**

```
Idle → Sent
Sent → ConnectFailed                                  [pre-completion, transient, breaker++]
Sent → TimedOutTTFT                                    [pre-completion, transient, breaker++,
                                                          ПОСЛЕДНЕЕ безопасное окно для reselect]
Sent → Http429{retryAfter?}                            [pre-completion, transient, breaker++,
                                                          cooldown = max(retryAfter, default)]
Sent → Http5xx                                          [pre-completion, transient, breaker++]
Sent → Http4xxClient (400/403/404, не 429)              [pre-completion, non-transient,
                                                          НЕ breaker++ (текущее поведение,
                                                          решение 2026-08-28) — цепь идёт дальше]
Sent → Http401Auth                                      [pre-completion, non-transient, НО:
                                                          breaker++ отдельно от общего non-transient —
                                                          память 2026-07-28 явно требует «401/404 →
                                                          не ретраить, но в cooldown»; ТЕКУЩИЙ код
                                                          этого не делает нигде — расхождение с
                                                          собственным решением владельца, нужно
                                                          подтвердить как правку]
Sent → QuotaExhausted (провайдер-специфичный маркер)    [pre-completion, breaker → LONG cooldown]
Sent → FirstByteReceived → Streaming
Streaming → Completed                                   [терминал, breaker.RecordSuccess]
Streaming → StreamBroken                                [post-completion — HTTP 200 уже ушёл клиенту,
                                                          НЕЛЬЗЯ тихо ретраить (ac-72d581037785,
                                                          «шва нет», кусало дважды); терминал этой
                                                          попытки как PartialFailure, видимый
                                                          вызывающему и логу, НЕ следующему legу
                                                          прозрачно]
```

Сейчас код НЕ различает `TimedOutTTFT` от `StreamBroken` потому что **стриминга нет вообще**
(REST `stream:true` → 400, LlmRouterApi.cs:16,131-132) — вся таксономия «до/после первого байта»
сегодня выродилась в один случай (вызов либо целиком успешен, либо целиком нет). Это не повод
не проектировать разницу — это ровно то место, где её дешевле всего заложить ДО, а не после
появления стриминга (владелец уже дважды получил один и тот же баг постфактум).

**Декларативно (конфиг владельца) vs авто-вывод:**
- Декларативно: список маршрутов + приоритет/tier (как сейчас, F4-code); per-endpoint override
  `allowedFails`/`cooldownTime`; правила детекции `QuotaExhausted` (провайдер-специфичны — единого
  кода/тела ответа нет, у BlockInsight'ов это будет что-то вроде 402 или текстового маркера, у
  других — 429 с конкретным `error.type`); правила переписывания заголовков (§5).
- Авто-вывод: таймеры open/half-open в рамках объявленных границ; проекция B (Primary/Degraded/
  Exhausted); телеметрия попыток — писать ШИРОКО (per-attempt строка, DuckDB уже есть в проекте
  per m-516ab8b4...), агрегацию выбирать на чтении.

**Чем автомат лучше `fallbacks: [...]` LiteLLM — честно, включая минусы:**

Лучше:
- Разделяет pre-completion (можно молча переключить) от post-completion (обязано быть видно) —
  плоский список фолбэков LiteLLM такого различия не делает вообще (retry/fallback — единый цикл
  вокруг `router.completion()`, никакой связи со стримингом на этом уровне).
- Политика как данные (по образцу методологии PetBox, а не как в LiteLLM, где типы фолбэков —
  3 хардкод-класса: `fallbacks`/`content_policy_fallbacks`/`context_window_fallbacks`): новый
  символ алфавита (скажем, «content-policy → терминально, не ретраить с другим фильтром») —
  это новая строка, а не правка `RunChainAsync`.
- Инвариант классов эквивалентности (`EmbedSpaceId`) — то, чего у LiteLLM/OpenRouter/Portkey нет
  вообще (m-516ab8b4...), а без него смена provider'a в векторной цепочке молча ломает
  сравнимость эмбеддингов. Автомат даёт естественное место повесить guard на переход.
- Admission control через существующий `/slots?fail_on_no_slot=1` у llama-server (m-
  571221702ea342c8be0b793bed13400f) — вписывается как guard ПЕРЕД `Sent`, без отдельной очереди
  приоритетов (владелец это уже отверг как решение для соседней идеи).

Хуже, честно:
- Дороже в разработке, чем YAML-список: `fallbacks: [a,b,c]` читает и правит non-engineer за
  минуту; policy-as-data с именованными состояниями/переходами требует хоть небольшой admin-UI
  или JSON-редактор — бюджет, который команда уже сознательно отклонила один раз («Что НЕ тащить»,
  m-3370e52b...).
- Однопроцессный in-memory `EndpointBreaker` не масштабируется на несколько процессов/подов —
  LiteLLM даёт это через Redis «из коробки» уже сегодня. Для нынешнего single-instance деплоя
  PetBox не проблема, но автономный шлюз, если когда-то станет многопроцессным, унаследует дыру.
- Больше состояний = больше непротестированной поверхности: 10-facts F10 уже фиксирует отсутствие
  тестов на сам обход цепи и брейкер — расширение автомата без роста тестового бюджета ухудшает,
  а не улучшает ситуацию.

## 2. Протоколы: сквозной режим vs трансляция

**Сквозной (pass-through, дёшево):** вход и выход — один и тот же протокол; шлюз трогает только
маршрут/ключ/заголовки, не тело. Не нужно понимать tool-calls, роли сообщений, SSE-форму чанков —
только `model`-поле (для маршрутизации) и, при стриминге, факт «первый байт пришёл» (для FSM
попытки, не для трансляции содержимого). Это почти буквально то, что `CapabilityRouter` уже делает
для OpenAI-chat-completions сегодня (F5/F6-code).

**Трансляция (дорого):** Anthropic Messages ↔ OpenAI chat ↔ OpenAI Responses. Нужно переразложить
тело целиком: место системного промпта, маппинг ролей, схему tool/function calls, ПЕРЕВОД
стриминговых событий (у Anthropic — `content_block_delta`, у OpenAI chat — `chat.completion.chunk`,
у Responses — `response.output_text.delta`; формы материально разные), маппинг stop-reason,
разное устройство usage/токенов. Именно тут CLIProxyAPI/LiteLLM/claude-code-router несут основную
массу кода.

**Новый факт, важный для порядка (нов., сверено 2026-09-25 против developers.openai.com/codex/
config-reference):** `model_providers.<id>.wire_api` у codex документирован как принимающий
**только** `responses` — кастомный провайдер обязан говорить Responses API, не chat/completions.
Это меняет рекомендацию: «просто отдать наш OpenAI-chat-совместимый REST» codex не устроит без
трансляции chat↔responses НА ШЛЮЗЕ (или без того, чтобы шлюз сам говорил Responses с апстримом,
что почти никто из провайдеров не поддерживает нативно).

**Рекомендация — порядок:**
1. OpenAI chat ↔ OpenAI chat, сквозной. Уже на 90% есть (`CapabilityRouter`), закрывает
   opencode/большинство клиентов сразу.
2. OpenAI Responses ↔ OpenAI Responses, сквозной. Нужен ИМЕННО для codex (см. выше) — без него
   Q2 не решается даже с виртуальными моделями, потому что codex не пошлёт chat-запрос кастомному
   провайдеру вообще.
3. Anthropic Messages ↔ Anthropic Messages, сквозной — для API-ключевых Anthropic-провайдеров
   (подписки, как sabotaged owner note подчёркивает, вне схемы; но не все Anthropic-совместимые
   бэкенды — подписки).
4. Любая ТРАНСЛЯЦИЯ (chat↔responses↔messages) — последним пунктом, по факту спроса
   (например, opencode-go шлёт Anthropic Messages, а нужный провайдер только chat), не
   заранее для всех 3×3 комбинаций.

## 3. Маршрутизация по имени модели: codex config.toml

Сегодня REST-эндпоинт уже мапит `model`→`Tier` (F6-code) — тот же примитив, что нужен для
codex-субагентов. Конкретно:

```toml
# ~/.codex/config.toml — один base_url, виртуальные "модели" резолвит шлюз
[model_providers.petbox-gw]
name = "PetBox LLM gateway (local)"
base_url = "http://127.0.0.1:8787/v1"
wire_api = "responses"          # см. §2 — codex не примет "chat" тут
env_key = "PETBOX_GW_KEY"

model_provider = "petbox-gw"
model = "route:chat-default"

[agents.reviewer]
description = "код-ревью — сильная/платная модель"
config_file = "roles/reviewer.config.toml"

[agents.scaffolder]
description = "болванки/скаффолдинг — бесплатная/дешёвая модель"
config_file = "roles/scaffolder.config.toml"
```

`roles/reviewer.config.toml`: `model = "route:chat-strong"` (шлюз резолвит на deepseek-v4-pro
цепь). `roles/scaffolder.config.toml`: `model = "route:chat-free"` (шлюз резолвит на openrouter
`:free` цепь с автоотвалом, §4). Это `agents.<name>.config_file` — **статический** механизм
(объявляется один раз на роль), НЕ решает «оркестратор выбирает провайдера динамически при
каждом spawn» — это по-прежнему упирается в подтверждённый баг `spawn_agent` (F5-history,
recurrence 2, апстрим не пришёл). Но закрывает более узкую и, вероятно, достаточную задачу
владельца: «роль X всегда на дешёвом, роль Y всегда на дорогом» без правки codex.

## 4. Бесплатные модели с автоотвалом

`QuotaExhausted` — отдельный символ алфавита (§1), НЕ = обычный 429. Детектируется правилом
per-provider (декларативно, т.к. единого признака нет: 402, специфичный `error.type`, текст
тела) → переводит endpoint в LONG-cooldown/Excluded вместо стандартных 30с. Ручной или
плановый (cron внутри шлюза) пробный запрос сбрасывает раньше срока, когда провайдер объявляет
возобновление (см. паттерн BlockInsight — ежемесячные окна, F1/F2-external). Аналог по форме —
per-model `allowed_fails`/`cooldown_time` override у LiteLLM (подтверждено чтением доков), но
триггер здесь другой (квота, не отказ).

## 5. Переписывание заголовков

Новый слой (Q7 подтверждённо пуст сегодня). Декларативно на маршрут/провайдера:
`stripIncoming` (убрать клиентские `Authorization`/кастомные), `setUpstreamAuth` (подставить
из зашифрованной колонки ключа — как уже делает `CapabilityRouter` внутри HTTP-клиента,
F4-code, только сейчас это не настраиваемо, а вшито), `addStatic` (статичные заголовки на
апстрим), `passThrough` (белый список того, что течёт как есть). Форма аналогична Message
Transforms LiteLLM / rewrites CCR / routing rules Portkey (все три подтверждены иметь это,
12-facts F3/F6/F7).

```
  — новый scope ApiKey (напр. gateway:proxy, отдельно от llm:invoke), конфиг в

Хост Б — автономный (dotnet tool / служба)
  — Windows Service (Microsoft.Extensions.Hosting.WindowsServices) / systemd,
    конфиг из локального TOML/JSON (форма как у самого codex — узнаваемо),
    БЕЗ core.db, БЕЗ мульти-тенанта — один владелец, одна машина.
```

## 7. Секреты

- **PetBox-хост:** как сегодня — зашифрованная колонка на `llm_endpoints` (F4-code), ничего не
  меняется.
- **Автономный хост:** локальный конфиг-файл. Рекомендация — скопировать паттерн codex дословно:
  `env_key = "DEEPSEEK_API_KEY"` (косвенно, через переменную окружения), НЕ ключ литералом в
  файле. Никакой синхронизации секретов между хостами — автономный шлюз намеренно не связан с
  зашифрованным реестром PetBox (это и есть смысл «полностью автономно, без PetBox»).

## 9. Этапы и развилки владельца

**Порядок (каждый этап самостоятельно ценен, не блокирует следующий целиком):**
1. Таксономия отказа как алфавит + `Retry-After`-парсинг + разделение 401/404 cooldown от
   общего non-transient — чинит §1 БЕЗ нового хоста, работает уже в текущем `CapabilityRouter`.
   Дешёвый, отвязан от остального.
2. `Gateway.Core` (FSM+pass-through+заголовки) как отдельная сборка, ещё без нового хоста —
   доказывается юнит-тестами на попытке, без сети.
3. OpenAI Responses pass-through — разблокирует Q2 для codex конкретно.
4. PetBox-хост шлюза (новый scope ключа, admin UI на существующей странице) — доказывается
   живым смоуком с одной машины.
5. Автономный хост (dotnet tool/служба) — только после того, как `Gateway.Core` подтверждён
   работающим внутри PetBox-хоста; иначе рискуем чинить баги в двух местах параллельно.

**Открытые развилки:**

- **401/404 → cooldown, а не просто non-transient-passthrough.** Решение владельца 2026-08-28
  явно сказало «не абортить цепь на non-transient» — но память того же дня рисерча (2026-07-28)
  отдельно требует cooldown именно для 401/404. Это противоречие МЕЖДУ ДВУМЯ прошлыми решениями
  владельца, не между фактами. Цена решить сейчас: 0 (просто явно выбрать одно). Цена не решить:
  следующий разработчик автомата угадывает и, скорее всего, угадывает неправильно — уже дважды
  так было с этим модулем.
- **Merge CapabilityRouter в Gateway или держать раздельно (§6).** Рекомендация — раздельно.
