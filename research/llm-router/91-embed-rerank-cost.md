# 91 — Сколько стоит embed/rerank, и что если убрать домашнюю машину

Отвечает на вопрос владельца «можно прикинуть трату на embedding/rerank? может избавиться от
домашней машины и модуля?». Метод переездов — как в 80 §3 (`log_query` по `events | where
MessageTemplate startswith "llm {Capability} served"`, поле `Model` различает cloud-плечи внутри
одного `Endpoint=openrouter`). Цены — `openrouter.ai/api/v1/models` и модельные страницы,
живьём, 2026-09-25 (прямой `curl` прошёл без прокси). Секреты нигде не читались и не выводились.

## 1. Объём

Лог `petbox` хранит ровно 30 дней (2026-08-26…2026-09-25) — «30 дней» ниже это весь лог.

| cap | окно | home | cloud(openrouter) | cloud % |
|---|---|---|---|---|
| Embed | 7д | 1860 | 495 | 21.0% |
| Embed | 30д | 13976 | 833 | 5.6% |
| Rerank | 7д | 842 | 311 | 27.0% |
| Rerank | 30д | 5183 | 480 | 8.5% |
| Chat | 7д/30д | 893 / 5014 | 2 / 18 | ~0.3% (вне темы) |

7-дневная доля выше 30-дневной в разы — не тренд, а пик: 22 сентября домашний узел явно лежал
(Embed cloud 401/день, Rerank cloud 271/день при среднем ~15-30/день), 25-е почти весь трафик снова
дома. День-в-день: 6–4329 событий/день за 30 дней (`bin(Timestamp,1d)`), т.е. волатильность на
порядок — усреднять за один короткий период опасно, использую оба окна.

Rerank cloud дробится по `Model`: **443 из 480 (92%) — бесплатный** `nvidia/llama-nemotron-rerank-vl-1b-v2:free`
(приоритет 20), только **37 (8%)** проваливаются до платного `cohere/rerank-4-fast` (приоритет 30).

**Кто генерирует — лог не говорит.** `ServiceKey` всегда `petbox-web` (монолит), `SourceContext`
всегда `CapabilityRouter` — событие не несёт caller (Memory/Sessions/Tasks/MCP-агент). По коду
(оценка, не из лога): `MemoryVectorizationJob`/`TasksVectorizationJob` — фоновые джобы, тик 60с,
бюджет `MaxDocsPerPass=200` документов/тик, **один HTTP embed-вызов на один документ**
(`VectorSearchIndex.cs:57`, `[doc.EmbedInput]`) — это, скорее всего, основной источник объёма embed
(1935 записей памяти в `$system` уже наблюдаемы, см. §5). Interactive-путь — `SearchService.cs:219`
(rerank при живом поиске) и одиночный embed запроса (`VectorSearchIndex.cs:105`) — на порядок реже
фоновой индексации, но с латентностью, которая бьёт по UX (§5).

## 3. Расчёт

Токены на embed-вызов лог не пишет (`usage` выбрасывается — 80 §1, факт подтверждён живым
event-дампом: поля `Attempt/Model/Capability/Endpoint`, `Usage` нет). **(оценка)** по
`memory_store_list(includeUsage)` на `$system`: `rowChars/totalEntries` по хранилищам —
874–2377 симв./запись → беру ~1500 симв./документ, ~400–700 ток./вызов при смешанном RU/EN тексте
(qwen-токенизатор, ~2–3.5 симв./ток).

| Сценарий | Embed | Rerank | Итого/мес |
|---|---|---|---|
| **Сейчас** (30д факт) | 833 cloud-вызовов × 500 ток ≈ 0.42M ток → **$0.008** | 37 платных × $0.002 = **$0.07** (443 бесплатных = $0) | **≈$0.08/мес** |
| **Сейчас** (7д факт, ×4.3) | 2128 cloud-вызовов ≈ 1.06M ток → **$0.021** | ~13 платных/нед×4.3×$0.002 ≈ **$0.11** | **≈$0.13/мес** |
| **100% облако**, тот же приоритет (free rerank first) | 10–15k вызовов/мес × 500 ток ≈ 5–7.5M ток → **$0.10–0.15** | 92% free + 8% cohere на ВЕСЬ трафик ≈ 400–450 платных/мес × $0.002 → **$0.8–0.9** | **≈$0.9–1.1/мес** |
| **100% облако**, free-tier rerank недоступен (худший случай) | то же — **$0.10–0.15** | весь rerank-трафик на `cohere/rerank-4-fast`: 5–5.7k/мес × $0.002 → **$10–11** | **≈$10–11/мес** |
| **Без модуля** (см. §4) | облачная часть та же, что «100% облако» | то же | **≈$1–11/мес** + инженерная цена §4, минус экономия на электричестве |

Домашняя машина, формула (владелец подставляет свои Вт/тариф — не выдумываю):
`стоимость_месяц = Вт × часы_работы_в_месяц ÷ 1000 × тариф_за_кВт·ч`. Пример на плейсхолдерах:
300 Вт idle-инференс, 24×30=720 ч, тариф 5₽/кВт·ч → 300×720/1000×5 = **1080₽/мес** — подставь свои
цифры, это НЕ измерение.

**Вывод по деньгам:** переезд embed/rerank на 100% облако — не тема для оптимизации бюджета: разброс
$1–11/мес целиком зависит от того, останется ли бесплатный rerank-тир у nvidia, а не от объёма
PetBox. Экономия на электричестве домашней машины (реальные Вт/тариф владельца) почти наверняка
перекрывает и худший случай на порядок.

## 4. Что станет с модулем без домашней машины

По классификации 63 §Часть1, для сценария «1 облачная embed-модель + 1 облачная rerank-модель,
без `home`»:

- **`CertPinningHttpClientProvider`** (57 строк) — мёртвый код: cert pinning был только для
  `home`-эндпоинта (самоподписанный сертификат домашнего узла), у облачных провайдеров TLS обычный.
- **`EndpointBreaker`** (46 строк) теряет причину существования: он написан ровно для «не ждать
  3-секундный connect-timeout спящего домашнего ПК на каждый вызов» (79% сегодняшних переездов —
  breaker-open, 80 §1). Без домашнего узла breaker вырождается в fallback между двумя облачными
  моделями, где 429/5xx прилетает быстро — можно оставить как есть (код тестирован) или упростить
  до retry-on-error без open/half-open state machine.
- **`EmbedSpaceId`** — при ровно одной embed-модели пространство эмбеддингов гарантировано
  структурно (нет второго плеча, которое могло бы разъехаться), а не рантайм-проверкой: поле
  вырождается в константу, но саму концепцию всё равно нельзя выкинуть — стоит добавить вторую
  cloud-модель (напр. deepseek-embed) когда-нибудь, инвариант снова понадобится.
- **`RerankQueryAsync`-инвариант** (одна модель на все чанки запроса) остаётся нужен независимо от
  числа плеч — это про совместимость чанков ОДНОГО запроса, не про home/cloud.
- **OpenRouter provider-fallback НЕ покрывает это без второй модели.** Проверено (`/models/{id}/endpoints`):
  `qwen/qwen3-embedding-4b` — **1 провайдер** (DeepInfra), `cohere/rerank-4-fast` — **1 провайдер**
  (Cohere сам). `allow_fallbacks`/`provider.order` в доке embeddings (openrouter.ai/docs/api-reference/embeddings)
  переключает между провайдерами ОДНОЙ модели — но раз провайдер один, переключать нечего: OpenRouter
  не даёт отказоустойчивости сверх того, что сегодня даёт `home→openrouter` пара. Отказоустойчивость
  «без домашней машины» = отказоустойчивость одного облачного хоста, что бы ни делал модуль.
- Реестр уровней (Project→Workspace→System), admin UI, MCP-обёртки — не про home/cloud, это
  мультитенантность PetBox поверх ЛЮБОГО набора плеч; не сжимаются этим сценарием.

Итог: убрать домашнюю машину — это про `home`-специфичный код (cert pinning, часть смысла breaker'а,
~100 строк), не про модуль целиком; K2/K1 (убить весь модуль, 90-summary) по-прежнему не оправданы —
причины из 90/80 §1 (реестр, MCP, per-project routing) не зависят от того, есть ли домашняя машина.

## 5. Риски

- **Переиндексация.** Смена/снятие облачной embed-модели у провайдера ломает `EmbedSpaceId` для ВСЕХ
  векторов этого пространства. Оценка объёма — только `$system`, `memory_store_list(includeUsage)`:
  **1935 записей памяти** (autocaptured 885, notes 492, session-digests 524, canon 1, ops 33). Это
  НЕ полная картина: не считает Tasks/Sessions episodic индексы (нет MCP-инструмента для их подсчёта)
  и не считает ~16 других проектов на сервере (90-summary упоминает миграцию ключей 16 проектов) —
  реальное число веторов кратно больше. Пометка: **(оценка, неполная)**.
- **Латентность.** Домашний embed — локальная сеть до `home`-хоста, connect-timeout 3с;
  облачный — интернет до OpenRouter/Cohere. Не измерялось в этом заходе (не было в объёме задачи);
  для interactive-rerank (`SearchService.cs:219`, живой поиск) это добавляет заметную задержку
  каждому запросу, не только фоновым джобам.
- **Приватность.** Тексты памяти/сессий уже сегодня уходят в облако 21–31% времени (fallback) —
  100%-облако не пересекает новую черту, просто делает происходящее сегодня частично — постоянным.
