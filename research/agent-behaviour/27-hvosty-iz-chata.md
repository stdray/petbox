## Поправка владельца к резерву: чем является канон

Резерв защищал разделение «файловый каскад для кита, серверный канон для рантайм-фактов
проекта», а несущей границей назвал идентичность писателя (кит / человек через PR /
агент через memory_upsert).

**Владелец возразил, и возражение принято:** факты существуют сами по себе. Канон —
это когда владелец говорит агенту закрепить некую прозу: может на основе фактов,
может из текущей ситуации, может из системы ролей. Продвижение факта в канон —
**акт решения владельца**, агент лишь исполнитель. Тем же решением его можно двинуть
в локальный файл.

**Следствие:** писателей не три, а два — **апстрим (кит) и владелец**; `memory_upsert`
не отдельный писатель, а одна из рук владельца. Граница проходит по ВЛАСТИ, а не по
механизму. Тогда «канон обязан жить на сервере» ни из чего не следует — остаётся
вопрос удобства, а не архитектуры.
