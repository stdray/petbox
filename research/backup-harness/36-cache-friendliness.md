## 2. Стабильность префикса — методологическая ловушка

Побайтовое сравнение СЫРЫХ тел запросов расходится РАНО: у Qwen общий префикс
ход↔ход — **35–38 КБ из ~100–105 КБ** (35 %), у Codex — **21–25 КБ из ~40–45 КБ** (55 %).
Место расхождения ОДНО И ТО ЖЕ у обоих: конец `messages`/`input` (закрывающая `]`), после
которого в проводном JSON идёт `"tools":[...]` — то есть **описания инструментов лежат
ПОСЛЕ растущей истории диалога в сериализации**, а не перед ней. Наивно это выглядело бы как
разрыв кэша на каждом ходе (тулы съезжают по байтовой позиции).

**Но `usage.prompt_cache_hit_tokens` показывает обратное** (таблица выше): 96–100 % попаданий
со 2-го хода у обоих. Вывод: порядок полей проводного JSON — не то же самое, что порядок
токенов в промпте, который реально видит модель (провайдер, вероятно, реконструирует
system+tools в начало последовательности по шаблону вне зависимости от порядка ключей в
HTTP-теле). **Побайтовый диф тела запроса — ненадёжный proxy для кэш-стабильности; надёжны
только счётчики `usage` от провайдера.**

Отдельно проверено содержимое динамических блоков (то, чего боялся вопрос): у Qwen —
`Today's date is Tuesday, September 8, 2026`, у Codex — `<environment_context><cwd>…
<current_date>2026-09-08</current_date>…`. В обоих случаях строка **побайтово идентична** на
всех ходах сессии (grep по `req-0002`…`req-0005` и `req-0001`…`req-0004`) — вставляется ОДИН
раз при старте сессии и дальше реплеится как часть истории, а не перегенерируется на каждом
ходе. **В пределах ОДНОЙ сессии обвязка не перештамповывает начало запроса** — часы, ENV,
список файлов не переинжектятся заново на каждый ход у обоих кандидатов.

## 3. Эффективная цена хода

Сумма miss-токенов ходы 2–4 (то, что реально оплачивается по полной ставке после старта):
**Qwen 769** (375+53+341), **Codex 959** (320+353+286) — Qwen у EQ, даже чуть ниже, при
стартовом оверхеде втрое большем. Трёхкратный разрыв старта **не умножается на ход — он
оплачивается практически один раз** (ход 1), дальше цена хода у обоих кандидатов измеряется
сотнями токенов, а не десятками тысяч.

## Главный вывод

**Для Qwen Code и Codex CLI на этом стенде — разрыв стартового оверхеда АМОРТИЗИРУЕТСЯ, а не
умножается.** Ход 1 несёт почти весь вес (Qwen 18 290 ток. по полной ставке, Codex 239–320);
ходы 2–4 обходятся в сотни токенов у ОБОИХ, разница между кандидатами по цене хода
практически стирается. Трёхкратный стартовый разрыв (`41-recount.md`) на длинной сессии
теряет вес пропорционально числу ходов — при 4 ходах уже даёт разрыв по СУММЕ miss-токенов не
3×, а обратный (Qwen 19 059 суммарно против Codex 1 198 — это всё ещё в пользу Codex по
абсолютной сумме, но целиком объясняется одним холодным стартом Qwen, а не повторяющимся
штрафом за ход).

## Оговорки

Данных мало: **1 прогон на кандидата, 4 хода** — не статистика, разброс между ходами внутри
одного прогона (miss 53…375 у Qwen) уже сравним по масштабу с разницей между кандидатами.
Ход 1 Codex — подогрет предыдущим (упавшим) прогоном в этом же расследовании, не эталонный
холодный старт. Билинг DeepSeek для hit-токенов — пониженная, не нулевая ставка (точный
коэффициент не проверялся, для вывода о «умножается/амортизируется» не требовался — считал по
miss-токенам, которые точно полная ставка). Механизм кэша DeepSeek (позиционный / чанковый /
по хэшу контента) — не документирован мной, вывод о «wire-порядок ≠ порядок в промпте модели»
сделан из наблюдаемого разрыва между байтовым дифом и `usage`, не подтверждён исходниками
провайдера.
