# Оверхед обвязки: стартовый расход, содержание системных промптов, дисциплина

2026-09-08 | Claude Opus 5 (1M), petbox-worker-highstakes | Docker `node:22-bookworm` (контейнер `bench-oh`, удалён); Claude Code — на машине владельца, ДРУГИМ методом, §A6.

**Метод части A (ЗАМЕРЕНО).** Локальный мок OpenAI-совместимого эндпоинта на `127.0.0.1:8899` (Node `http`, без зависимостей): пишет тело КАЖДОГО POST в файл, отвечает валидным SSE в трёх диалектах — `/v1/chat/completions`, `/v1/responses`, `/v1/messages`. Приём тот же, что в `26-qwen-inject-tui.md`. Каждый харнесс запускался в ПУСТОМ каталоге (без `AGENTS.md`, без MCP, без проектных файлов) с промптом `reply OK`; все четыре получили от мока `OK` и вышли с кодом 0 — перехвачен рабочий запрос, а не ошибка. **Счётчик один на всех:** `gpt-tokenizer@4.0.0`, кодировка `o200k_base`.

## A3. Что ценного (правила, правдоподобно экономящие ходы)

- **Qwen** — таблица «Prefer Dedicated Tools» (`read_file` вместо `cat/head/sed`, `edit` вместо `sed/awk`, `write_file` вместо heredoc, `glob` вместо `find`, `grep_search` вместо `grep/rg`); «Maximize use of parallel tool calls»; «Never make assumptions about the contents of files; use `read_file`» (читай перед правкой); «Prefer editing existing files over creating new ones».
- **Codex** — единственный прямо про экономию токенов: «Do not waste tokens by re-reading files after calling `apply_patch` on them. The tool call will fail if it didn't work.» Плюс ограниченный цикл («iterate up to 3 times») и «start as specific as possible… then broader tests».
- **opencode** — «You should minimize output tokens as much as possible»; «fewer than 4 lines»; «prefer to use the Task tool in order to reduce context usage»; «batch your tool calls together».
- **Droid** — плотнейший параллелизм: «Issue independent calls in one block so they run in parallel… fan out several speculative searches… Never batch a call whose input depends on an earlier result». Плюс «No user response or confirmation UI is available» — правило, совпадающее с режимом запуска.

## A4. Что выглядит балластом

**Инструкции под функции, которых в сборке НЕТ** — проверяется механически, сопоставлением текста промпта со списком `tools` того же запроса. **Codex** трижды требует `apply_patch` («Use the `apply_patch` tool to edit files (NEVER try `applypatch` or `apply-patch`…)») с примером JSON-вызова, а в инструментах запроса его НЕТ: `exec_command, write_stdin, request_user_input, view_image, multi_agent_v1, get_goal, create_goal, update_goal, web_search` — файлы писать нечем, кроме shell. Там же висячая ссылка «More on this in the "Sandbox and approvals" section»: такого раздела в доставленном промпте нет. **Qwen** запрещает вызывать `ask_user_question` (дважды) и `enter_plan_mode` — ни того, ни другого нет среди его 28 инструментов.

**Взаимоисключающие указания.** Qwen дважды дословно объявляет режим неинтерактивным («Never ask the user a question, even if the user explicitly requests one») — и тут же в few-shot показывает две модельные реплики, заканчивающиеся вопросом: «Would you like me to write a commit message and commit these changes?» и «Which one would you like to start with, or should I read all of them?». 732 токена примеров учат ровно тому, что запрещено абзацем выше.

**Повторы:** у Qwen абзац про неинтерактивность продублирован целиком (строки 83 и 192); у opencode «You MUST answer concisely with fewer than 4 lines» — дважды дословно (строки 19 и 84). **Под пустую подсистему:** 999 токенов Qwen (17 % промпта) описывают файловую память — типы, frontmatter, двухшаговая запись, правила индекса — и трижды сообщают «Your memory is currently empty». **Под несуществующего читателя:** 44 % промпта Codex — преамбулы и вёрстка сообщений «пользователю», которого в `codex exec` в момент работы нет; у opencode 9 % — подсказки про `/help` и GitHub-issues, недоставляемые в headless.

## A5. Окупается ли объём — проверка на своих же цифрах

Гипотеза: харнесс с бо́льшим промптом завершает за меньшее число ходов. Ходы = число POST'ов к модели, задача из части B, модель одна (`deepseek-chat`), 3 прогона на кандидата.

| харнесс | system, ток. | ходы B1 (×2) | ходы B2 | среднее | цепочка tool-call'ов | токенов на задачу |
|---|---|---|---|---|---|---|
| Droid | 890 | 3, 3 | 2 | 2.67 | `Create` (+`Read`) | 22–33k |
| opencode | 2 001 | 3, 3 | 5 | 3.67 | `write` / `bash, write, bash` | 15–30k |
| Codex | 4 145 | 4, 3 | 3 | 3.33 | `exec_command` ×2–3 | 28–37k |
| Qwen | 5 808 | 2, 2 | 2 | **2.00** | `write_file` | 44–45k |

**Гипотеза как правило НЕ подтверждается.** Монотонной связи нет: Qwen (самый большой промпт) лидирует по ходам, но Droid с промптом в 6.5 раза меньше идёт вторым, а Codex с промптом в 4.6 раза больше Droid тратит ходов БОЛЬШЕ всех. Разброс объясняет не объём прозы, а **инвентарь инструментов**: у кого есть выделенный инструмент записи файла (`write_file`, `Create`, `write`) — укладывается в один вызов; Codex, у которого файлового инструмента нет вовсе, идёт через `exec_command` и добирает ходы на проверке. Правило Qwen «Prefer Dedicated Tools» работает лишь потому, что такие инструменты у него есть.

**И там, где ходы экономятся, объём себя не окупает:** один ход Qwen стоит ~22k токенов базы, и чтобы сравняться с opencode по стоимости задачи (15k за 3 хода), Qwen должен был бы уложиться меньше чем в один ход — большой промпт сам и делает ход дорогим.

> [!WARNING]
> Данных мало: 3 прогона на кандидата, задача решается за 1–2 вызова, различий в качестве нет вовсе (§B). Опровергнут только сильный вариант гипотезы. Слабый — что регламент окупается на длинной задаче, где он один раз предотвращает неверную ветку, — этим стендом НЕ проверяется.

## A6. Claude Code — ДРУГОЙ МЕТОД, числа несопоставимы

Перехват невозможен (проприетарный эндпоинт); промпт из бинаря НЕ извлекался. **ЗАМЕРЕНО по собственной телеметрии:** транскрипты `~/.claude/projects/*/*.jsonl`, у первого `assistant`-сообщения сессии `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`. 224 сессии, версии 2.1.251–2.1.263, модель `claude-opus-5`. Минимум по всем сессиям (пустой временный каталог) — **14 416**; типичная сессия во временном каталоге — 22 400–22 650; рабочий каталог `D:/my/prj/petbox` — минимум 24 864, медиана **44 540** (n=72); медиана по всем 224 сессиям — 35 872.

**ПО ДОКАМ (не мой замер):** публичная оценка стартового оверхеда — **~33k токенов** до чтения промпта, с разбивкой «системный промпт ~2.5k + определения инструментов 14–17k» ([systima.ai](https://systima.ai/blog/claude-code-vs-opencode-token-overhead), обсуждение — [HN 48883275](https://news.ycombinator.com/item?id=48883275)). Та же публикация даёт opencode ~7k — что совпадает с моим независимым замером 7 440 (§A1) и служит проверкой метода. Мой пол для Claude Code (14 416) вдвое ниже публичных 33k; правдоподобная причина — в версиях 2.1.25x схемы инструментов и MCP отдаются отложенно (механизм `ToolSearch`, наблюдаем в этой же сессии), но это ГИПОТЕЗА.

**Структура — ПО ДОКАМ И ПО НАБЛЮДАЕМОМУ ПОВЕДЕНИЮ, без дампа:** идентичность и тон; политика инструментов с запретом `find`/`grep` в пользу `Glob`/`Grep`; правила правок (читать файл перед `Edit`, не создавать файлы без нужды, не коммитить без просьбы); блок безопасности; `CLAUDE.md`/память проекта; каталог скиллов; `<system-reminder>`-вбросы в пользовательский ход; отложенные схемы через `ToolSearch`. По составу блоков ближе всего к Qwen Code, по отсутствию few-shot-простыней — к Droid.

## Оговорки и чего не проверял

- Расход зависит от **модели** (A — мок `mock-model`, B — `deepseek-chat`), **версии харнесса** (Qwen 0.23.0 · Codex 0.153.4 · opencode 1.18.29 · Droid 0.213.0 · Claude Code 2.1.251–2.1.263) и **задачи** (`reply OK` / B1 / B2). Разные токенизаторы дают разные числа: четыре контейнерных кандидата посчитаны ОДНИМ счётчиком (`gpt-tokenizer@4.0.0`, `o200k_base`), Claude Code — счётчиком Anthropic, поэтому вынесен отдельно. A1–A4 объективны и повторяемы; A5 и B — наблюдение на 2–3 прогонах, статистики не дают.
- Оверхед с подключённым PetBox-MCP (122 инструмента) не мерился: нужен был голый харнесс, чтобы разница была свойством обвязки, а не нашего сервера. Для Qwen это ляжет поверх худшего старта.
- Кэширование промпта (какая доля первого запроса оплачивается по полной ставке на повторных ходах) — прокси видит запросы, но кэш-политика у каждого провайдера своя.
- Задача, на которой кандидаты расходятся по КАЧЕСТВУ, и длинная многоходовая задача, где регламент мог бы окупиться (слабый вариант гипотезы §A5) — бюджет ушёл в часть A.
