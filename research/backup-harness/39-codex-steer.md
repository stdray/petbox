# Стенд досылки: Codex CLI — канал STEER (не queue) — живой прогон

Дата: 2026-09-08 | Исполнитель: Sonnet 5, petbox-worker. Docker (`node:22-bookworm`,
контейнер `bench-steer`, удалён `docker rm -f` по завершении). Codex CLI **0.153.4**
(`npm install -g @openai/codex@0.153.4`), DeepSeek-ключ из `customModels[0]` владельца
(`~/.factory/settings.json`), передан как `CODEX_API_KEY` (BYOK-переменная, установлено
прошлым прогоном), `base_url=https://api.deepseek.com/v1`, `wire_api="responses"`. Ключ
нигде не напечатан (извлечён в файл в scratchpad, использован через `$(cat file)`).

## Отличие от прошлого прогона (24-bench-qwen-codex.md)

Прошлый раз слали через `codex queue --thread <UUID>` (внешний процесс) — это
`thread/queue/add`, доставка ПОСЛЕ хода. В этот раз — канал **steer**: обычный Enter в
живом TUI под tmux во время работающего хода (`TurnInputMode::Steer`, тот же путь, что и
`send_input` оркестратора к субагенту). Путь поднялся сразу, других (app-server
`turn/steer` JSON-RPC, agent-control API) не потребовалось — не пробовал, честно фиксирую.

## Установка канала

`tmux new-session -d -s cx bash` → `codex` (TUI, git-репо в `/work` инициализирован для
трастed-каталога — `--skip-git-repo-check` в TUI не существует, это флаг только `exec`).
Задача через `tmux send-keys ... Enter`: `Run ./hang.sh verbatim (no timeout wrapper, no
backgrounding) and wait for it to finish, then report the test results.`

## Основной прогон: hang.sh (вечный)

- Ход вошёл в блокирующий вызов — ПОДТВЕРЖДЕНО живьём: `ps aux` в контейнере показал
  `/bin/sh ./hang.sh` + дочерний `sleep 5`, TUI: `Working (Xs • esc to interrupt)`.
- Steer отправлен через Enter в 13:33:46 (~8-10с после старта хода): «STOP the hang.sh
  test hangs by design and will never exit. Kill the hang.sh process now, then run: echo
  STEER-OK-7f3q > /work/proof.txt and report that you did this instead of waiting.»
- Сразу после отправки TUI показал строку `Messages to be submitted after next tool call
  (press esc to interrupt and send immediately)` — это UI-подпись, а не факт: реальная
  доставка случилась РАНЬШЕ, чем закончился бы `./hang.sh` (он никогда не заканчивается),
  что и есть решающее доказательство steer, а не queue-после-хода.
- Между 13:34:52 (ещё «Working», реакции нет) и 13:35:18 (ход закрыт) модель: прочла
  `hang.sh`, выполнила `ps -ef | grep hang.sh|sleep`, УБИЛА процесс (`exit 130`),
  ПРОВЕРИЛА, что `proof.txt` не существует, и ЯВНО ОТКАЗАЛАСЬ его писать («I won't
  fabricate a completion marker»). Ход закрыт: `Worked for 1m 44s` (итого ~104с от старта
  хода, ~90-95с от отправки steer).
- **Доставка содержания подтверждена, а не шаблонная реакция**: модель процитировала
  текст ловушки («hangs by design»), различила ДВЕ части моей инструкции (убить процесс —
  выполнила; написать proof-строку — сознательно отказалась как «фабрикация») — это
  сильнее, чем совпадение с текстом: значит она реально ПОНЯЛА содержание, а не
  среагировала на ключевые слова.
- `ps aux` после хода: `hang.sh` и его `sleep 5` ОТСУТСТВУЮТ — остался только PID1
  контейнера (`sleep infinity`). **Процесс действительно убит.**

## Контроль: hang30.sh (30с)

Первая попытка смазана моей же ошибкой тайминга (steer отправлен до старта хода — оба
сообщения слились). Повтор с подтверждением через `ps aux`, что `hang30.sh` реально
запущен (13:39:04), затем steer отправлен в 13:39:09 (~5с после старта, за ~25с до
естественного конца). `hang30.sh` естественно завершился ~13:39:34 (30с); ТОЛЬКО ПОСЛЕ
этого модель обработала steer и написала: «hang30.sh had already finished naturally... so
I ignored the follow-up». proof2.txt не создан (корректно per условие «если уже
завершился — игнорируй»).

**Честная оговорка:** контроль НЕ различает «доставлено на границе tool-call» от
«доставлено на очередном ~30с sampling-чекпоинте», потому что для 30-секундного скрипта
естественный конец и период yield-клэмпа (см. код, ≤30с) почти совпадают по времени. Этот
контроль сам по себе НЕ доказывает «на границе» и не опровергает «steer»; отличие видно
только по основному прогону — там естественной границы нет вообще (`hang.sh` вечен), а
доставка всё равно произошла, что возможно только через мидфлайт-дренаж `input_queue`, а
не через ожидание завершения вызова.

## Исход по таблице спецификации

**ПРЕРЫВАЕТ.** Сообщение доставлено ВНУТРИ незакрытого хода (без естественной границы —
она физически не наступает у `hang.sh`), висящий процесс убит, агент отреагировал именно
на содержание текста (избирательно: выполнил одну часть инструкции, отверг другую как
фабрикацию — возможно только при реальном понимании смысла, не по шаблону).

Время: steer → реакция ≈ 90-95с (несколько циклов ~30с yield-клэмпа `exec_command`,
модель сначала исследовала, затем убила). Диагностика — секунды (Enter долетел мгновенно,
UI показал его в очереди на следующий tool-call сразу после отправки).

## Какой путь сработал

Enter в живом TUI под tmux во время активного хода — сработал сразу и дал наблюдаемый
живой факт. `turn/steer` (app-server JSON-RPC) и agent-control `send_input`
(`core/src/agent/control.rs:192-210`) НЕ пробовал отдельно — по коду это тот же
`input_queue`-механизм, но живьём не замерено; TUI-путь дал полноценный результат в
рамках бюджета задачи.
