# Стенд досылки: Codex CLI vs Qwen Code — живой прогон

Дата: 2026-09-08 | Исполнитель: Sonnet 5, petbox-worker. Всё в Docker (`node:22-bookworm`,
контейнер `bench-cq`, удалён по завершении). Ключ — DeepSeek из `customModels` владельца
(`~/.factory/settings.json`), OpenAI-совместимый endpoint `https://api.deepseek.com/v1`,
ключ нигде не напечатан. Оба кандидата работали на своём ключе, без аккаунта вендора
харнесса — ПОДТВЕРЖДЕНО живьём (см. ниже), не только по коду.

## Установка (пин версий)

| кандидат | пакет | версия | путь установки |
|---|---|---|---|
| Codex CLI | `@openai/codex` (npm, latest) | **0.153.4** | `npm install -g` в контейнере |
| Qwen Code | `@qwen-code/qwen-code` (npm, latest) | **0.23.0** | `npm install -g` в контейнере (совпадает с HEAD клона) |

Ставил релизные пакеты, не собирал из клонов — быстрее, и это ровно то, что сделала бы
третья сторона (раздаваемость проверяется на публичном пакете, не на дневном срезе репо).

## Codex CLI: BYOK живьём

`model_providers.deepseek { base_url="https://api.deepseek.com/v1", env_key="DEEPSEEK_API_KEY",
wire_api="responses" }`, `model_provider="deepseek"`. Важно: в этой сборке `wire_api="chat"`
**отклоняется на этапе парсинга конфига** (`CHAT_WIRE_API_REMOVED_ERROR`, только `"responses"`
валиден — `model-provider-info/src/lib.rs:65-92`). Опасался, что это ломает BYOK для
chat-completions-провайдеров типа DeepSeek — ЗАМЕРЕНО живьём, что НЕ ломает: DeepSeek принял
Responses-формат запроса, `codex exec 'say hi'` → `Hi!` за один прогон. Раздаваемость на
DeepSeek — подтверждена, вопреки статическому опасению.

**Переменная auth (расхождение доки/код закрыто):** `codex doctor` с `OPENAI_API_KEY=sk-...` →
`auth mode: none`, `reachability mode: ChatGPT auth` (ключ не используется для авторизации).
С `CODEX_API_KEY=sk-...` → `auth mode: api_key`, `reachability mode: API key auth` (реальный
BYOK-путь). Код: `read_codex_api_key_from_env()` (`CODEX_API_KEY`) — то, что реально драйвит
`load_auth()` (`login/src/auth/manager.rs:1475`); `read_openai_api_key_from_env()`
(`OPENAI_API_KEY`) используется только в `realtime_conversation.rs` и как префилл поля логина
в TUI onboarding — на авторизацию не влияет. **Вывод: доки врут, `CODEX_API_KEY` — рабочая
переменная, `OPENAI_API_KEY` для дефолтного провайдера бесполезна.**

## Qwen Code: BYOK живьём

`--openai-api-key/--openai-base-url` (или `OPENAI_API_KEY`+`OPENAI_BASE_URL`) на
`https://api.deepseek.com/v1`, `-m deepseek-chat`. Работает штатно, авторизация именно
`OPENAI_API_KEY` (без расхождений с доками) — `qwen -p 'say hi'` → `Hi.` с первой попытки.

**Ловушка методологии:** позиционный промпт (`qwen "..."`) — это **one-shot режим**, процесс
завершается после одного хода; досылка туда физически некуда доставлять (сессия мертва).
Живая сессия для теста досылки требует `-i/--prompt-interactive`. Без этого первые прогоны
ложно выглядели как «канал сломан» — оказалось, канала для сообщения ещё не было.

## Ловушка (hang.sh) и контроль (hang30.sh) — по спецификации

Обе связки: агент получает задачу «запусти `./hang.sh` verbatim (без timeout/backgrounding),
дождись», реально входит в blocking tool-call. DeepSeek иногда сам оборачивал вызов в свой
`timeout N` — тест переформулировался явным запретом, пока агент не заходил в СЫРОЙ вызов.

| кандидат | команда досылки | исход (hang.sh, вечный) | контроль (hang30.sh, 30с) | время ожидания |
|---|---|---|---|---|
| Codex CLI | `codex queue --thread <UUID> --message <TEXT>` (внешний процесс) | **НЕ приходит** — ждали 187с внутри висящего вызова, ноль реакции | доставлено ровно на границе (~30-31с, сразу после `./hang30.sh completed`), обработано штатно | 187с (висяк) / 31с (контроль) |
| Qwen Code | TUI `-i`: Enter «steer» или Ctrl+Q «queue» в момент висящего tool-call; также внешний `--input-file` JSONL `{"type":"submit",...}` | **встаёт в `⏳ queued`** и в момент висящего вызова НЕ прерывает; доставляется только когда харнесс сам обрывает вызов по таймауту (см. ниже) | доставлено ровно на границе (~32с, сразу после `✓ Shell ./hang30.sh` завершился), обработано штатно | ~108с до вынужденной границы (харнесс-таймаут) / 32с (контроль) |

Оба — **НА ГРАНИЦЕ** по таксономии легенды: сообщение реально доходит только когда
tool-call естественно завершается (контрольный прогон это доказывает — тем же каналом,
тот же текст, разница только в конечности скрипта). На вечном висе граница не наступает
никогда — сам механизм досылки её не создаёт ни у одного кандидата.

## Таймаут tool-call у харнесса — решающее отличие

- **Codex CLI**: настраиваемого таймаута на shell tool-call НЕ нашёл (`grep` по исходнику —
  ноль совпадений на `tool_timeout`/`shell_timeout`/`exec_timeout`); ЗАМЕРЕНО — висящий вызов
  не прерывался харнессом за 187с (тест остановлен по бюджету, не по признаку завершения).
  Значит для истинно вечного зависания у Codex нет самолечения: ни досылка, ни таймаут —
  сообщение владельца может ждать сколь угодно долго.
- **Qwen Code**: у shell-тула есть **дефолтный жёсткий таймаут 120000мс (2 мин)**, ЗАМЕРЕНО
  дважды живьём (`Command timed out after 120000ms before it could complete`), включён по
  умолчанию, TUI даже предупреждает за секунды до обрыва («Ctrl+B to keep it running in the
  background»). Это и есть исход **ТАЙМАУТ ХАРНЕССА** — не досылка чинит боль, а сам факт,
  что харнесс не даёт tool-call висеть вечно, и уже ПОСЛЕ вынужденного обрыва доставляет
  накопленную очередь как обычно.

## Закрывает ли боль владельца

Сценарий боли (застрявший воркер, сообщение в очереди, никто не реагирует) — **истинного
прерывания (ПРЕРЫВАЕТ) не даёт ни один кандидат**: оба реализуют «положить в очередь до
границы», а не «прервать висящий вызов текстом».

- **Codex CLI: боль НЕ закрывает.** Ни досылки-с-границей, ни таймаута — вечный `hang.sh`
  вечно висит, сообщение владельца лежит в очереди без гарантии когда-либо примениться.
- **Qwen Code: закрывает частично, но практически.** Досылка сама по себе такая же
  «на границе», как у Codex, — но встроенный дефолтный 2-минутный потолок на shell-tool-call
  гарантирует, что граница наступит сама, без участия человека, и любое отложенное сообщение
  (включая штатную досылку) применится не позже ~2 минут. Это не «услышал и прервался», а
  «система не даёт застрять дольше двух минут», что для боли владельца (opencode: ждать
  неограниченно) — практическая, хоть и не архитектурная, победа.

## Границы прогона

- Оба кандидата — Docker-only, на машину владельца ничего не ставилось; контейнер `bench-cq`
  удалён (`docker rm -f`) по завершении.
- `--input-file` внешний канал Qwen Code при верном `-i` режиме доставляет сообщение (ЗАМЕРЕНО
  на контрольном 30-секундном прогоне) — то же «на границе», что и клавиатурный ввод; отдельно
  не гонял вечный hang.sh через этот канал (бюджет), но механика идентична TUI-каналу по коду
  (`RemoteInputWatcher` → тот же `submitFn`/очередь).
- `codex agents`/`qwen sessions ps` для листинга активных сессий headless не пробовал —
  ID сессии брал из `session_index.jsonl`/`chats/*.jsonl` напрямую, этого хватило.
