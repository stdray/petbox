# Qwen Code 0.23.0 — инжект в первый ход и TUI-гигиена (живой прогон)

Дата: 2026-09-08 | Исполнитель: Claude Sonnet 5, petbox-worker | Среда: Docker
`node:22-slim` (контейнер `qwen-live`, удалён после прогона), `npm i -g
@qwen-code/qwen-code@0.23.0` (совпадает с версией из D1). Ключи провайдера не
использовались: локальный mock OpenAI-совместимый сервер (Node `http`, SSE) на
`127.0.0.1:8842`, `--auth-type openai --openai-base-url ... --openai-api-key dummy`.

## Проверка 3 — инжект в ПЕРВЫЙ ход

**ПО КОДУ.** Единственный вызов `hookSystem.fireSessionStartEvent` —
`packages/core/src/core/client.ts:2184-2192`, внутри `fireSessionStartHook`
(`client.ts:2169`), везде под `await`. Этот метод сам вызывается под `await`
внутри `startChat()` (`client.ts:2329`), результат сразу применяется —
`chat.applySessionStartContext(...)` (`client.ts:2334`) — ДО того как
`startChat()` вернёт объект чата. Все 6 мест вызова `startChat()`
(`client.ts:565,597,620,622,1519,5113`) сами вызываются под `await`, включая
внутри `GeminiClient.initialize()`, которую CLI обязан дождаться до первого
запроса к модели. Гонки по конструкции нет: SessionStart НЕ detached, в
отличие от DeepSeek Harness.

Есть намеренный опт-аут: `hookRunner.ts:635` —
`hookConfig.type === HookType.Command && hookConfig.async === true`.
Это ЯВНЫЙ флаг `async: true` в конфиге отдельного command-хука
(по умолчанию `false`/отсутствует ⇒ синхронно).

**ЗАМЕРЕНО.** Хук `SessionStart` (`sh`, `sleep 0.5` перед выводом) отдаёт
`{"hookSpecificOutput":{"additionalContext":"PETBOX-QWEN-CANARY-7788"}}`.
Запуск `qwen "hi" --openai-base-url ... -m mock-model --approval-mode yolo`
(one-shot, non-interactive):
- Дефолт (без `async`): маркер — В ЗАПРОСЕ #1, как часть системного сообщения
  (`messages[0].role === "system"`), а не отдельным `user`-сообщением, как у
  DeepSeek. `transcript_path` в payload хука был НЕ пуст (побочное наблюдение,
  не входит в задание — не проверял стабильность этого через SessionEnd).
- Контроль `"async": true` на том же хуке: маркер ОТСУТСТВУЕТ в запросе #1 и
  ни в одном другом захваченном запросе за весь прогон (второй захваченный
  запрос — не продолжение диалога, а отдельный служебный вызов
  memory-extraction-субагента; в one-shot-режиме больше ходов к модели нет).
  Хук при этом реально отработал (`hook-input.json` записан) — результат
  просто не успел никуда попасть, потому что его никто не ждёт.

**Итог.** Инжект попадает в первый ход НАДЁЖНО при дефолтном (синхронном)
хуке — гонка DeepSeek здесь не воспроизводится. Она воспроизводится, только
если ПОЛЬЗОВАТЕЛЬ САМ включит `async: true` на SessionStart-хуке — тогда
эффект хуже, чем у DeepSeek (там маркер хотя бы долетал вторым ходом; здесь
в one-shot он может не долететь никогда). Вывод для обвязки: не ставить
`async: true` на SessionStart.

## Проверка 4 — TUI-гигиена, Home/End

**ПО КОДУ.** Дефолтный рендерер — ink (`packages/cli/src/ui/opentui/
renderer-selection.ts`: opentui только по `QWEN_TUI_RENDERER=opentui`,
требует Node ≥26.4/Bun ≥1.3 — в контейнере Node 22, не проверял). В
ink-режиме поле ввода — `BaseTextInput.tsx`, реальный ввод символа сначала
идёт через `onKeypress` перехватчик `InputPrompt.tsx`, а нераспознанное там
падает на `buffer.handleInput(key)` (`BaseTextInput.tsx:313`).
`text-buffer.ts:2685-2687`: голые клавиши `home`/`end` (`key.name==='home'`/
`'end'`) жёстко привязаны к `move('home')`/`move('end')` — перемещение
курсора В СТРОКЕ ввода. `Ctrl+A`/`Ctrl+E` — то же самое через отдельный
слой команд (`keyBindings.ts:130-131`). `Ctrl+Home`/`Ctrl+End` — ДРУГАЯ
команда, `SCROLL_HOME`/`SCROLL_END` (`keyBindings.ts:281-282`), потребитель —
`ScrollableList.tsx` (списки/диалоги, не композер и не общая история сессии).
В `InputPrompt.tsx` нет перехвата голых `home`/`end` под историю/скролл —
конфликта в коде не нашёл. Не настраивается через `settingsSchema.ts` как
отдельная опция — только через переопределение `keyBindings` целиком.

**ЗАМЕРЕНО живьём (PTY через `tmux`, реальный интерактивный TUI, без
модели).** `tmux new-session ... 'qwen --openai-base-url ... -m mock-model'`
внутри контейнера, `tmux send-keys` шлёт настоящие терминальные
последовательности для именованных клавиш (`Home`, `End`, `C-j`), не голый
текст. Тест: напечатал `HELLOWORLD` → `Home` → `Z` → в поле ввода
`ZHELLOWORLD` (курсор ушёл в начало строки, не в историю сессии — экран
транскрипта не менялся). Дальше `End` → `Y` → `ZHELLOWORLDY` (курсор ушёл в
конец). Итог: **конфликта с прокруткой истории НЕТ** — обе клавиши работают
как в обычном readline-поле.

Заодно (той же PTY-сессией): многострочность — `Ctrl+J` вставляет перевод
строки внутри композера (вторая строка отрисована отдельной строкой, `Enter`
не срабатывает как newline без модификатора — тоже readline-конвенция);
вставка из буфера — `tmux set-buffer` + `paste-buffer` (bracketed paste)
вставляет текст одним куском в позицию курсора, без искажений.

## Чего не проверил и почему

- Реальный процесс на Node ≥26.4/Bun ≥1.3 → рендерер `opentui`
  (`packages/cli/src/ui/opentui/input-prompt.tsx`, своя `TextareaRenderable`
  из `@opentui/core`, СВОЙ обработчик клавиш, не `text-buffer.ts`) — не
  собран и не проверен ни по коду, ни живьём; это экспериментальный
  неосновной путь (гейт по версии рантайма), сам факт по коду это подтверждает.
- `SessionEnd`/выгрузка транскрипта — не в объёме этой задачи (см. отдельный
  пункт в `40-decisions.md`); `transcript_path` был непуст в SessionStart-
  payload, но это не то же самое событие и не проверялось само по себе.
- Гонка `send_message`/`interrupt_agent` к застрявшему воркеру у Qwen — не
  моя задача (закрыта в `40-decisions.md` через таймаут tool-call, замерено
  в `22-steering-bench.md`).
- Не проверял поведение Home/End при переносе длинной строки на несколько
  визуальных строк (только 10-символьная строка) и при активном автокомплите/
  поповере — не входило в объём, бюджет строк/времени ушёл на решающий
  вопрос (конфликт с историей), а не на все грани редактирования.
