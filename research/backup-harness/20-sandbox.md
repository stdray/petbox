# Кандидат: сандбокс-замер раздаваемости droid (Factory) 0.213.0

Дата: 2026-09-08 | Исполнитель: Sonnet 5, petbox-worker | Источники: живой прогон в
Docker (node:22), docs.factory.ai, factory.ai/pricing

## Вердикт в одну строку

Раздаваемо: `droid exec` на custom-модели (BYOK) СТАРТУЕТ и РАБОТАЕТ на чистой
машине без аккаунта Factory и без FACTORY_API_KEY — барьер стоит по МОДЕЛИ и по
РЕЖИМУ (exec vs interactive), не по наличию логина как таковому.

## Метод (ЗАМЕРЕНО)

Контейнер `node:22`, чистый (без монтирования `~/.factory`, без FACTORY_API_KEY),
удалён после теста. Установка: `curl -fsSL https://app.factory.ai/cli | sh` —
единственный официальный способ с сайта (docs.factory.ai quickstart ссылается на
platform-tabs, реальная команда нашлась через поиск и подтвердилась установкой) →
поставила v0.213.0 в `~/.local/bin/droid`, чек-сумма проверена самим скриптом.
Ключ провайдера: взят РЕАЛЬНЫЙ plaintext-ключ владельца из `~/.factory/settings.json`
(`customModels[0]`, DeepSeek V4 Pro, `provider: anthropic`, `baseUrl: api.deepseek.com/anthropic`) —
все 9 записей `customModels` там хранятся в открытом виде, шифрования нет. Ключ
скопирован ТОЛЬКО в контейнер (`docker cp`, минимальный settings.json с одной
записью), нигде не напечатан целиком (в чате виден только 6-символьный префикс для
проверки "plaintext vs encrypted"). `~/.factory` владельца открывался только на
чтение (`ls`, `cat | python3 -`), на запись не трогался.

## Пошаговые результаты (все ЗАМЕРЕНО)

1. **`droid exec` без ЛЮБОЙ аутентификации** (нет `~/.factory`, нет
   `FACTORY_API_KEY`, дефолтная модель `gpt-5.6-sol`):
   ```
   Error during droid execution: Authentication failed. Please log in using
   /login or set a valid FACTORY_API_KEY environment variable.
   ```
   Отказ ПОСЛЕ инициализации: `~/.factory/` (cache, sessions, logs, telemetry,
   host.json) создаётся ДО отказа — значит бутстрап конфигурации происходит раньше
   проверки логина, сам отказ — уже на попытке обратиться к дефолтной модели.

2. **`FACTORY_API_KEY=fake-invalid-key-12345`** (форма правдоподобная, ключ
   фиктивный):
   ```
   Error during droid execution: Authentication failed. FACTORY_API_KEY is set
   but appears to be invalid. Unset it or replace it with a valid key.
   ```
   Отдельная, более точная ветка ошибки — значит переменная реально читается и
   валидируется до вызова модели.

3. **`droid exec -m custom:DeepSeek-V4-Pro-0`, РЕАЛЬНЫЙ ключ владельца, БЕЗ
   Factory-логина, БЕЗ FACTORY_API_KEY** — единственный решающий тест:
   ```
   $ droid exec -m custom:DeepSeek-V4-Pro-0 'Reply with exactly one word: PONG'
   PONG
   ```
   exit 0. Полноценный ответ модели. **Это и есть ответ на вопрос раздаваемости:
   да, стартует.**

4. **Та же модель, но ФИКТИВНЫЙ (заведомо валидный по форме) ключ провайдера** —
   различение барьера Factory vs барьера провайдера:
   ```
   Error during droid execution: Exec failed
   ```
   (короткое сообщение в stdout; в `~/.factory/logs/droid-log-single.log` полный
   след — `FetchError: 401 {"detail":"Missing authorization token in HTTP
   headers","status":401,"title":"Unauthorized", ...}` от эндпоинта DeepSeek,
   6 попыток ретрая). Ключевое: это НЕ ошибка "Authentication failed... log in
   using /login" из пп.1-2 — барьер явно провайдерский, не Factory-шный. Значит
   в п.3 успех был именно за счёт валидности ключа, а не случайной подмены.

5. **`droid` (интерактивный, без TTY, `< /dev/null`, тот же settings.json с
   валидным custom-ключом из п.3, всё ещё без Factory-логина)**: полностью
   рисует TUI (заставку, `v0.213.0`, статус-бар Skills/MCPs/AGENTS.md), НО
   останавливается на экране:
   ```
   Welcome to Factory CLI
   Please login with your Factory account to continue.
   > Login
     Exit
   ```
   и виснет там (killed by `timeout 8`, exit 124). **Отличие от `exec`:
   интерактивный режим требует Factory-логин ВСЕГДА, даже когда в settings.json
   уже лежит рабочая custom-модель** — в `exec` то же самое BYOK-конфигурирование
   логина не требует. Граница проходит не только по модели (снимок п.16-26), но
   и по режиму exec/interactive отдельно от модели.

## Что нужно другу для раздаваемости

Ничего сверх самого droid + своего API-ключа провайдера, ПРИ УСЛОВИИ:
(а) он работает только через `droid exec -m custom:...` (headless/скриптово),
(б) не запускает интерактивный TUI и не пытается открыть Missions/встроенные
модели. Интерактивный вход и Missions по факту требуют аккаунт Factory
(п.5 замерено; Missions — по докам из снимка, платный план + Extra Usage).
Бесплатной регистрации, по докам, не существует — все тарифы платные от $20/мес,
но неясно, обязательна ли оплата для САМОГО факта регистрации (см. выше).

## Чего не проверил и почему

- Полный signup-флоу (карта на шаге регистрации vs только на шаге апгрейда) —
  граница задачи прямо запрещала это проходить.
- Работает ли `--mission` в контейнере без Factory-логина при custom worker-model
  (снимок владельца уже показал ЗАМЕРЕНО на его машине, что миссии падают на
  auth ДАЖЕ с `--worker-model custom:...` — не переизмерял в контейнере, так как
  это дублирует уже надёжный замер владельца и не относится к вопросу exec-раздачи).
- PetBox-обвязка (MCP/хуки) внутри контейнера — не тестировал, вне вопроса задачи
  (только раздаваемость самого droid).
