(контейнер `oc-bench`, удалён `docker rm -f` по завершении). `npm i -g opencode-ai@1.18.29`
(владельца версия; `npm view opencode-ai dist-tags` в день замера подтвердил `latest=1.18.29` —
второй прогон "если вышла новее" не нужен, владелец уже на актуальной). Ключ — DeepSeek из

`https://api.deepseek.com/v1`, модель `deepseek-chat`), вписан в `provider.deepseek.options.apiKey`

аккаунта opencode.ai. Роли `petbox-orchestrator`(primary)/`petbox-worker`(subagent) заведены в
конфиге, обе на `deepseek/deepseek-chat`.

## 1. Стенд досылки (обязательный)

Канал — headless `opencode serve --port 4096`, второй `opencode run --attach ... --session <id>`
досылает сообщение в ту же сессию (это ровно то, что делает TUI при отправке сообщения в
работающую сессию — тот же REST-эндпоинт `POST /session/{id}/message`).

**Контроль (hang30.sh, 30с):** команда `opencode run 'Run ./hang30.sh verbatim ... --agent
petbox-worker --auto`. Tool `bash ./hang30.sh` шёл 875905→905976мс (30.07с, совпадает со
скриптом). Досылка STOP отправлена на +12.2с (внутри вызова) → `step_start` с обработкой STOP
пришёл в 906499мс, **сразу после и только после** конца tool-call. Граница доказана.

**Вечный hang.sh — решающий нюанс.** Первая попытка: модель САМА проставила `bash`-тулу
`"timeout":30000` (самоограничение, как у Codex/Qwen в `24-bench-qwen-codex.md`) — переигран
явным запретом задавать `timeout` в промпте. Чистый прогон: `bash ./hang.sh` без параметра
timeout шёл 046128→166245мс = **120117мс**, конец — синтетическая строка от самого инструмента:
`"shell tool terminated command after exceeding timeout 30000 ms"` (в первой попытке) и
`"...120000 ms..."` (во второй) — **харнесс сам убивает процесс**, это не shell-обёртка модели.
Досылка STOP отправлена на +16.6с (глубоко внутри вечного цикла) → обработана только в
166716мс, через 471мс ПОСЛЕ принудительного киллА, не раньше.

| исход | по спецификации |
|---|---|
| **ТАЙМАУТ ХАРНЕССА** | харнесс принудительно оборвал `./hang.sh` через 120000мс (дефолт tool'а, не таймаут MCP), сообщение обработано сразу после — тот же паттерн, что у Qwen Code |

Чистая досылка-с-прерыванием (ПРЕРЫВАЕТ) не наблюдалась ни разу: голое сообщение в сессию —
всегда «в очередь до границы»; границу здесь создаёт не сам механизм steering, а независимый
дефолтный киллер tool-call'а.

**Оговорка:** в вечном прогоне в истории 2 идентичных STOP-сообщения (055059/063338мс) — не баг
сервера, а осиротевший процесс от моей же бракованной первой попытки досылки; оба дали одну и
ту же границу (после килла), на вывод не повлияло.

## 2. Потолок исполнения tool-call

**ЗАМЕРЕНО.** Дефолт — **120000мс**, если модель не передаёт `timeout`; включён всегда (не флаг).
Настраивается **моделью за один вызов** (`bash`-тул принимает `timeout` в мс, JSON-схема:
`minimum: -9e15` / `maximum: 9e15`, реального потолка нет — модель может поставить хоть 1мс, хоть
любое огромное число, как и сделала в первой попытке — 30000). **НЕ настраивается статически
харнессом/оператором**: прогнал полный JSON-schema `opencode.json` (`https://opencode.ai/config.json`)
через поиск по `timeout` — совпадения только `ProviderConfig.options.timeout/headerTimeout/
chunkTimeout` и `Mcp*Config.timeout`/`experimental.mcp_timeout` — это именно таймаут ОЖИДАНИЯ
ответа сервера/MCP (та величина, о которой предупреждает `01-legend.md`), а не потолок
исполнения. Отдельного `opencode.json`-ключа под дефолт bash-тула нет.

## 3. Блокирует ли субагент главную сессию

**ЗАМЕРЕНО двумя независимыми способами.**
- REST: primary-сессия получила task-tool-вызов `petbox-worker`→`./hang30.sh` (32.4с). Пинг
  `"what is 2+2, answer immediately"` отправлен в ТУ ЖЕ сессию на +12.4с работы таска; сам
  процесс `opencode run --session` с этим пингом вернулся только в 292846мс — через 1.15с
  ПОСЛЕ окончания task-tool-вызова (291699мс), не раньше. Главная сессия не ответила, пока
  воркер работал.
- TUI (tmux, живой PTY): во время `⠙ Petbox-Worker Task — Run hang30.sh` набрал в основном
  поле ввода `typed while worker busy`, нажал Enter — текст встал в поле, ушёл из view при
  сабмите, но обработан ассистентом только ПОСЛЕ `✓ Petbox-Worker Task ... 33.6s`, с ответом
  «Worker already completed». Оба замера согласованы.

Занятно: собственное описание `task`-тула (`GET /experimental/tool`) обещает «for background
tasks, you will be notified automatically when the result is ready» — но параметра
`background` в JSON-схеме тула нет, и живьём поведение строго блокирующее. Обещание в тексте
инструмента не подтверждено ни одним доступным путём.

## 4. Есть ли у субагента поле ввода

**ЗАМЕРЕНО живьём (tmux PTY).** В основной сессии текст, набранный во время работы воркера,
сразу виден в рамке `┃  Ask anything…`. Переключился на дочернюю сессию (`ctrl+x`, `Down` —
подсказка из UI `ctrl+x down view subagents`): внизу экрана — голая `┃` без плейсхолдера и без
рамки ввода; набрал `can I type here` — на экране НИЧЕГО не появилось (ни в этой панели, ни
после возврата в родителя). Живое подтверждение issue #6896 («intentional change»), не только
по тексту мейнтейнера.

## 5. Home/End в поле ввода

**ЗАМЕРЕНО живьём (tmux PTY, дефолтный `tui.json`, без правок).** Ввёл `HELLOWORLD`, `Home`,
`Z` → результат `HELLOWORLDZ` (курсор НЕ переместился в начало, Home молча проглочен, не видно
и скролла истории — экран не изменился). `End`+`Y` → `HELLOWORLDZY` — тоже без эффекта
(ожидаемо, т.к. курсор и так был в конце). Конфликт с историей воспроизведён (Home не работает
как редактирование строки), хоть видимого скролла экрана в этой сессии (короткая история) не
случилось.

**С обходом владельца — ЗАМЕРЕНО, не по докам.** Применил `tui.json` (`messages_first:"none"`,
`messages_last:"none"`) в НОВОМ TUI-процессе (тот же контейнер, тот же ключ). Тот же тест:
`HELLOWORLD`→`Home`→`Z` → **`ZHELLOWORLD`** (курсор реально ушёл в начало строки). Далее
`End`→`Y` → **`ZHELLOWORLDY`** (курсор ушёл в конец). Обход из #27661 подтверждён живым нажатием
клавиш, а не только тем, что конфиг грузится — закрывает пробел из `11-cand-opencode.md`
(«живого TTY не было»).

## Итог: что подтвердилось, что нет

- **Досылка не прерывает** — подтверждено (ПО ДОКАМ → ЗАМЕРЕНО, тот же результат).
- **Субагент блокирует главную сессию** — подтверждено живьём (было ПО ДОКАМ/issues, теперь
  ЗАМЕРЕНО дважды, включая точный тайминг).
- **У субагента нет поля ввода** — подтверждено живьём (было ПО ДОКАМ, теперь ЗАМЕРЕНО).
- **Home/End ломаются** — подтверждено в дефолте; **но обход владельца реально работает**,
  живым нажатием клавиш (было "не проверено", теперь ЗАМЕРЕНО — рабочий фикс).
- **Не воспроизвелось / оказалось не так, как в инвентаре:** «нет самолечения от вечного
  зависания» — НЕВЕРНО как категоричное заявление. У opencode ЕСТЬ дефолтный жёсткий потолок
  на bash-tool-call (120с), эмпирически не документированный в issues про steering (те issues
  — про очередь сообщений, а не про потолок исполнения) — он практически закрывает боль
  владельца тем же способом, что и у Qwen Code, просто раньше не был измерен.
