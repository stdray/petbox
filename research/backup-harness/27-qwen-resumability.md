# Qwen Code 0.23.0 — продолжаемость субагента (по коду)

Дата: 2026-09-08 | Исполнитель: Claude Sonnet 5, petbox-worker | Метод: чтение
кода клона `D:/my/prj/_analysis/repos/qwen-code` (HEAD `cffc4049`, 2026-09-08).
Живой прогон НЕ делался — три вопроса ниже разрешились однозначно по коду,
включая ветку после отмены (сама область retention/terminal-статуса видна
целиком в `background-tasks.ts` без нужды воспроизводить гонку живьём).
Пометка **ПО КОДУ** — не «ЗАМЕРЕНО», отдельная категория см. `40-decisions.md`.

## 1. Идентификатор — ЕСТЬ, с оговоркой (только для фонового пути)

Делегирование субагентам есть и устроено богаче, чем у остальных кандидатов:
`packages/core/src/tools/agent/agent.ts` (4438 строк), фон/форк/foreground —
три разных пути спавна. Топ-уровневые обычные субагенты по умолчанию идут в
фон (`run_in_background` по умолчанию `true`, `agent.ts:753-757,845-894`).

Для фонового пути идентификатор ОБЯЗАТЕЛЕН и виден модели дословно в ответе
на сам спавн — `agent.ts:3865-3869`:
`` task_id: ${hookOpts.agentId} (internal ID — do not mention to the user.
Use send_message to continue this agent, or task_stop to cancel.) ``,
плюс явный запрет повторного спавна: «Do not treat the agent as cancelled or
relaunch it because the notification has not arrived yet — the result comes
under the original task_id» (`agent.ts:3868`). Ровно та формулировка, которой
не хватило оркестратору opencode.

Оговорка: для foreground-вызова (`run_in_background: false`, синхронный,
блокирующий) task_id моделью не получаем вовсе — ответ содержит только
текст результата субагента (`agent.ts:4196-4198`), и такая запись
дополнительно исключена из `list_agents` фильтром `entry.isBackgrounded`
(`packages/core/src/tools/list-agents.ts:44`). Это осознанный дизайн (msg
уже вернулся инлайн, продолжать нечего через этот канал), но означает: ось
«идентификатор всегда виден» верна только для пути, которым реально
пользуются для «спавнил и пошёл дальше» (фон) — не для inline-вызова.

## 2. Возврат в сессию — ЕСТЬ, с сохранением контекста

`packages/core/src/tools/send-message.ts`, маршрут «Route 1: background task
by task_id» (строки 222-365):
- `running` (222-337): сообщение встаёт в очередь, доставляется на границе
  тул-раунда (`registry.queueMessage`, строка 341); модель получает явный
  текст «Do not relaunch the task while waiting» (строка 362).
- `paused` (269-289): `config.resumeBackgroundAgent(task_id, message)` —
  восстановленная задача продолжается с этим сообщением как первой
  continuation-инструкцией, контекст сохранён.
- `completed` (295-326): сначала пробуется `registry.continueResidentAgent`
  — тот же живой чат-раннтайм, наивысшая сохранность контекста; если раннтайм
  не резидентный (например, после рестарта сессии), `reviveCompletedBackgroundAgent`
  поднимает агента заново ИЗ СОХРАНЁННОГО ТРАНСКРИПТА, а не с чистого листа.

Это прямой и рабочий аналог `SendMessage`/`Resuming agent` из Claude Code
(см. `50-precard-subagent-resumability.md`), в отличие от opencode, где
`task_id` не передавался вовсе и продолжения не было в принципе.

## 3. После отмены — ЕСТЬ ОГОВОРКА: терминально для продолжения, но НЕ молча

`packages/core/src/tools/task-stop.ts:74-89`: отмена работающего агента —
`agentRegistry.cancel(taskId)`; ответ модели явно обещает, что финальный
task-notification с реальным (частичным) результатом ещё придёт — не голое
«cancelled» (комментарий и текст ответа, `task-stop.ts:78-89`).

`packages/core/src/agents/background-tasks.ts`, метод `cancel()` (933-967):
статус переходит в `'cancelled'` — ЗАПИСЬ В РЕЕСТРЕ НЕ УДАЛЯЕТСЯ, `agentId`
остаётся валидным ключом. `finalizeCancelled()` (995-1010) всё равно
выставляет `entry.result = partialResult` и шлёт notification — накопленная
работа не выбрасывается молча, как это было в замеренном боевом случае opencode.

Но продолжить именно ЧЕРЕЗ send_message после отмены нельзя: в
`send-message.ts:328-337` статус `'cancelled'` не входит ни в `paused`, ни в
`completed`, ни в `running` — падает в ветку «Cannot send messages to stopped
tasks», ошибка `SEND_MESSAGE_NOT_RUNNING`, а не тихая новая сессия под тем же
task_id и не потерянный id.

Итог по оси 3: ОТМЕНА ТЕРМИНАЛЬНА для продолжения (та же практическая точка,
что у opencode) — НО id не теряется, ошибка явная и типизированная, а
частичный результат долетает. Ключевой боевой дефект («97 toolcalls
выброшены молча, id не возвращается вовсе») здесь по коду не воспроизводится:
модель узнаёт о невозможности продолжения сразу и по названному task_id,
а не спавнит дубликат вслепую.

## Что это значит для схемы «оркестратор + воркеры»

Для дефолтного (фонового) пути делегирования Qwen Code несёт тот же контракт,
что и Claude Code: id обязателен, виден, возврат штатный, отмена — известная,
не тихая терминальность. Гейт из `50-precard-subagent-resumability.md`
(«не спавнить повторно без id») для Qwen Code можно писать НЕ с нуля — сам
харнесс уже отказывает в продолжении отменённой задачи текстовой ошибкой;
оркестратору достаточно не игнорировать эту ошибку и не спавнить дубликат
вручную. Единственное, что стоит держать в виду при внедрении: не заворачивать
дальнейшую работу в inline (`run_in_background: false`) там, где ожидается
возможность вернуться позже — тем путём id не выдаётся и не отслеживается.
