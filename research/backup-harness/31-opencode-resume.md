# Замер: описание resume-механики агентом vs код opencode 1.18.29

Репозиторий `anomalyco/opencode`, тег `v1.18.29` (клон в
`D:/my/prj/_analysis/repos/opencode`, ветка `analysis-1.18.29` = tags/v1.18.29).
Ключевой файл: `packages/opencode/src/tool/task.ts`.

## П.1 — существует ли `task_id` как параметр

Утверждение агента: не заявлял отсутствия параметра, но всё построил на том, что
«ни разу не передавал `task_id`».

Код: `task.ts:47-50` — `task_id: Schema.optional(Schema.String)` в `BaseParameterFields`,
описание модели дословно: *"pass a prior task_id and the task will continue the same
subagent session as before instead of creating a fresh one"*. Параметр реально в
сигнатуре, JSON-schema отдаётся модели (`task.ts:366`, `ToolJsonSchema.fromSchema`).
Дополнительно `task.txt:14` (системное описание тула): *"The output includes a task_id
you can reuse later to continue the same subagent session"* и *"unless you provide
task_id to resume"*.

**Вердикт: ВЕРНО.** Параметр существует, модель знала о нём из описания тула (не
выдумала пункт (а) целиком) — просто не передавала.

## П.2 — механизм resume: что называется, что принимает, при каких статусах

Код: `task.ts:136-138`:
```
const session = params.task_id
  ? yield* sessions.get(SessionID.make(params.task_id)).pipe(Effect.catchCause(() => Effect.succeed(undefined)))
  : undefined
...
const nextSession = session ?? (yield* sessions.create({...}))
```
Резолюция — ЧИСТО по существованию сессии в `Session.Service` (durable store). **Нет
проверки статуса фоновой job** (`running`/`completed`/`error`/`cancelled`) на этом
пути вообще — ни здесь, ни в `background-job.ts` (`get`, `list`, `cancel` — просто
читают/пишут map по id, никакой из них не участвует в решении «резолвить сессию по
task_id или нет»). Job-registry (`background-job.ts:113-119`, коммент в коде) explicitly
process-local/non-durable и относится к ОТСЛЕЖИВАНИЮ фоновой задачи, а не к самой сессии.

**Вердикт по утверждению «resume работает только для живой или завершённой задачи»:
НЕ ПОДТВЕРЖДЕНО КОДОМ.** Единственный гейт — нашёлся ли `sessions.get(task_id)`.
Сессия отменённой job из стора не удаляется (см. п.3), значит резолвится наравне с
любой другой.

## П.3 — что происходит при отмене

`session/prompt.ts:152-155`: `cancel(sessionID)` → `state.cancel(sessionID)` — это
`SessionRunState.Service`, обрывает ИСПОЛНЕНИЕ, не трогает запись сессии.
`background-job.ts:337-358` (`cancel`): помечает job `status: "cancelled"` в
in-memory `Map`, закрывает `Scope`. Сессия (объект в `Session.Service`, отдельное от
job хранилище) не удаляется НИГДЕ в этом пути.

Но есть реальная асимметрия в `task.ts:338-340` (foreground-ветка, `acquireUseRelease`):
```
if (result?.status === "error") return yield* Effect.fail(new Error(result.error ?? "Task failed"))
if (result?.status === "cancelled") return yield* Effect.fail(new Error("Task cancelled"))
```
Ветка `"error"` разворачивает `result.error`, который для ошибок из `runTask()`
СОДЕРЖИТ id (`task.ts:218,222`: `` `Subagent failed (task_id: ${nextSession.id})` ``).
Ветка `"cancelled"` — жёстко заданная строка `"Task cancelled"`, **id нигде не
подставляется**. Это единственное реальное расхождение, которое буквально совпадает с
самоотчётом агента дословно («результат возвращается как «Task cancelled», а не как
готовый task»).

**Вердикт: ЧАСТИЧНО ВЕРНО, но не в смысле агента.** Id не пропадает из системы (сессия
жива в сторе), он не попадает только в текст этого конкретного возврата ошибки — узкий
баг рендеринга результата, а не архитектурная невозможность resume после отмены.

## П.4 — сходится ли самоотчёт агента с кодом

| пункт агента | код | вердикт |
|---|---|---|
| (а) не передавал `task_id` → новая сессия | `task.ts:136-138,156-157`: без `task_id` — всегда `sessions.create()` | ВЕРНО |
| (б) resume только для live/completed, отмена терминальна «в принципе» | нет проверки статуса job на пути resolve по `task_id` (`task.ts:136-138`); сессия отменённой job не удаляется | ВЫДУМАНО — конкретно этого ограничения в коде нет |
| (в) id отменённой задачи «не сохраняется» | сохраняется НА УРОВНЕ СЕССИИ/СТОРА; не сохраняется только в тексте ОДНОГО конкретного error-возврата (`task.ts:340`) | ЧАСТИЧНО — верное наблюдение симптома, неверное обобщение причины |

**Итог: ЧАСТИЧНО.** Агент не соврал про сам параметр (знал о `task_id` из описания
тула — против сильного сигнала «параметра нет вовсе») и верно опознал симптом (текст
«Task cancelled» без id — реально то, что вернул код). Но объяснение механики —
«resume в принципе невозможен после отмены, id отменённой задачи не сохраняется» —
придумано: такого ограничения нет ни в схеме параметра, ни в резолве сессии, ни в
job-реестре. Правдоподобная реальная причина: одна конкретная ветка ошибки не
прокидывает id в текст, оркестратор просто не имел строки с id под рукой — и это
задним числом одето в теорию о принципиальной невозможности, а не проверено.

## Что не проверено

Не проверялось, попадает ли `nextSession.id` в контекст модели другим путём (через
`ctx.metadata` на `task.ts:192-195`, до ожидания результата), т.е. мог ли оркестратор
технически иметь id раньше, даже если финальный текст ошибки его не содержит.

## Следствие для оси «Продолжаемость субагента»

Дефект харнесса локальный: `task.ts:340`, ветка `"cancelled"`, не прокидывает
`task_id` в текст ошибки (в отличие от `"error"`, `task.ts:339`) — не «resume после
отмены невозможен», а «id может не попасть в свой же текст»; сессия резолвится по
`task_id` без проверки статуса. Для матрицы: opencode не в кандидатах (`40-decisions.md`,
D3) — чинить незачем; ценность замера методологическая: самоотчёт о результате (текст
без id) точен, самоотчёт о механике — придуман. Правило «самоотчёту модели о харнессе
не верить без проверки по коду» подтверждено, не опровергнуто.
