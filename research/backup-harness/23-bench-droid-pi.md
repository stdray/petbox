# Стенд досылки: Droid и pi

Дата: 2026-09-08 | Исполнитель: Sonnet 5, petbox-worker | Всё в Docker (node:20/22-bookworm-slim),
ключ — DeepSeek из `~/.factory/settings.json.customModels` владельца (baseUrl/сырой ключ, не печатался),
контейнеры удалены по завершении. Стенд и ловушка (`hang.sh`/`hang30.sh`) — по `22-steering-bench.md`
дословно; термины — по `01-legend.md`.

## Droid — версия **0.213.0** (контейнерная, НЕ 0.170.0 из прошлого замера)

Сначала санити-чек: обычный `droid exec -m custom:DeepSeek-V4-Flash-1 "Say hi..."` отработал (ответ
получен) — сеть/ключ/модель рабочие, проблема ниже локализована именно в input-format.

| механизм | команда | что сделано | исход |
|---|---|---|---|
| `stream-json` | `droid exec --input-format stream-json -o stream-json --auto high -m custom:DeepSeek-V4-Flash-1 --cwd /work < msg.json` | payload `{"type":"user","message":{"role":"user","content":[{"type":"text","text":"Run ./hang30.sh..."}]}}` (канонический claude-code-стиль) | CLI печатает предупреждение "stream-json is deprecated"; сообщение отклонено `{"type":"error","message":"Only 'user' messages are accepted via stdin."}` — БУКВАЛЬНО ТА ЖЕ строка ошибки, что и на 0.170.0 в прошлом замере, для сообщения, которое по типу и есть 'user'. Механизм НЕ ЗАВОДИТСЯ, воспроизведено на двух версиях |
| `stream-jsonrpc` | `droid exec --input-format stream-jsonrpc -o stream-jsonrpc --cwd /work < init.json`, `init.json` = `{"jsonrpc":"2.0","id":1,"method":"droid.initialize_session","params":{"machineId":"m","cwd":"/work","disableBuiltinSkills":true}}` (метод и форма — дословно из docs.factory.ai/droid-exec/overview, JP-зеркала и deepwiki, все три источника совпали) | JSON провалидирован Python'ом (валиден, однострочный, без BOM) перед отправкой | Каждый раз `{"type":"response","id":null,"error":{"code":-32700,"message":"Invalid JSON-RPC message"}}` — parse-уровня отказ на буквальном примере из докoв. Пробовал варианты конверта (`"type":"request"`, добавление `factoryApiVersion`/`factoryProtocolVersion`) — тот же результат |

Дополнительно: поставил официальный `@factory/droid-sdk` (npm) — низкоуровневый клиент, который сам
собирает `stream-jsonrpc` под капотом. Он потребовал `FACTORY_API_KEY` (даже для custom-модели —
это ДРУГОЙ ключ, не DeepSeek); с фиктивным значением сессия стартовала, но модельный запрос упал
`401` — SDK, судя по всему, требует настоящий Factory-аккаунт даже на custom-модели, что вне границ
задачи (не ставить аккаунт). Также подтверждено по докам SDK: `DroidSession` в Node-рантайме не
даёт способа вставить сообщение В СЕРЕДИНЕ хода — только `interrupt()` (жёсткий обрыв хода,
`subtype:"interrupted"`), т.е. даже официальный клиент не описывает канал «дописать без обрыва».

**Различение по спецификации:** `stream-json` — механизм НЕ РАБОТАЕТ (подтверждено дважды на разных
версиях идентичной ошибкой, вендор сам пометил deprecated). `stream-jsonrpc` — Я НЕ СМОГ ЕГО
НАСТРОИТЬ (три независимых источника доков дали один и тот же нерабочий пример; не доказано, что
метод в принципе недостижим, только что бюджет угадывания исчерпан).

**Исход для Droid: НЕ ДОХОДИТ** (ни один механизм не довёл диалог даже до первого хода — контрольный
30-секундный прогон поэтому неприменим, различать «границу» не от чего). Настраиваемый таймаут на
tool-call — не проверялся содержательно, т.к. ни один turn не запустился.

## pi — версия **0.85.1** (npm latest; локальная 0.78.0 требует Node <22, здесь Node 22.23.2)

Провайдер: нативный `deepseek` (`DEEPSEEK_API_KEY` = тот же сырой ключ), модель `deepseek-v4-flash`.
Команда: `pi --mode rpc --no-session --provider deepseek --model deepseek/deepseek-v4-flash --tools bash`
(права по умолчанию «all permissions» — `--auto`-флага у pi нет и не нужен). Досылка — RPC-команда
`steer`: stdin `{"type":"steer","message":"...","id":"steer-1"}`.

Первая попытка провалилась методологически: с доступным `read`-инструментом DeepSeek САМ читал
`hang.sh`, распознавал бесконечный цикл и подстраховывался `timeout 35 ./hang.sh` — ловушка не
воспроизводилась (агент не «застревал», а сознательно ограничивал вызов). Исправлено: `--tools bash`
(без `read`) + явный запрет добавлять timeout в промпте → агент выполнил `./hang.sh` буквально, без
обёртки и без параметра `timeout` у самого tool-call — вот тут ловушка воспроизвелась по-настоящему.

### Контрольный прогон (`hang30.sh`, 30с) — граница подтверждена

| t | событие |
|---|---|
| 3.16s | tool_execution_start `bash`, команда `./hang30.sh` |
| 10.01s | отправлен `steer` → тут же `queue_update` (сообщение встало в очередь), НЕ доставлено как ход |
| 33.16s | `tool_execution_end` (ровно ~30с работы скрипта) → `turn_end`/`turn_start` → ТОЛЬКО ТЕПЕРЬ `message_start` с ролью user и текстом STOP |

Т.е. `steer` реально ждёт завершения tool-call'ов текущего хода — доки не врут, это измерено, не
процитировано.

### Реальный вис (`hang.sh`, бесконечный) — граница НЕ наступает

| t | событие |
|---|---|
| 1.49s | tool_execution_start `bash`, команда буквально `./hang.sh` (без `timeout`) |
| 15.02s | отправлен `steer` → `queue_update` (встал в очередь), процесс продолжает висеть |
| 15.02s…210.09s (195с ожидания, > 3 минут по спецификации) | НИЧЕГО: ни `tool_execution_end`, ни `turn_end`, ни доставки сообщения как хода — полное молчание |
| 210.09s | жёсткий килл стенда (не харнесса) |

**Исход для pi: НЕ ДОХОДИТ**, и это доказанная граница, а не догадка — идентичный сценарий с
конечным (30с) скриптом доставил сообщение ровно на границе хода, тот же сценарий с бесконечным —
не доставил НИКОГДА за 3+ минуты. Настраиваемого таймаута на tool-call у pi по умолчанию НЕТ:
`bash`-инструмент принимает необязательный аргумент `timeout`, но это решение МОДЕЛИ на каждый вызов
(как и было видно в первой, забракованной попытке — модель сама поставила `timeout:40`), harness
собственного дефолтного лимита не навязывает.

## Вывод: закрывает ли боль владельца

Ни один кандидат её не закрывает.

- **Droid**: механизм досылки не удалось даже завести (stream-json — сломан/deprecated, воспроизведено
  на двух версиях; stream-jsonrpc — не настроилось за отведённый бюджет, включая попытку через
  официальный SDK). Вопрос «доходит ли сообщение при вечном висе» остался непроверяемым — до него
  дело не дошло.
- **pi**: механизм заведён и измерен ЧЕСТНО (не по докам) — `steer` реально работает и реально
  доставляет сообщение НА ГРАНИЦЕ хода (control-прогон это доказал), но при настоящем бесконечном
  висе внутри tool-call сообщение НЕ ДОХОДИТ вообще, что и предсказывала гипотеза владельца из
  `13-cand-pi-aider.md`: «доставляется после завершения текущих tool-calls» — для вечно висящего
  вызова это «никогда». Боль владельца (воркер встрял, сообщение уже в очереди, агент не видит)
  этим механизмом НЕ закрывается — ни частично, ни полностью.
