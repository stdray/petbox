# Кандидат: Claude Code (baseline, не «кандидат на замену»)

Версия `claude.exe 2.1.263`, установлена и авторизована подпиской владельца ДО этого
замера. Весь живой прогон — в `D:/tmp/cc-bench` (git-репозиторий не создавался),
`--setting-sources project` (свой `.claude/settings.json` в этой папке, глобальный
`~/.claude/settings.json` и `~/.claude.json` НЕ читались и не менялись). Авторизация не
трогалась — использована штатная сессия владельца как есть. Каталог убран по завершении.

## 1. Раздаваемость (BYOK) — Л

Не поддерживается для произвольного провайдера «из коробки». `ANTHROPIC_BASE_URL` +
`ANTHROPIC_API_KEY` меняют эндпоинт, НО протокол должен быть Anthropic Messages API.
Живой прогон на ключе владельца (`~/.factory/settings.json`, не печатался): запись
`deepseek-v4-flash` с `"provider":"anthropic"` — `claude -p --model deepseek-v4-flash`
вернул `rc=0`, ответ получен. Запись `glm-5.2` с `"provider":"generic-chat-completion-api"`
(голый OpenAI-формат) — `rc=1`, `"There's an issue with the selected model"`. Строк
`OPENAI_API_KEY` в бинаре нет вовсе. Вывод: раздаваемость есть, но ТОЛЬКО на
Anthropic-протокол (сам Anthropic, Bedrock/Vertex/Foundry, чужой прокси-транслятор) —
обычный OpenAI-совместимый провайдер напрямую не подключается. Это и есть слабость.

## 2. Автономность от подписки — Д

Живой тест невозможен (подписку не отключить). По флагам: `setup-token` требует
подписку; `ANTHROPIC_API_KEY`/`apiKeyHelper` — независимый от неё путь (оплата по
токенам), задокументирован в `--bare`. Граница: закончилась подписка — харнесс жив на
API-ключе, меняется только тарификация, не работоспособность.

## 3. MCP — Л

Тривиально да, и измерено самим фактом: эта же диалоговая сессия — рабочий пример
(`mcp__petbox__*` — нативная для Claude Code схема имён MCP-инструментов). Отдельно в
изолированной папке подтверждено наличие команд `claude mcp add/list` в `--help`.

## 4–5. Хуки: SessionStart (инжект) и SessionEnd (транскрипт) — Л, включая headless

`SessionStart` → команда, вывод JSON `{"hookSpecificOutput":{"additionalContext":...}}`.
`SessionEnd` → на stdin JSON с `transcript_path`, файл на момент вызова уже дописан.
Живой прогон `claude -p` (headless): маркер `CANON-MARKER-XYZ789` инжектирован и виден
модели в первом же ходе; `SessionEnd` получил `transcript_path` на реальный `.jsonl`
(22 строки на момент хука). **В headless оба хука работают** — в отличие от дыры Qwen
Code (там `SessionEnd` в `-p` не срабатывает вовсе). Дополнительно оба хука сработали и
в интерактивном PTY-прогоне (см. §7) — маркер попал в контекст и там же.

## 6. Делегирование — К

`Task` — нативный, отдельный от MCP инструмент (виден в `system:init` списке `tools`).
Роль/модель субагента независимы от роли/модели родителя. Блокировка — как у любого
tool-call: `Task` синхронен для хода, но длинные вызовы уходят в фон (см. §7) —
оркестратор не подвисает намертво.

## 7. Досылка — главная ось. Стенд по `22-steering-bench.md`, PTY (`node-pty`, реальный TTY)

Бинарь: `claude.exe 2.1.263`. Запуск: `claude --model sonnet --setting-sources project
--permission-mode bypassPermissions` в PTY; досылка — реальный ввод текста в поле (не
API, не `stream-json`: там повторный `type:user` во время хода вообще не был подхвачен
— отдельная, менее репрезентативная находка, в файл не выношу как основной результат).

**Контрольный прогон (`hang30.sh`, 30 с) — обязателен по спецификации, сделан.**
Сообщение отправлено на 15-й секунде хода, пока шёл `$ ./hang30.sh` (счётчик
`3s…10s…30s`). Всё это время в UI: «STOP… · Press up to edit queued messages» — сообщение
принято в очередь, но не влияет на работающий вызов. Обработано ТОЛЬКО после его
завершения на ~44 с (`Ran 1 shell command` → тут же ответ на STOP). **Исход: НА ГРАНИЦЕ**,
граница доказана (не поломка — на живом коротком вызове доставка происходит, просто не
раньше конца tool-call).

**Основной прогон (`hang.sh`, бесконечный).** Первая попытка дословной формулировкой
(«Run ./hang.sh and wait for it to finish...») ловушка НЕ воспроизвелась: агент сперва
читает файл (`Read`), опознаёт `while true` и останавливается на интерактивном выборе
(«запустить с таймаутом» / «пропустить» / «почини скрипт» / …), так и не войдя в
блокирующий вызов — сам факт достоин отдельной строки в реестр решений. Повторный прогон
с явным «выполни напрямую, не спрашивай» довёл до реального `$ ./hang.sh`: агент сам
объявил «wait up to the tool's max timeout» (то есть выставил таймаут вызова сам, не
дефолт), досылка отправлена на 22-й секунде (ещё в фазе размышления, ДО старта
`Bash`) — тем не менее к моменту убийства прогона на 170 с (< 600 000 мс — верхний
предел `Bash`) сообщение так и осталось в очереди, `hang.sh` не был убит и результат по
STOP не пришёл. **Исход на окне ≤170 с: НЕ ДОХОДИТ** (совпадает с четырьмя другими
кандидатами из `40-decisions.md`).

**Ответ на наблюдение владельца (момент отправки: думает / зовёт tool / пишет ответ).**
Разницы не найдено: сообщение во время «thinking» (до старта `Bash`) и во время самого
`Bash`-вызова в контрольном прогоне — оба ждут границы ХОДА целиком (включая вложенный
tool-call), а не границы фазы генерации. «Быстрее во время мышления» не подтвердилось.

## 8. Таймаут на tool-call — К + Л

Есть и включён по умолчанию: `BASH_DEFAULT_TIMEOUT_MS=120000` (2 мин),
`BASH_MAX_TIMEOUT_MS=600000` (10 мин, потолок) — обе переменные окружения, найдены в
бинаре и совпадают с текстом ошибки харнесса. **Важная оговорка**: это не жёсткий
недоговариваемый потолок как у Qwen (120 с) — модель сама вправе запросить таймаут
вплоть до 600 000 мс на конкретный вызов (что и произошло в основном прогоне §7,
поэтому в окне ≤170 с принудительного `ТАЙМАУТ ХАРНЕССА` не случилось). Отдельно есть
`CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT`/`MCP_TIMEOUT` — тот же механизм, но для MCP-вызовов.

## 9. Продолжаемость субагента — К (по строкам бинаря, три вопроса раздельно)

(а) id обязателен: `SubagentStop` несёт `agent_id`, `agent_transcript_path`, `agent_type`.
(б) возврат в контекст поддержан штатно: строки `subagent_resume_transcript_missing`,
`«Fixed the main agent not being told when you resume a subagent you had stopped from its
transcript view»` — то есть возврат идёт через транскрипт субагента, а не заново.
(в) после отмены НЕ терминально для обычных субагентов — резюм остановленного субагента
описан как нормальный (ранее баганый) путь. Исключение: `«Cannot resume fork agent»` —
fork-субагенты резюмировать нельзя. Живого прогона не делал (риск задеть рабочую сессию
владельца через реальный Task) — оценка К, не Л.

## 10. Home/End — Л

PTY-тест: `abcdef` → Home → `X` → End → `Y`. По снимкам перерисовки поля ввода `X`
вставился ПЕРЕД `abcdef`, `Y` — ПОСЛЕ, порядок не нарушен, скролла истории не случилось.
Работает корректно. Перенос длинной строки не проверялся (не хватило бюджета времени).

## Поправка владельца, 2026-09-08 (замер в бою)

Дописано оркестратором со слов владельца. Инвентарь выше не переписан.

**У Claude Code при ИСТЁКШЕЙ подписке не работает даже BYOK** — проверено владельцем на
практике. Это прямо противоположно поведению Factory Droid, где `droid exec` на
custom-моделях со своими ключами продолжает работать после окончания подписки (замерено
независимо, см. `02-snapshot.md` и `20-sandbox.md`).

Следствия для матрицы, обе строки исправлены:

- **Живёт без подписки: НЕТ.** Раньше стояло «не проверено» — исполнитель не мог это
  выяснить, не отключая подписку владельца. У владельца замер есть.
- **Раздаваемость: НЕТ**, а не «с оговоркой». Тот факт, что BYOK технически работает на
  Anthropic-протоколе, ничего не даёт третьему лицу без активной подписки: инструмент у
  него просто не запустится. Оговорка про протокол остаётся верной, но описывает условия
  ВНУТРИ действующей подписки, а не возможность передать среду.

Это и есть исходная причина всего исследования, сформулированная владельцем в самом
начале: при истечении подписки отваливается всё, даже с чужими провайдерами.
