## 1. Потолок исполнения tool-call — ПЕРЕПРОВЕРЕНО, прежний ❌ был неверен

**По коду.** У Codex это НЕ «kill после N мс», а другой примитив — «yield и вернуть
управление, процесс живёт дальше в фоне»:
- `pub(crate) const MAX_YIELD_TIME_MS: u64 = 30_000;` — жёсткий клэмп
  (`core/src/unified_exec/mod.rs:77`, применяется `clamp_yield_time`:216: `.clamp(MIN_YIELD_TIME_MS, MAX_YIELD_TIME_MS)`).
  Модель управляет `yield_time_ms` за вызов, но харнесс всегда сжимает его в
  `[250мс, 30000мс]` — модель не может попросить больше 30с ожидания на ОДИН вызов.
- Дефолт при отсутствии параметра — 10000мс (описание тула,
  `core/src/tools/handlers/shell_spec.rs:29-31`).
- Процесс НЕ убивается по истечении: он продолжает жить как фоновая сессия
  (`unified_exec`), адресуемая по id для последующего опроса/записи в stdin.
- Отдельно есть `DEFAULT_EXEC_COMMAND_TIMEOUT_MS: u64 = 10_000` (`core/src/exec.rs:61`) —
  это дефолт для другого пути (write-stdin/oneshot внутри уже открытой сессии), не общий
  потолок.

**ЗАМЕРЕНО живьём (`hang.sh` = `while true; do sleep 1; done`, `codex exec --json`,
`-s danger-full-access`).** Три независимых прогона показали ОДИН и тот же паттерн:
`item_2 command_execution` стартует, дальше модель САМА каждые ~31-32с получает контроль
назад и печатает `agent_message` вида «still running, waiting» (тайминги одного прогона:
старт 922.403, опросы 954.258 / 985.920 / 1017.994 — интервалы 31.86с/31.66с/32.07с,
согласуется с клэмпом в 30000мс + оверхед). Харнесс возвращает управление модели, как и
предсказывает код; вечный процесс не убивается, а продолжает жить (`ps aux` внутри
контейнера показывал живой `hang.sh` пока не убит вручную).

**Но: внешняя досылка (`codex queue --thread <id> --message ...`) всё равно НЕ доставляется**,
пока агент сам не завершит ВЕСЬ ход (`turn`). В прогоне с очередью: `queue` отправлен в
998.048с (внутри окна между опросами 985.920 и 1018с), следующий `agent_message` в 1017.994с
не содержит НИКАКОЙ реакции на очередь — тот же шаблонный текст «still waiting». Причина по
коду: каждый внутренний опрос — это НЕ новый `turn` (единственный `{"type":"turn.started"}`
на весь прогон), а внешняя очередь по `multi_agents_spec.rs:168-232` доставляется на
границах ТУРНА/сообщения, а не на границе отдельного yield-опроса. Раз модели явно сказано
«жди завершения», турн не заканчивается никогда (`hang.sh` вечен) — и 187с из `24-bench-*`
воспроизведены как частный случай общей картины: очередь ждёт границы турна, а турн-обёртка
вокруг серии yield-опросов границей не считается.

**Вывод для матрицы:** старая ❌ («потолка нет вовсе») — НЕВЕРНА. Потолок ЕСТЬ, жёстко
зашит (30000мс на вызов), встроен и всегда включён (не опция), но это ceiling управления,
а не ceiling жизни процесса — сам разболтанный процесс не убивается. Для боли владельца
(«застрявший воркер + сообщение в очереди») это ближе к Codex-у из `16-cand-codex-qwen.md`
(«НЕ закрывает»), но по другой причине, чем считалось: не потому что харнесс не возвращает
управление, а потому что возврат управления происходит ВНУТРИ одного турна, куда внешняя
очередь не долетает.

## 2. Продолжаемость субагента — три вопроса раздельно

Делегирование у Codex есть («spawn_agent»/multi-agent v1 и v2 версии тулов), заменять
нечем спрашивать — есть.

**(а) Выдаётся ли id при спавне, обязателен ли.** Да и да. Выходная схема
`spawn_agent_output_schema_v1`: `"required": ["agent_id", "nickname"]`
(`core/src/tools/handlers/multi_agents_spec.rs:390-399`) — `agent_id` обязателен в ответе
инструмента на каждый спавн.

**(б) Можно ли по id вернуться в ТУ ЖЕ сессию с сохранением контекста.** Да, явным
инструментом `resume_agent`: «Resume a previously closed agent by id so it can receive
send_input and wait_agent calls» (`multi_agents_spec.rs:242-260`). Обработчик
(`core/src/tools/handlers/multi_agents/resume_agent.rs:90-122,191-212`) при статусе
`NotFound` вызывает `agent_control.resume_agent_from_rollout(...)` — восстановление ИЗ
СОХРАНЁННОГО НА ДИСКЕ rollout-файла той же сессии, не с нуля. Это отличается от opencode
(`31-opencode-resume.md`): там `task_id` был в схеме, но моделью не использовался; здесь
явный тул с этой единственной целью существует и код проверяет rollout, а не просто
наличие в сторе.

**(в) Что происходит после ОТМЕНЫ.** Отмена НЕ терминальна. `interrupt_agent`
(`core/src/tools/handlers/multi_agents_v2/interrupt_agent.rs:71-99`) останавливает только
текущий ход агента (`agent_control.interrupt_agent`), не удаляет и не закрывает его.
Юнит-тест `multi_agent_v2_list_agents_keeps_interrupted_resident_agents`
(`core/src/tools/handlers/multi_agents_tests.rs:1555-1624`) прогоняет ровно эту
последовательность: spawn → interrupt → list_agents — и агент ОСТАЁТСЯ в списке резидентных
(`result.agents.len() == 2`, обе записи на месте). Живой прогон не делал (бюджет), но это
юнит-тест на реальном коде обработчиков, не самоотчёт модели — по границам задачи
приравнено к ЗАМЕРЕНО (чтение кода с file:line).

## 3. Перевод C→L (дёшево, всё ЗАМЕРЕНО живьём в контейнере)

**MCP с нашим сервером.** `config.toml`: `[mcp_servers.petbox]`, `url = "…/mcp"`,
`env_http_headers = { "X-Api-Key" = "PETBOX_API_KEY" }` (значение хедера тянется ИЗ ENV,
литерал не пишется — формат `McpServerTransportConfig::StreamableHttp.env_http_headers`,
`config/src/mcp_types.rs:557-559`). `codex mcp list` → `petbox … enabled`. Реальный вызов
`whoami` через `codex exec` вернул настоящий ответ сервера (`project":"$system"`, полный
список scopes) — не косвенно, инструмент реально исполнился в контейнере. В PetBox — только
чтение (`whoami`), как и требовалось.

**Hook-инжект (SessionStart) — ЗАМЕРЕНО, headless.** `~/.codex/hooks.json`, `SessionStart` →
command-хук, печатает маркер в stdout + POST на локальный мок (`127.0.0.1:8085`, свой
`http.server`). **Без `--dangerously-bypass-hook-trust` хук в headless вообще не
выполняется** — ни файла на диске, ни запроса к моку, при этом `codex exec` завершается
успешно и НИЧЕГО не сообщает о непройденном trust-гейте (тихая дыра, аналогичная headless-
дыре у Qwen Code из `25-qwen-wiring.md`, но с рабочим обходом). С флагом — хук отработал:
файл `session_start_input.json` записан, мок получил POST с тем же телом. Маркер РЕАЛЬНО
попал в промпт модели: `grep` по rollout-транскрипту нашёл его как
`role":"developer","content":[{"type":"input_text","text":"PETBOX_CANON_MARKER_7f3a: …"}]` —
т.е. инжект долетает до модели как отдельное developer-сообщение (не просто лог). Оговорка:
прямой вопрос модели «процитируй маркер» дал `NO_MARKER` — по трассе reasoning модель ВИДЕЛА
маркер, но не признала его «дополнительным контекстом» по смыслу моего вопроса by её же
рассуждению — это огрех формулировки пробы/модели, не дефект доставки.

**Hook-транскрипт (SessionEnd) — ЗАМЕРЕНО, headless, та же оговорка про trust.** С флагом
хук получил `hook_event_name":"SessionEnd","reason":"other"` (подтверждает найденное по коду
в `16-cand-codex-qwen.md` — `reason` действительно всегда `"other"`) и `transcript_path`,
указывающий на реальный rollout-файл, который на момент хука уже содержит полную сессию.

**Headless вообще — единая находка для обоих хуков.** Дыра — не «хуки не работают headless»
(как у Qwen Code), а «хуки требуют persisted trust, для headless без интерактивного
подтверждения единственный путь — `--dangerously-bypass-hook-trust`» (сам флаг найден в
`codex exec --help`, поведение подтверждено живьём дважды: без флага — 0 срабатываний хуков
при успешном exit; с флагом — оба хука отработали).
