# Формат инвентаря сценариев (вторая волна) — читают воркеры G и H

## Зачем эта волна

Первая волна оценивала прототип по **нашим восьми формам спроса**, снятым с 12 задач.
Владелец указал на дефект этой рамки, и он справедлив: те 12 задач были перекошены в сторону
системы прав, поэтому «спрос» вышел узким и специфическим — вокруг атрибутов, деклараций
тенанта и злополучного числа 85. Оценивать инструмент по такому списку — значит мерить его
линейкой из собственных недавних совпадений.

Вторая волна переворачивает рамку: **строки таблицы задаёт РЫНОК, а не мы.** Смотрим, для каких
задач люди писали инструменты представления кода, как они себя позиционируют и на какие вопросы
пользователя предлагают ответы — пусть даже маркетингом. Наши восемь форм становятся ОДНОЙ
колонкой в этой таблице, а не её определением.

## Ключевое правило

**Сценарий формулируется словами продукта, а не нашими.** Если CodeQL продаёт «найти уязвимость
по потоку данных от источника к стоку» — так и пиши, не переводи это в «форму D5». Нормализация —
работа консолидатора, не твоя. Твоя работа — точность цитаты и честность про её статус.

## Статус каждого утверждения — обязателен

У каждой строки проставь один из четырёх:

| Статус | Что значит |
|---|---|
| `маркетинг` | заявлено на лендинге/в анонсе, без демонстрации |
| `док` | описано в документации с примером запроса или сценария |
| `демо` | есть воспроизводимый пример/туториал, который делает именно это |
| `замер` | кто-то (мы или третья сторона) измерил результат |

Смешивать нельзя. «Продукт умеет X» без статуса — брак: половина этого поля состоит из
вендорских цифр с неназванными базлайнами, и мы это уже знаем (см. wiki «Индексы кода для
агентов», раздел «Как читать их заявления»).

## Форма файла

Лимит — **160 строк**. Сырые выписки и ссылки — отдельным файлом в `measurements/landscape/`.

```markdown
# Ландшафт: <твой сегмент> — воркер <X> — 2026-08-20

## Вердикт в одной строке

## Продукты (по одному блоку, 5-9 продуктов)
### <Продукт> — <кто автор, жив ли, цена>
- **Позиционирование (цитата):** «...»
- **Источник рёбер** (по `01-legend.md`): IL / синтаксис / семантика / строки / рантайм / иное
- **Язык запросов:** есть/нет, какой, пример запроса на 1-3 строки
- **Сценарии, которые продаёт:** маркированный список, каждый со статусом
- **Что честно НЕ обещает:** прямые оговорки из документации — это ценнее рекламы
- **Упаковка:** CLI / IDE / сервер / библиотека / CI-шаг; локально или облако

## Сводная таблица сценариев сегмента
| Сценарий (словами продуктов) | Кто предлагает | Статус | Нужен ли граф или хватает grep/LSP |

## Сценарии, которых НЕТ ни у кого в сегменте
(самое ценное: пустые клетки рынка)

## Противоречия с нашими предположениями
(где рынок решает задачу иначе, чем мы собирались)
```

## Обязательная последняя колонка

Для каждого сценария ответь: **нужен ли для него граф вообще?** Три варианта — «хватает
текстового поиска», «хватает LSP/Find Usages», «нужен граф». Это и есть тот детектор, который
уже сформулирован в wiki: если потребитель всё равно получает top-k сниппетов, граф использован
как ранжировщик, и сравнивать его надо с PageRank по импортам, а не с grep.

## Чего НЕ делать

- Не пересказывать содержимое файла в чат-ответе — контекст оркестратора дефицитен.
- Не оценивать наш прототип: сопоставление — работа следующего шага, у тебя нет для неё данных.
- Не переоткрывать содержимое wiki-страницы «Индексы кода для агентов» — прочитай её и
  опирайся, а не пересказывай. Пять уровней индексов, детектор из четырёх вопросов и разбор
  JetBrains Context там уже есть.
- Не верить вендорским процентам. «До 68 %» — это не число, а диапазон от нуля.
