# Язык запросов — воркер C — 2026-08-20

## Вердикт в одной строке
**Вердикт ПЕРЕВЕРНУЛСЯ после перепроверки варианта 1.** Рекомендация: **KQL-реюз, но через
KustoLoco как исполняющий движок** (не через выписывание своего SQL-бэкенда, как я считал в
первой версии этого файла) — с ОБЯЗАТЕЛЬНЫМ patch-ем did-you-mean поверх диагностик и ручной
(precompute) реализацией транзитивности на D5, потому что `make-graph`/`graph-match` в KustoLoco
не исполняются. Причина переворота: мой центральный аргумент против варианта 1 ("0 строк
исполняющего бэкенда переносится") был эмпирически опровергнут (см. секцию ниже) — стоимость
варианта 1 падает с ~15–25 до ~7–11 чел-дней, ниже s-expr (8–14), при уже готовом, знакомом
агентам движке. s-expr остаётся близким вторым — держит закрытость словаря "из коробки"
(did-you-mean у KQL/KustoLoco надо доклеивать, не бесплатно). Часть 2 перепроверки (ниже):
альтернативный путь "тот же трансформер + DuckDbDialect + новая схема" переиспользует 88.5%
строк компилятора операторов (не 0%, как я считал), но для заявленной глубины ≤3 всё равно
дороже KustoLoco из-за церемонии БД — вердикт ДЕРЖИТСЯ, вариант 3 — задокументированный запасной.

## Перепроверка варианта 1 (KustoLoco) — по запросу координатора
Поправка к вводным координатора: `KustoLoco.Core` подключён ТОЛЬКО в `tests/PetBox.Tests.csproj`
(`grep -rl KustoLoco **/*.csproj` — один файл, не `src/**`); строки в `KqlAggregateExpressions.cs`/
`KqlTransformer.SqlComposition.cs` — КОММЕНТАРИИ про семантику, не `using KustoLoco.Core`. Движок —
доверенный ТЕСТОВЫЙ оракул (`DualExecutor.AssertSameAsync` сверяет прод-SQL-путь с KustoLoco на
каждом KQL-тесте), не продовая зависимость сегодня; перевод в прод — новый шаг со своей проверкой
(лицензия/сопровождение/память на графе 180k LOC — НЕ проверено).

Эмпирическая проверка (свой проб-проект, `KustoQueryContext.CopyDataIntoTable` на 2 POCO-таблицах,
4+3 строки, БЕЗ SQLite):
1. **Произвольная in-memory таблица + `where`/`union`/`summarize`/`join`** — ВСЕ выполнились
   корректно: `where HasAttr==true` → 2 строки; `union` двух `where` → 4; `summarize count() by
   ParentType` → `{T1:2, T2:2}`; `join kind=inner (calls) on $left.Name==$right.Src` → 3 строки с
   объединёнными колонками. Никакой трансляции в SQL для этого пути нет вообще — KustoLoco сам
   исполняет план по in-memory данным.
2. **Неизвестная колонка** (`where TypeCa == true` / `project TypeCa`) — ОШИБКА, не тихий `null`:
   "The name 'TypeCa' does not refer to any known column, table, variable or function." + встроенная
   разметка позиции в тексте запроса. По существу то же, что `KS142` у сырого `Kusto.Language`,
   оформлено даже нагляднее (маркеры прямо в запросе). Подсказки did-you-mean по-прежнему НЕТ.
3. **`make-graph`/`graph-match`** — с 4-клаузным синтаксисом (`with methods on Name`,
   `[e*1..3]`) парсится, но исполнение падает: "Query operator 'makegraph' not supported".
   Решительно: транзитивный путь НЕ работает в KustoLoco ни при какой форме — 7 форм исполняются
   "из коробки", D5 нужно самим (bounded self-join ≤3 или предвычисленная достижимость) — по D5
   KQL и s-expr теперь НА РАВНЫХ, это больше не аргумент ни за, ни против KQL.
4. **Пересчёт**: схема таблиц + POCO для `CopyDataIntoTable` — 1–2 дн.; did-you-mean-слой поверх
   перечислимого `GlobalState` — 1 дн. (НЕ построен, оценка по конструкции); completion-реюз —
   0.5 дн.; D5 precompute — 2–3 дн.; провенанс — 1–2 дн.; MCP-тул — 1–2 дн. **Итого ~7–11
   чел-дней**, ниже прежних 15–25 и ниже s-expr (8–14). Не забыто: словарь у KQL НЕ закрыт
   (доклеенный, не встроенный did-you-mean), операторов больше нужного (mv-expand/parse/lookup
   графу не нужны) — реальные минусы, но при паритете по D5 и уже показанном качестве ошибок
   (п.2) не перевешивают доверенный движок и знакомство агентов с KQL.

## Проверка прежних выводов (`02b-prior-art.md`)

   сама по себе требует только ПАРАМЕТРА у одиночного предиката — тариф "Find Usages", не язык.
   Композиции требует ровно D5-случай "A И НЕ B" — булев комбинатор. Проверено по всем 8 формам:
   D2–D4, D6–D8 — одиночные параметризуемые предикаты. Вывод уточнён, не опровергнут.
2. **"LINQ поверх модели Roslyn уже язык; Cypher строго хуже"** — с выводом ПРОТИВ Cypher согласен
   (по другой причине — непроверенное качество ошибок embedded-движка). С LINQ-как-языком-для-
   АГЕНТА не согласен: тариф "Roslyn как API" (ценой ПРОГРАММЫ, не строки) — агент шлёт запрос
   ОДНИМ tool-call без REPL/IntelliSense, LINQ-текст либо произвольный C# (риск исполнения + шум
   компилятора), либо под-грамматика — снова закрытый DSL, просто на C#-синтаксисе.
3. Формулировка владельца ("расширение KQL ИЛИ lisp-прототип") — после перепроверки вывод

## Кандидаты — один и тот же запрос (D2 простой, D5+D1 сложный)
**1. KQL + KustoLoco** (та же грамматика/диагностики, движок — не свой SQL-бэкенд)
```
types | where HasAttribute("Ns.Attr") | union (methods | where HasAttribute("Ns.Attr") | project ParentType)   // D2
// D5+D1 — make-graph не исполняется (п.3 перепроверки), поэтому bounded self-join на предвычисленной closure:
reach3 | where Src=="root" and Dst=="A" | project M=Src
| where M !in (reach3 | where Dst=="B" | project Src)
```
Ошибка на `TypeCa`: см. таблицу — имя+позиция, разметка в тексте запроса, без подсказки (доклеивается).

**2. Минимальный s-expr** (свой парсер, закрытые ~15–20 предикатов + `and`/`not`/`or`)
```
(attr-carriers "Ns.Attr" :kinds (type method))                                            ; D2
(and (calls? self "A" :max-depth 3) (not (calls? self "B" :max-depth 3)))                 ; D5+D1
```
Ошибка на `type-ca`: закрытый словарь → тривиальный Левенштейн НА БИНДЕ, встроенно:
"unknown function 'type-ca' — did you mean 'attr-carriers'?". Язык не реализован — оценка по
конструкции, не измерение.

**3. Cypher (embedded — kuzu/DuckDB PGQ)**
```cypher
MATCH (n) WHERE (n:Type OR n:Method) AND n.hasAttr = "Ns.Attr" RETURN n                    // D2
MATCH (m:Method)-[:CALLS*1..3]->(:Method {name:"A"})
WHERE NOT EXISTS { MATCH (m)-[:CALLS*1..3]->(:Method {name:"B"}) } RETURN m                // D5+D1 — нативнее всех на ЭТОЙ форме
```
Ошибка на `n.typeCa`: **НЕ проверено** (kuzu не установлен). Риск: узлы Cypher-семьи часто
схемонезависимы — неизвестное свойство даёт `NULL`, не ошибку (тот же "честный ноль" NDepend);
у kuzu схема строгая, может биндить статически — не проверено.

**4. Без языка (JSON-команды, по одной на форму + `max_depth`)**
```json
{"cmd":"attr-carriers","attribute":"Ns.Attr","kinds":["type","method"]}                    // D2
{"cmd":"calls-and-not-calls","calls":"A","not_calls":"B","max_depth":3}                    // D5+D1 — работает одной командой
```
D5 не требует взрыва команд — одна спец-команда покрывает его целиком. Слабое место — рост:
девятая форма с новой комбинацией требует нового командного имени и кода.
