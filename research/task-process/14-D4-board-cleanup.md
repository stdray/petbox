Дата 2026-09-25, автор: Claude Sonnet 5 (petbox-worker). Источники просмотрены: 9 карточек
(tasks_node_get/search), 1 сессия (session_get), код на `origin/main` через checkout ветки
`research/task-process-problems` (на 2 коммита позади `origin/main` — `git ls-tree`/`git grep

## 1. Суть проблемы одним абзацем

Владелец прав буквально («Done копится бесконечно, как и любой другой финальный статус») —
`02-snapshot.md` подтверждает цифрами: terminal-доля от 5.4% (spec, у которой вообще нет
terminalok-статуса) до 88.1% (work: 971 из 1102). Но «копится» и «вредит» — разные
утверждения. Единственный существующий инструмент — `tasks_board_close` — закрывает ВСЮ
доску целиком (governance-акт, гейтится `methodology:write`), а не отдельные терминальные
узлы внутри активной доски; узел-уровневого архива/скрытия не существует вовсе. Реальная
цена накопления неоднородна по механизмам: где-то она задокументированно постоянна
(листинги режут по `limit`, не по размеру доски), где-то растёт линейно и без предохранителя
(дедуп наблюдений сканирует ВСЕ закрытые узлы навсегда), а где-то payload доски отправляется
в браузер целиком независимо от того, сколько скрыто клиентским тоглом.

Ничего прямо по D4 не найдено целевым поиском (`архивация`/`retention`/`terminal`). Косвенно

слово, а измерить по каждому механизму отдельно (сделано в §1/§4).

## 4. Механизм: почему так происходит

- Факт: ни одна FSM не имеет обязательного перехода ПОСЛЕ терминального статуса — `Done`/
  `accepted`/`fixed`/`deprecated` висят на доске бессрочно (`tasks_workflow`, §02-snapshot).
- Факт: `tasks_board_close` — единственный рубильник, целиком по доске; закрыть его для
  `work` остановило бы ВЕСЬ процесс, а не только скрыло старое Done — несоразмерное средство.
- Факт (код): большинство путей чтения либо не прячут `terminalok` вовсе (board-страница,
  поиск с `q`), либо прячут по `statusKind` клиентски/на вызов, а не архивируют физически —
  стоимость размера доски платится на КАЖДОЕ чтение, если явно не сузить запрос.
- [гипотеза] `limit`-резание в `tasks_search` и клиентский `ActiveOnly` маскируют рост для
  агента, но НЕ для сервера (весь payload собирается) и НЕ для дедупа наблюдений (сканирует
  всё). Боль сегодня — не «агент видит слишком много», а два конкретных пути O(размер доски):
  дедуп наблюдений и полный fetch страницы доски.

## 5. Как принято в индустрии

Jira: `Resolved`/`Closed` скрыты фильтром по умолчанию, не удаляются; отдельная «Archive»
(project-level, права) физически прячет issue из поиска. Linear: авто-архивация Done/
Cancelled через N дней (настраиваемый таймер), архив — отдельным тоглом. GitHub: closed
скрыты по умолчанию, `is:closed` возвращает; нет авто-архивации. Trello: ручная Archive-
кнопка, архив — отдельный список, можно выгрузить/снести целиком. Паттерн: «скрыть по
умолчанию» — универсально и дёшево; «физически переместить» — только для дорогих путей
(поиск/индекс), не для простого листинга.

## 6. Варианты решения

- **A. Ничего не менять, только измерить.** Цена 0. Риск: два реально растущих пути (дедуп
  наблюдений, board-страница) остаются без предохранителя.
- **B. Скрыть terminalok по умолчанию на всех путях чтения** (не только `q`-поиске). Цена
  небольшая (унифицировать `FilterVisible`/`TaskBoard.cshtml.cs` под уже существующий
  `statusKind`). Ломает рамку `tasks-search-no-terminal-default` если тронуть и поиск —
  трогать только board-view default. Не снижает размер БД/дедуп-пула, только payload чтения.
- **C. Архивный флаг на узле (Linear-стиль), по возрасту с момента терминального перехода.**
  Цена средняя (поле/производный вид, джоба). Ломает: требует решить судьбу рёбер `part_of`/
  `blocks`/`observation_obligation` на архивный узел (прецедент дефекта
  `blocks-edge-never-closes-on-kind-without-blocksgate`, fixed — рёбра уже раз ломались
  тихо); дедуп наблюдений нельзя архивировать вслепую — рецидив не найдётся.
- **D. Архивация целой доски** (расширение `tasks_board_close`) — «этап закрылся → доска в
  архив», привязка к D5. Цена низкая (кнопка уже есть), но не решает накопление ВНУТРИ
  активной доски.
- **E. Time-based ретеншн (авто-удаление/компактизация старше N).** Цена высокая, риск:
  необратимо для наблюдений (recurrence-счётчик и история — то, что делает observations
  полезной; `research/flow-control` уже отметил доску как «вне очереди решений») и для
  spec/work (verdict-история, AGENTS.md п.6). Не рекомендуется без замера вреда per-board.
- Приоритет, не решение: B первым (дёшево, не ломает поиск), C — только для `work`/`intake`/
  `classic`/`client-issues`, D — синхронно с D5, E — только после замера как в §2c.

## 7. Несогласия и сомнения в постановке владельца

Формулировка «Done копится бесконечно» верна фактически (88.1% work, см. §02-snapshot), но
скрыто предполагает, что это САМО ПО СЕБЕ проблема. Прямой прецедент (§2c, memory GC job)
показывает: для соседнего модуля та же гипотеза была проверена измерением и ОТВЕРГНУТА —
цена оказалась константой на вызов, а не функцией размера. Здесь я НЕ утверждаю то же самое
для tasks (не измерено: нет данных о фактической стоимости чтения board-страницы в мс/байтах
при 1102 узлах work против гипотетических 130). Но два пути ИЗМЕРЕНО растут без потолка:
дедуп наблюдений (`includeClosed:true`, код §2d) и полный fetch `TaskBoard.cshtml.cs`. Не
согласен, что «нет способа очищать доски» — способ ЕСТЬ (`tasks_board_close`), просто
несоразмерный (весь-или-ничего); формулировка владельца скрывает, что проблема — в
ГРАНУЛЯРНОСТИ существующего инструмента, а не в его полном отсутствии.
