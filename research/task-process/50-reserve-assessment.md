## 1. По целям

**Р1 — устояло с оговоркой (несущий факт неверен).** «Одна правка данных, без кода» — нет: у инварианта
гейта нет свободного `detail` (факт 5). Данными можно заполнить только `Description` перехода — и он
виден в guide, но не в отказе. Инцидент из 19 показывает, что агент вывел содержание **из имени гейта**,
т. е. из той самой генерируемой строки. Значит нужен маленький код: описание артефакта, рендерящееся и в
инвариант, и в отказ. Всё ещё дёшево и агентское, но карточка A обещает не то.

**Р2 — опровергнуто в части (2), устояло с оговоркой в (3).**
- (2) «хотелка → intake как бэклог» — переезд свалки на доску, где 62 из 69 никто не триажировал (факт 2):
  `raw` на ideas (37) сменится на `reported` на intake. Плюс это ломает канон в двух местах: doc
  «Intake … NOT part of the requirements pipeline … holding area until each item is routed» и кит-скилл
  «Nothing in the spec reflects the ask → an idea». Хотелка по определению квартета **и есть** кандидат на
  изменение спеки — она правильно лежит в `raw`. Настоящий признак дампа — не доска, а **незрелость/низкий
  приоритет**, и для него уже есть колонка `raw`: она не гейтится, не попадает в очередь владельца и не
  мешает `review`. Дешевле: ничего не переезжает; правило кита/doc дополняется одной строкой «замеченная
  мимоходом хотелка → `raw` с `priority`, без exploring; не спрашивали — не заводи» (это и есть
  «задачи не плодим»). Кит перевыпускать не обязательно.
- (3) `research`-тип на `work`: ~5 из 122 идей (4 %) — не оправдывает новый тип, исключение в
  link-constraint и перевыпуск кита. `chore` уже spec-less по дизайну; исследование = `chore` + тег
  (`concern:research` или новая ось), результат — memory/doc. Ноль кода, одна фраза в правиле маршрута.
  Оговорка: в `work` исследование получит гейт `Review → Done` с approve — ещё одно решение владельцу
  (см. §2); альтернатива — исследование живёт на идее в `exploring` (это буквально его семантика).
- `doc/methodology.md:32` («A topic → 0..N tasks») — верно, править; `:280-281` тоже (мёртвая `roadmap`).

**Р3 — устояло с оговоркой: глагол да, «перенос» нет.** Терминализировать intake в момент промоушена
ломает две вещи: (а) `petbox_report_issue_status` — внешний репортёр увидит `done` до фикса; (б) уже
работающий эффект `Done → issue_task → done` (факт 6) — закрывать станет нечего. Правильная семантика —
`confirmed` + ребро (оба уже данные), закрытие остаётся за Done-эффектом. Тогда глагол — сахар над двумя
вызовами, которые агент может сделать сегодня (`tasks_upsert` на work с `links.issue_task` + статус intake).
Измеренная проблема D3 — 4/8 фиксов прямо на intake и 1/8 копия — это дисциплина, не отсутствие
инструмента → её место в Р10 (предупреждение при создании work-узла, чей текст совпадает с открытой заявкой
без ребра). Зависимость «Р3 после Р2» — искусственная: promote не использует «intake как бэклог».
Карточка C — `chore` **[live]** — а новый MCP-глагол это новая поверхность (feature), листа спеки под него
я не нашёл (**[live]** `spec q:"intake promote issue_task"` → ближайшие `idea-gate`, `idea-review-ceiling`);
либо глагол идёт через идею B, либо C ограничивается гардом/предупреждением и остаётся chore.

**Р4 — опровергнуто как приоритет, устояло как примитив (и только для Р7).**
- Цена накопления не измерена (П13 сам это признаёт), а по умолчанию терминальное **уже скрыто** почти
  везде (факт 6). Единственный живой симптом — узлы закрытой `roadmap` в query-выдаче; и это по спеке
  владельца **[live]** `tasks-search-status-tiers` («включено всё, закрытое ниже рангом — ярус, не
  ворота») и `tasks-search-no-terminal-default` («в query-режиме ИСЧЕЗАЮТ … флаг includeClosed»).
  Р4 возвращает `includeArchived` — тот самый убранный механизм. Это разворот решения владельца, и
  карточка D должна об этом говорить прямо, а не «лист не нарушается». Для `roadmap` есть спека

- Пункт «пул дедупа архив не видит» — **опровергнут** фактом 3: он убьёт сигнал регрессии для всего,
  что починили > N дней назад, и такие наблюдения будут заводиться заново вместо реопена.

  одной строкой раньше, чем выбирать N.

**Р5 — устояло с двумя оговорками; «почему не шипнулось» реестр не объясняет.**
- Причина: решение 28.08 жило только в `research/flow-control/60-state.md` («карточек НЕТ — осознанно»)

**Р7 — опровергнуто по несущему допущению, альтернатива инвертирована.** «Готовность считается

Закрытие этапа: у обоих вариантов без Р4 оно ничего не прячет; с тегом «закрытие» = вердикт на

## 2. Чего не видит вся картина

- **Пропускная способность владельца — узкое место, и реестр его сужает.** Один существующий owner-гейт
  стоит 70–110 дней (факт 1). Реестр добавляет: 5 решений «в один разговор» (шаг 2), пробуждения в очередь
  (Р5), рекуррентные карточки с флагом (Р8), секцию Review (Р6). Ни одно Р не **снимает** решений с
  владельца. Выход: агентские шаги вперёд; владельцу — одна идея-контейнер с 3–4 пунктами «да/нет», а не
  пять веток; и пункт «`review` старше 30 дней без решения = авто-`exploring` с пометкой» (снимает груз).
- **Решения без карточек — тот же дефект, что D6.** flow-control (28.08) и эта папка: обе живут в git,
  обе с «карточек не заводим». Минимум — ОДНА work-карточка «применить решения research/task-process»
  с чеклистом принятых Р; иначе через месяц будет `70-state` и «почему не шипнулось» ещё раз.
- **Мера успеха не задана ни у одного Р.** Для Р2: доля `raw` старше 30 дней; для Р3: доля Done-work без
  `issue_task` при совпадающей заявке; для Р4: латентность страницы `work`; для Р5: число «проснувшихся»
  за месяц. Без этого «сработало» будет решать та же память, которая забыла `spec_plan`.
- **Цепочка квартета в предкарточках:** C (см. Р3); D разворачивает два листа спеки — `spec_plan` обязан
  их назвать как изменяемые/deprecated; H — лист есть **[live]** (`owner-away-digest`, `owner-decision-pending-flag`),
  чисто; E → bug под `primitives-types-statuses-transitions` **[live]**, чисто; I — норма на всех
  проектах кита как `chore` натянуто, но без серверного поведения допустимо.
