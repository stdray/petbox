## 1. В чём вообще вопрос (он был склеен из четырёх)

Формулировка владельца («может git-lfs, может S3, либо я не совсем понял вопрос») — честная реакция на
склейку. Разводим:

| # | вопрос | короткий ответ (обоснование ниже) |
|---|---|---|
| В1 | чем артефакт **адресуется** в условии перехода | парой (единица, слаг): тег `artifact:<slug>` на активном комментарии единицы |
| В2 | где физически лежит **содержимое** | сегодня — тело комментария (GFM-текст в БД); в общем виде — где угодно, см. В3 |
| В3 | что механизм обязан **знать** о содержимом | ничего. Гейт проверяет только НАЛИЧИЕ предъявления; содержимое для него непрозрачно |
| В4 | чем **комментарий** отличается от артефакта | ничем как сущность; артефакт = комментарий + утверждение (тег). Различие в заявке, не в носителе |

git-lfs и S3 — кандидаты ответа на В2 и только на него. В1, В3, В4 от них не зависят, и именно они —
модельные вопросы. Это главное распутывание файла.

## 2. Как устроено сегодня — по фактам

- **Носитель**: комментарий узла. `comments_upsert` — `tags` это открытые строки, конвенция
  `artifact:<slug>` помечает артефакт; `body` — GFM-markdown в БД. `comments_search(node:...)` /
  `comments_get(id)` — чтение.
- **Живой пример**: идея `kind-worlds-decision-paths` (`$system/ideas`), комментарий
  `fd9a5600edc74195b15d88bd4af4622b`, тег `artifact:spec_plan`, тело — markdown-план правок спеки.
- **Гейт**: `preconditionArtifact:"spec_plan"` на переходе `exploring→review` kind'а доски `ideas`
  (`tasks_methodology_rules_get(key:"quartet")`). Сервер (`GuardEngine.RequirePreconditionArtifacts`,
  `src/PetBox.Tasks.Engine/GuardEngine.cs:372`) проверяет ровно одно: среди активных комментариев узла
  есть тег `artifact:<slug>`. Тело не читается вовсе — тег на пустом комментарии гейт проходит.
  Обход через рождение сразу в гейченом статусе закрыт.
- **Обобщение уже началось в коде**: `RequiredArtifactDef(Slug, Inline)` в
  `src/PetBox.Tasks.Engine/MethodologyDefinition.cs` — schema v2 сворачивает `requiresReason` и
  `preconditionArtifact` в один список «требуемых артефактов»: reason — это inline-артефакт (контент
  едет полем того же вызова), spec_plan — non-inline (комментарий должен уже существовать). Это прямое
  подтверждение гипотезы §4 из `07-requirements.md` на паре из пяти строк таблицы G легенды.
  Потолок v1: реально энфорсится один inline + один non-inline на переход.
- **Вложений/файлов/S3/LFS в petbox НЕТ**: grep по `origin/main` даёт только случайные совпадения
  («cache attachment point» и т.п.). Изобретать не с чего — и не по чему промахнуться.
- **Реальный предел носителя**: тела комментариев платятся контекстом читающего агента
  (`comments_search`, бюджет ~30k на ответ) и рискуют клиентской обрезкой при больших телах
  (задокументировано в `comments_upsert`). Это и есть та «боль», на которую пришлось бы отвечать
  хранилищу, — сегодня она не наблюдена ни на одном живом артефакте.

## 3. Примитив в обобщённом виде

**Artifact (артефакт) — именованное свидетельство, предъявленное единице.** В терминах
`08-model-draft.md` это уже есть: атом `bring: artifact(kind)` в условии перехода.

- **Адрес**: (Unit, slug). Слаг — из словаря процесса (`spec_plan`, `reason`, ...), не глобальный.
- **Механизм знает**: существование, слаг, активность (не удалён), автора, версию. Всё это у
  комментария уже есть.
- **Механизм НЕ знает**: содержимое, формат, размер, где лежат байты. Тело — либо само содержимое
  (текст), либо указатель на него (URL, путь@SHA, id лог-потока). Для гейта эти случаи неразличимы,
  и это свойство надо сохранить: гейт проверяет предъявление, честность содержимого держится
  review'ом владельца — ровно как `enforceApproval:false` в таблице G легенды.
- **Комментарий и артефакт не разводить в две сущности.** Носитель один; артефактность — это
  утверждение «данный комментарий есть свидетельство рода X», т.е. тег. Развести их — значит завести
  второй параллельный путь с телом, автором, версией и удалением, что режется правилом отсечения.

Следствие для модели: примитиву «хранилище» в модели МЕСТА НЕТ. Есть атом `artifact(kind)` и есть
носитель-комментарий; вопрос «где байты» — вне модели, как хранилище и транспорт по §5 требований.

## 4. Сценарии → где содержимому естественно лежать

| сценарий | где лежит содержимое | нужен ли НОВЫЙ механизм |
|---|---|---|
| комментарий-обоснование (reason) | тело комментария / поле `reason` перехода (inline-артефакт) | нет |
| план спеки (`spec_plan`) | тело комментария, markdown | нет — живой пример работает |
| ссылка на коммит | SHA в теле; у единицы и так есть привязка к коммитам (§2.1 требований) | нет |
| ссылка на внешний документ | URL в теле | нет |
| скриншот | вне PetBox; в теле — ссылка (файл, внешний хост) | нет сейчас; кандидат на blob-store, если ссылки докажут протухание |
| лог прогона | лог-модуль PetBox (`log_create`/`log_query`) или файл; в теле — указатель | нет — существующий модуль уже это умеет |
| большой дамп | файл/внешнее хранилище; в теле — указатель | нет сейчас; тот же кандидат, что скриншот |

Итог: **0 из 7 требуют нового механизма сегодня**; 2 (скриншот, большой дамп) живут на внешней
ссылке, у которой есть известная цена — протухание и недоступность байтов агенту через PetBox.
Наступление этой цены — измеримое условие возврата, а не повод строить заранее.

## 5. git-lfs и S3 — по правилу отсечения

**git-lfs — не берём.** Это деталь хранения больших файлов внутри git-репозитория, а не механизм
PetBox. Если содержимое артефакта живёт в репо проекта, адресация «путь@SHA» в теле комментария
работает уже сейчас, и хранится ли файл в lfs — репозиторию виднее; PetBox об этом знать не должен
(В3). Прикручивать же git-репозиторий к серверу PetBox ради артефактов — сложность против текущего:
появляется второй стор со своей синхронизацией и GC. Вернуться: никогда как к механизму PetBox;
как конвенцию «артефакт = файл в репо, в комментарии ссылка» можно применять хоть сегодня без
единой строчки кода.

**S3 (заливка + надстройка) — не берём сейчас.** Что решает: байты больших/бинарных артефактов
доступны через PetBox, ссылки не протухают. Чего стоит: bucket/креды/лайфцикл, API заливки, GC
осиротевших блобов, связь блоб↔комментарий, доступ для агента — целый модуль против «тег на
комментарии», при нуле наблюдённых больших артефактов в `$system`. Вернуться, когда: (а) появился
живой сценарий, где агенту нужно записать И прочитать бинарь/дамп через PetBox, и (б) внешние ссылки
доказуемо ломались. Тогда форма — маленький content-addressed blob-store за существующим API
(тело комментария несёт `blob:<hash>`), а S3 — лишь возможный бэкенд этого стора, деталь реализации,
в модель не попадающая. Инвариант В3 сохраняется: гейт по-прежнему видит только тег.

## 6. Что осталось невыясненным

1. **Пустое свидетельство проходит гейт** — тег без тела сервер пропустит (проверка presence-only).
   Дефект это или свойство («содержимое сторожит владелец») — решение владельца; минимальная
   проверка непустоты тела дешева, но это уже чтение содержимого — первый шаг за черту В3.
2. **Судьба свидетельства после удаления комментария**: гейт пройден, комментарий удалён — переход
   остаётся, предъявление исчезает. Нужен ли снапшот/запрет удаления артефактных комментариев —
   не решено; данных о реальных случаях нет.
3. **Потолок v1** (один inline + один non-inline на переход) — хватает всем живым определениям;
   когда понадобится больше одного, проверить, что `RequiredArtifacts`-список энфорсится целиком.
4. **Мера боли не снята**: ни распределение размеров тел артефактных комментариев, ни случаи
   обрезки/протухания никто не мерил. До этих измерений любое хранилище — решение без задачи.
