### П-3. «Цепочка неконструируема» под C
- **04-summary (§5, «Мера») говорит:** «ЦЕЛЬ — цепочка неконструируема»; классы ошибок, ставшие невозможными под C: «…adopt-застревание, зомби-заморозка».
- **c-lifecycle говорит:** новая цепочка `board_close → rules_upsert без migration (закрытая доска вне scope валидации) → board_reopen` даёт застрявший узел БЕЗ закрытия инстанса; «даже под C доска может быть закрыта на старых правилах каталога, потом кто-то поменяет каталог, потом reopen — тот же зомби-узел».
- **Вердикт:** права c-lifecycle. Проверено мной: фильтр `b.ClosedAt is null` в scope валидации обоих сервисов (MethodologyInstanceService.cs:201, MethodologyDefinitionService — аналогичный паттерн), reopen — голый тоггл; её живой пробник `zt1` виден в песочнице (доска `zt1` теперь в инстансе `zt2` — след пробы adopt). C устраняет ТОЛЬКО adopt/close-instance маршрут; класс «застрявший узел» переживает C, чинится вербами `board_close/reopen` + migration (Р-3).

### П-4. Почему застрял `n1` — «instance is closed»
- **04-summary (§5, узел S4) говорит:** «n1 ЗАСТРЯЛ НАВСЕГДА … needs a known type page, got note / type is immutable / **instance is closed**».
- **e-live-data / c-lifecycle говорят:** `wiki2.methodologyInstance == "$utility"` (всегда открыт); `n1` застрял из-за иммутабельности типа + текущий kind `wiki` слоя знает только `page`, не из-за закрытого инстанса.
- **Вердикт:** правы инвентари. Перепроверено мной sandbox-ключом (lab-mcp.json) сегодня: `wiki2` — `closed:false`, членство `$utility`. Диаграмма §5 описывает пройденное состояние цепочки как текущее/итоговое; «instance is closed» в финальном узле ложно. Оркестратор чинил снимок, но не сводку и не `diagrams/*.mmd` (источник истины картинок — чинить там ТОЖЕ).

### П-5. «Три поколения хранилищ в MethodologyDefinitionService»

## Что инвентари добавили сверх сводки
- **6-я копия логики резолвинга**: `GetMethodologyGuideAsync` несёт свою active/single-open/ambiguous ветку, не вызывая `RuntimeAsync` (b-resolution, TasksService.cs:683-719) — сводка §4 рисует «два алгоритма».
- **guide структурно не принимает `board`** (схема тула без параметра) и **молчит про битый активный указатель** — репортит «none active», не называя dangling `alt` (d-surfaces). Сводный каталог невозможен ни одним вызовом.
- **UI**: бейдж «not active» называет `$utility` «open methodology instance» (ложь лейбла по легенде D); админ-страница `ProjectMethodology.cshtml.cs` структурно не видит утилитарный слой (d-surfaces).
- **Cross-DB цена C**: членство доски живёт в Core-БД, документы правил — в per-project tasks-файле; 4 разные схемы, 4 независимых курсора версий (a-storage). Сводка §4 обещает «каждая часть цели срезает код» — cross-DB часть не срезается, пока граница Core/per-project стоит.
- **Затенение dual-read**: stored-шаблон с ключом `"methodology"` молча затенит легаси-документ (a-storage).
- **Коллизии не безобидны**: документы `smoke-verdict-gate` для `intake`/`ideas`/`spec`/`work` СОДЕРЖАТЕЛЬНО отличаются от quartet v22 (verdict-артефакты, статус `Deferred`…) — «merge» коллизий при A/C ещё опаснее, чем сводка предполагает (e-live-data).
- **Рецепт владельцу**: ~45 дешёвых вызовов для точной цены C по 9 непросмотренным проектам (e-live-data, раздел «Что владелец должен снять»).
- **`ResolveActiveKeyAsync` уже трактует протухший указатель как отсутствующий** — dangling ломает только поверхности чтения, не резолвинг досок (c-lifecycle).

## Что из инвентарей просится в реестр решений
- **Р-1. Принять: закрытый инстанс исключён из области уникальности слага (веха A)** — закрытый = запись истории вне каталога. Альтернатива: чистка/переименование 5 smoke-коллизий до включения A. Без решения веха A невключаема — существующие данные нарушают правило в момент включения (e-live-data, 02-snapshot).
- **Р-2. Принять: читаемость правил закрытых процессов — флаг `closed` в едином каталоге, БЕЗ отдельной сущности «архив»** — альтернатива: новая таблица-архив (+миграция, +поверхность чтения). Без решения цена C неисчислима, а сводка ссылается на несуществующую сущность (a-storage, П-1).
- **Р-3. Принять: `board_reopen` прогоняет валидацию живых узлов против текущих правил** — альтернатива: reopen остаётся тогглом, застревание чинится отдельным migration-вербом. Без выбора класс «застрявший узел» переживает C (c-lifecycle, П-3).
- **Р-4. Принять: необратимость `tasks_methodology_close` — намеренный контракт, наследуемый C** — альтернатива: завести `methodology_reopen`. Без явного выбора закрытие процесса под C останется единственным необратимым вербом без обратного, и никто не сможет сказать, дизайн это или дыра (c-lifecycle).
