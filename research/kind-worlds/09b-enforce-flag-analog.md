# 09b — Аналог включения/отключения флага под «носитель правила и есть маркер»

Дата: 2026-08-26. Источник данных — живой `$system`, снято `tasks_methodology_rules_get(key:"quartet")`
и `tasks_methodology_utility_get`, версии 22 и 2. Ролей нет, только `owner` (§6 `07-requirements.md`).

## 1. Инвентаризация — по живым данным

Всего 34 перехода в quartet (intake 5, ideas 12, spec 1, work 9, wiki 7) + 7 дублей `wiki` в
утилитарном слое (тот же документ, не считаю отдельно — это дубль-декларация, к теме не относится).
`checklist` — **0 переходов** во всей живой конфигурации; ветку проверить не на чем, только на
бумаге. `preconditionArtifact` — 1 переход.

| комбинация (RA/enforce/RR/artifact) | штук | примеры |
|---|---|---|
| F/F/F/— (свободный переход) | 20 | Pending→InProgress, draft→live, raw→exploring |
| F/F/T/— (только причина) | 6 | triage→duplicate, triage→wontfix, review→rejected, exploring→rejected, live→stale, draft→stale |
| F/F/F/spec_plan (только артефакт) | 1 | exploring→review (ideas) |
| **T/F/F/— (одобрение, НЕ блокирует)** | **3** | confirmed→done (intake), review→accepted (ideas), Review→Done (work) |
| **T/F/T/— (одобрение + причина, НЕ блокирует)** | **4** | raw→shipped, exploring→shipped, review→shipped, deferred→shipped (все ideas) |

Точный пересчёт целевой комбинации: **`requiresApproval:true` встречается 7 раз во всей живой
конфигурации `$system`, и во всех 7 `enforceApproval:false`.** `enforceApproval:true` не
встречается **ни разу** — ни в одном из 34 переходов. Это не пробел выборки: гейт-одобрение в
`$system` эксплуатируется owner'ом **только** в honor-полярности, о чём подробнее в §4.

Второй факт того же порядка: `reason_required` и `precondition_artifact` в живом `invariants`
всегда выходят как обычные (не `_convention`) варианты — у этих двух механизмов сегодня нет
работающего honor-режима в `$system` (хотя схема, по описанию `tasks_methodology_guide`, такую
пару `..._convention` умеет отдавать). Значит, реальная развилка Р-12 существует **только для
одного механизма из четырёх — одобрения**; остальные три уже сегодня «данные — всегда сервер»,
и (a) их не трогает.

## 2. Что станет с каждой комбинацией

**F/F/F (20), F/F/T (6), F/F/F+artifact (1) — итого 27 переходов: без изменений.** Сегодня это
уже «данные → сервер проверяет всегда». Под (a) они остаются данными как есть — не то место,
где 07a вообще что-то меняет.

**T/F/F (3) и T/F/T (4) — 7 переходов: развилка настоящая, и вариант «остаться данными» не
бесплатен.** Под (a) данные проверяет сервер ВСЕГДА — honor-полярности у данных нет. Значит:

- **(i) остаться данными → стать блокирующими.** В словаре черновика (`08-model-draft.md`)
  это условие `signature(by: owner)`, всегда проверяемое сервером. Но в `$system` нет механизма
  «owner подписывает, агент продолжает без остановки» — есть только ручное закрытие карточки
  самим владельцем. Сделать `signature` блокирующим значит: agent физически не выполняет
  `confirmed→done` / `review→accepted` / `Review→Done` / `*→shipped` сам; нужен либо синхронный
  owner на связи в момент каждого перехода (обычно не так — задачи копятся и закрываются
  пачкой), либо новое состояние «ожидает подписи» с очередью и уведомлением. Второго не
  существует сегодня — это **новая инфраструктура сверх текущей реализации**, и по правилу
  отсечения §6 `07-requirements.md` она не считается «бесплатной сменой ярлыка».
- **(ii) уйти в прозу памятки доски.** Работает без новой инфраструктуры, но это и есть прямой
  вопрос владельца: **`Review → Done` сегодня — строка в машиночитаемом `invariants`
  (`{"kind":"work","rule":"approval_gate","detail":"Review -> Done"}`), которую агент разбирает
  программно.** Уйдя в прозу, она пропадает из `invariants` насовсем — не появляется даже как
  `..._convention`-запись, потому что у (a) такой записи не существует: «данные» и «конвенция» —
  не два значения одного поля, а два разных носителя.

Поскольку (i) отклоняется отсечением, **реальный исход для всех 7 — уход в прозу**, то есть все
100% сегодняшних owner-only гейтов `$system`. Компенсируется это только рукописно: автор памятки
сам перечисляет каждый такой переход и держит текст в синхроне при переименованиях статусов
(хрупкое место, см. §6 `07-requirements.md`). Инструмента, проверяющего расхождение прозы с
фактическими переходами, при (a) нет и быть не может — он сам потребовал бы носителя-данные,
что противоречит идее «носитель и есть маркер».

## 3. Согласование с генерацией прозы

Сегодняшний гайд (`tasks_methodology_guide`, дословно из живого `$system`) для honor-гейта:

> The agent NEVER performs Review -> Done — that transition is the owner's/maintainer's call,
> owner-only (convention — the server does not block it; this gate holds only because the agent
> is honest about it). Stop at Review and hand over.

и для kind без гейтов вообще (wiki):

> No approval gate in this kind — the executor sets promoted themselves; nobody else is expected
> to approve.

Обе строки сгенерированы одним и тем же кодом из одного и того же поля (`requiresApproval` ×
`enforceApproval`) — единообразно для всех kind'ов, воспроизводимо, без ручного текста.

Под моделью без флага для тех же 7 переходов сгенерировать программно уже **нечего** — правило
живёт не в `rules`, а в прозе памятки доски, которую пишет человек. Дословный аналог для
`Review → Done` выглядел бы примерно так (написанным РУКАМИ владельца в теле памятки, не
выведенным):

> Review → Done is the owner's call. The agent stops at Review — this is not checked by the
> server, it holds because the agent is honest about it.

Сравнение по трём признакам:

1. **Понятно ли агенту, кто сторожит.** Формально да, если текст написан аккуратно и прочитан
   целиком. Но единообразия нет: 7 сегодняшних строк сгенерированы одним алгоритмом; 7 рукописных
   зависят от того, кто и когда их писал, и ничто не мешает забыть один переход при правке доски.
2. **Можно ли разобрать программно.** Нет. `invariants` не получает запись для этих переходов ни
   в каком виде — ни `approval_gate`, ни гипотетический `approval_gate_convention`. Надстройка,
   которая захочет спросить «какие переходы ждут owner'а», не может это вычислить — придётся
   парсить свободный текст памятки эвристикой, то есть тем самым «языком предикатов над прозой»,
   которого методология избегает вводить в другом месте (`08-model-draft.md`, «Условия»).
3. **Не стало ли длиннее.** Построчно — не длиннее, часто короче (фраза на весь kind вместо
   фразы на переход). Экономия мнимая: теряется точность per-transition. Если сохранить её
   (в ideas это четыре разных перехода `*→shipped`, каждый отдельно), проза повторяет тот же
   объём вручную — без генерации и без гарантии синхронности с фактическими переходами.

## 4. Вердикт

Не окупается — во всяком случае не как чистая модель (a) из `08-model-draft.md`, применённая
буквально к сегодняшнему `$system`.

Ключевой факт из живых данных: гейт-одобрение в `$system` используется **исключительно** в
honor-полярности — 7 из 7 переходов с `requiresApproval:true` имеют `enforceApproval:false`,
`enforceApproval:true` не встречается вовсе. Это не мёртвая ветка API, которую не жалко
выбросить, — это **единственная** полярность, которой владелец реально пользуется каждый день,
ровно затем, чтобы правило было видно агенту программно, но не останавливало работу до
синхронного участия человека. Модель (a) не умеет выразить именно эту точку: «данные» у неё
означает «сервер проверяет всегда», без промежутка. Единственный способ сохранить сегодняшнее
поведение для всех 7 переходов — увести их в прозу, а это ровно то, что убирает их из
машиночитаемого `invariants`, который агент сегодня разбирает программно.

Если владелец готов принять это как цену — а именно: `Review → Done` и шесть его соседей
перестают быть данными, которые видит любая будущая надстройка над `invariants`, и становятся
рукописным текстом без проверки на расхождение — тогда (a) можно принимать, но не как бесплатное
упрощение, а как сознательный отказ от машиночитаемости для самой употребительной сегодняшней
комбинации. Если нет — гипотеза 07a («носитель и есть маркер») в чистом виде здесь не проходит
именно на той комбинации, которую задание просило пересчитать точно, и нужен третий носитель —
по факту это данные, помеченные как необязывающие, то есть вариант (b) `enforce: server | honor`
под другим именем, а не его отсутствие.
