# research/ — рабочие пространства исследований

Здесь живут **черновые пространства** больших разборов: инвентари, снимки состояния,
реестры решений, предкарточки, диаграммы. Один подкаталог на тему.

Заводится скиллом `analysis-workspace`; форма и стадии описаны там.

## Чем это НЕ является

- **Не документация.** `doc/` поддерживается и читается при онбординге; расхождение с кодом
  там чинится в том же изменении, что его вызвало. Здесь — черновики, которые устаревают
  по определению.
- **Не источник истины.** Авторитетны доски `$system` и спека. Ничто отсюда не является
  основанием для кода: карточка предшествует коду, а не файл из этой папки.
- **Не архив.** Разбор, который отработал и промоутнут в карточки, можно удалять. То, что
  осталось, помечается датой и состоянием.

## Почему в репозитории, а не снаружи

Раньше такие папки держали вне репозитория из-за риска `git clean` для untracked-файлов.
Это решало один риск и создавало другой: работа терялась вместе с машиной и была не найдена
следующей сессией. Внутри репозитория, на своей ветке, — и не теряется, и в `main` не
попадает без явного решения.

## Правила

1. **Ветка, а не `main`.** Ветка вида `research/<тема>`. Мержить в `main` — отдельное решение
   владельца; по умолчанию не мержится.
2. **`00-INDEX.md` обязателен.** Папка с нумерованными файлами, по которой нельзя
   сориентироваться, хуже чата.
3. **Датировать каждый файл** и называть состояние, против которого он писан
   (`origin/main` SHA, ответ живого сервера) — иначе через неделю непонятно, что устарело.
4. **Легенда терминов — первым файлом**, не последним. Слово с двумя референтами портит
   каждый следующий файл незаметно.
5. **Один файл — один автор.** Параллельные субагенты, пишущие в общий файл, коллизируют.
6. **Правка решения не распространяется сама** — после неё поиск старой формулировки по
   всей папке.
