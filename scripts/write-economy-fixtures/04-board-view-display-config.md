## Боль

Сейчас КАЖДЫЙ режим сам решает, что показать у узла, и это зашито в его разметку: table всегда рисует семь колонок (включая `delivery`, которое вне spec ВСЕГДА пустое), kanban всегда показывает теги и приоритет, outline не показывает ничего сверх заголовка. Пользователь не может ни убрать лишнее, ни добавить нужное.

Набор свойств — ещё одна ортогональная ось, а не свойство режима.

## Суть

Отображаемые свойства (тип, статус, приоритет, теги, updatedAt, delivery, тело, блокеры…) выбирает ПОЛЬЗОВАТЕЛЬ через диалог, и выбор применим К ЛЮБОМУ режиму. В базе **даже outline умеет показать всё** — просто его пресет по умолчанию выключает часть полей. Режим задаёт только ПРЕСЕТ по умолчанию, а не потолок возможного.

Связь с уже сделанным: `delivery` — вычислимое поле spec-узлов (считается из входящих `task_spec` при каждом чтении). На work/intake оно ВСЕГДА пусто — значит в table там сейчас мёртвая колонка. Это ровно та боль, которую лечит пресет свойств по кинду/режиму.

## Сюда же — отображение статуса

Статус сейчас режет глаз во всех режимах (мейнтейнер, 2026-07-12). Два следствия, оба ложатся в эту же ось:

1. Статус — такое же выключаемое свойство, как теги или приоритет. В дереве/outline его разумно гасить по умолчанию.
2. **Но терминальный ОТРИЦАТЕЛЬНЫЙ статус (Cancelled / rejected / deprecated / wontfix) должен оставаться виден ВСЕГДА** — и не бейджем, а самой формой строки: зачёркнутый заголовок. Иначе, скрыв статус, мы скроем тот факт, что требование отменено/устарело — читатель будет верить мёртвому тексту.

Зачёркивание — это не «ещё одно свойство», а инвариант поверх любого пресета свойств: как бы пользователь ни настроил колонки, мёртвое обязано выглядеть мёртвым. Применимо там, где методология явно маркирует терминально-отрицательную категорию статуса (`StatusKind.TerminalCancel` уже есть в движке) — т.е. спека (`deprecated`) и wiki-подобное, где есть «устарело».

## Где хранится выбор

Тот же вопрос, что у режима просмотра (сейчас localStorage по ключу доски). Не решать здесь — это часть `ui-state-persistence` (синхронизация UI-состояния localStorage ↔ сервер). Просто не плодить третий механизм памяти.

## Non-goals

- Сохранённые наборы/профили колонок с именами — это уже `board-saved-queries`.
- Перетаскивание/ширина колонок — рюшечки, потом.
