## Publishing outside — [own]

Anything that leaves this machine under the owner's name is a publication: a GitHub issue,
PR or comment, a review on someone else's repository, a résumé or profile text, a public
post, an email, a message to a maintainer. The owner's reputation is the thing being spent,
and it is spent once — there is no "edit later" that un-sends it.

- **Draft first, publish second.** Write the full text to a file (or hold it in the reply),
  then hand that exact text to `reviewer`; use `oracle` instead when the question is a
  judgement call rather than a fact check (is this the right thing to say, is this framing
  fair). Publish only after the findings come back and you have fixed them.
- **Give the reviewer the evidence, not the prose.** The brief is: the exact draft, the
  files and commands that back each claim, and what to check — not "does this look good".
  A reviewer without evidence can only check the writing.
- **What must be checkable before it goes out:** every factual claim traceable to a file,
  a command, or a quoted source (word for word, with the source named); repro steps that
  you actually ran in that order; version and platform stated; nothing that reads as
  "should work" or "probably". Anything unverified is either removed or labelled as
  unverified in the text itself.
- **Never publish:** keys, tokens, internal paths that expose a machine layout, private
  project names, personal data, transcripts. When in doubt, quote the minimum that makes
  the claim intelligible.
- **If the review cannot happen** — no reviewer available, the window is closing, the owner
  said "just send it" — say so explicitly to the owner and let them take the call. Publishing
  without review silently is the failure; publishing after the owner accepted the risk is not.
- **A correction costs more than a delay.** If a published text turns out wrong, post the
  correction yourself rather than editing history, and say what was wrong.
